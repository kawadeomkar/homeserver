# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Infrastructure repo for a homelab: the Ansible that configures the machines and builds a Kubernetes cluster on them,
and the manifests Flux applies to that cluster (`k8s/`). There is no application code.

- **Ansible**, run from this machine: `roles/truenas` (the NAS, through its API), `roles/proxmox_apt` (the
  hypervisor's package repositories and upgrades), `roles/proxmox_tailscale` (remote access: the hypervisor on the
  tailnet, and with routes the LAN's Tailscale subnet router, behind a forwarding guard), `roles/proxmox_storage` (its
  VM-disk storage on the NAS), `roles/proxmox_backup` (the nightly backup of its VMs), `roles/proxmox_vm` (the
  cluster's VMs and Home Assistant's), `roles/haos_onboard` (a new Home Assistant's owner account), `roles/talos`
  (Talos Linux on the cluster's VMs), `roles/flux_bootstrap` (the Flux Operator, which hands the cluster to Flux),
  `roles/app_scale` (`make suspend` and `make resume`: the apps scaled to zero and back) and `roles/status` (`make
  status`: what runs and what needs doing, read without changing anything).
- **Flux** syncs `k8s/clusters/<setup>` from this repository: the platform in `k8s/infrastructure/` (MetalLB,
  Traefik, cert-manager, local-path-provisioner, csi-driver-nfs with a NAS, kube-prometheus-stack, Intel's GPU
  plugin) and the apps in `k8s/apps/` (the media apps, Nextcloud, PhotoPrism, Frigate, Homepage). Home Assistant is
  a VM of its own, Home Assistant OS, which `homeassistant.yml` creates.

**Built, and run as test deployments.** On 2026-10-17 the whole chain ran on the home machines (the NAS, Proxmox, the
cluster's VMs, Talos, Flux and every app), before its merge, and was rebuilt with a new secrets bundle after a security
review (`docs/SECURITY-REVIEW.md`, gitignored; `scripts/runbooks/teardown.md` takes it down). The run found two things
no fake had modelled, both fixed: Talos finds a Proxmox disk by its slot, never its serial (`kubernetes_disk_slots`),
and Talos 1.14.2 leaves a pending install's phase out of its status. On 2026-10-20 the setup without a NAS ran the whole
chain too, on a second Proxmox host, the apps a few at a time; it found that a 10 GiB data disk never mounts and that
the apps' images outgrow a small worker system disk, both refused now (`kubernetes_settings_error`). Treat the cluster
as disposable until it holds data worth keeping.

## Direction of travel

The repo targets exactly two setups, one host of each kind (hardware in `docs/MACHINES.md`, which is gitignored):

| Machine | Role |
|---|---|
| `homeserver` | **Proxmox** hypervisor; the cluster runs in **Talos Linux** VMs on it, a control plane and a worker in both setups. Also on the tailnet, the one way in from outside, when `local.yml` sets `tailscale_enabled`, and the LAN's Tailscale subnet router when it gives `tailscale_advertise_routes` |
| `truenas` | TrueNAS Community Edition; external storage for Proxmox's VM disks and backups and for the cluster's shared data. **Optional**: with no NAS address in `local.yml`, the NAS play ends by itself and everything stays on the Proxmox host (below) |
| `opnsense` | router and firewall; the LAN's DHCP reservations and the cluster's wildcard DNS record, by hand |

Two switches pick the setup, both worked out from `local.yml`, never set: `nas_present` (a NAS address) and
`kubernetes_present` (node addresses). The decisions behind the cluster are `docs/KUBERNETES-PLAN.md`, its work
packages and their status `docs/KUBERNETES-IMPLEMENTATION.md` (both gitignored). Still open: the owner's steps
(`TODO.md`): DHCP reservations, a servers VLAN, the CA on each device.

**History.** The repo began as manifests for a single Ubuntu host running k3s (after minikube and microk8s), mostly
generated by `kompose`, with the Ansible that configured that host. Both are gone: the host's roles, playbooks and
Vagrant setup were deleted (Talos has no SSH, apt or user accounts), and the old `k8s/<service>/` directories were
rewritten as `k8s/apps/` and `k8s/infrastructure/` under Flux. They are in the git history. Nothing in the tree
carries their assumptions any more (hostPaths under `/opt`, NodePorts, k3s's bundled Traefik and ServiceLB,
privileged media pods); an old branch that does is dead weight. `docs/ISSUES.md` and `docs/MIGRATION-TRIAGE.md`
(gitignored) audited that tree, and most of their findings are moot since.

Always run tools from the project's virtualenv, never from `PATH`. On this machine that is the pyenv virtualenv `homeserver` (Python 3.14.6, under pyenv's `versions/3.14.6/envs/`); `make` uses the active virtualenv (`VIRTUAL_ENV`) and otherwise the virtualenv `python3` runs from, only when the checkout chose it: `pyenv local homeserver` (a git-ignored `.python-version` at the checkout's top, or the main checkout's for a worktree) or `pyenv shell`, never pyenv's global version or a `.python-version` above the checkout, which `make install`'s `poetry sync` would empty; `VENV=<path>` overrides both. make never creates an environment: the user makes and keeps it wherever they like, and `make install` fills it, refusing a Python that is not a virtualenv, since `poetry sync` removes every package the lock does not list. Without any, make stops on every target but `help`. Poetry is the exception: it comes from `PATH` (`POETRY=<path>` overrides), installed outside the project's environment, e.g. with `pipx install poetry`. Never install it into the `homeserver` env: `poetry sync` would remove its dependencies. `make` runs it with `VIRTUAL_ENV` set to the project's environment; without one, Poetry would make an environment of its own in its cache. Outside the checkout, where no `.python-version` applies, `python3` resolves to a broken pyenv build (3.13.1, `libintl` dyld error), and `~/.local/bin/ansible-playbook` and `~/.local/bin/yamllint` have a dead shebang. ansible-core 2.21 treats a non-boolean conditional as a fatal error. When the shell's standard handles are non-blocking, ansible commands exit with "Ansible requires blocking IO"; redirect stdin from `/dev/null` and stdout/stderr to a file.

`kubeconform` is the usable gate for manifests — `kubectl --dry-run=client` is not, since it needs a live API server for OpenAPI validation. `kubectl` v1.36.2 (with Kustomize v5.8.1 embedded), `kubeconform` v0.8.0 and `kube-linter` v0.8.3 are what works locally. `make lint TYPE=manifests` runs kubeconform strictly against the Kubernetes version Talos ships, with the schemas pinned to one commit and cached in `.cache/kubeconform`. `make lint TYPE=manifests` runs kube-linter with `.kube-linter.yaml`: its default checks, minus three that contradict choices made here (read-only root filesystems, non-root users, memory limits), plus the liveness and readiness probe checks, a check that every container requests memory and one that rejects `imagePullPolicy: Always`. **It lints what Flux applies, not the files**: `scripts/ci/render_manifests.py` builds each path a setup's Flux Kustomizations apply with kustomize and substitutes the placeholder settings (`tests/fixtures/cluster-settings.yaml`) into `.cache/k8s-rendered/<setup>/`, because kube-linter silently skips an object it cannot decode, and a limit of `"${GPU_I915}"` is no quantity until Flux substitutes it (linting the raw files dropped Jellyfin's and Frigate's Deployments without a word). The script fails on a manifest no setup applies, and `test_k8s.py` checks that every quantity parses once substituted, which neither kubeconform (any string passes its schema) nor kube-linter reports. A workload that needs what a check forbids carries an `ignore-check.kube-linter.io/<check>` annotation saying why. Both tools come from `PATH`, as gitleaks does for the leak checks (Homebrew here, pinned by version and checksum in CI); the idempotence tests also take `openssl` from `PATH`, for the fake NAS's certificate.

Vault: `group_vars/all/local.vault.yml`, git-ignored like `local.yml` and committed nowhere: nothing reads it from the repository, and this public repo would publish even its ciphertext (until 2026-10-20 it was committed as `group_vars/all/vault.yml`, which the commits from then keep; README's "The vault" has the one-time move, and the new path is one no commit ever held, since a checkout of an older branch overwrites an ignored file without asking). `local.vault.yml.example` lists its keys, and `tests/policy/test_vault.py` checks that it names every vault variable the group_vars read. `ansible.cfg` sets `vault_password_file = ./.vault_pass`, so `--ask-vault-pass` is unnecessary locally. It holds `vault_truenas_api_key` (read by `group_vars/nas/connection.yml`), with remote access `vault_tailscale_auth_key` (a one-off Tailscale auth key, read by `group_vars/proxmox/tailscale.yml` and spent at the host's first login; a spent one does nothing), with Home Assistant `vault_haos_owner_password` (its owner account's, read by `group_vars/proxmox/haos.yml`), optionally `vault_truenas_mail_password` (the alert mail's server, read by `group_vars/nas/truenas.yml`), and `vault_discord_token`, left over from the deleted roles. Never the Talos secrets bundle: it is every key of the cluster, and lives in `talos_config_dir` alone (`kubernetes_settings_error` refuses `vault_talos_secrets`). Never print its contents; check it by listing variable names only.

## Architecture

### Infrastructure Ansible

Infrastructure roles in four playbooks: `truenas.yml` runs `roles/truenas`, `proxmox.yml` runs `roles/proxmox_apt`, `roles/proxmox_tailscale`, `roles/proxmox_storage` then `roles/proxmox_backup`, `homeassistant.yml` runs `roles/proxmox_vm` and `roles/haos_onboard` on the Proxmox host, `kubernetes.yml` runs `roles/proxmox_vm` on the Proxmox host and then `roles/talos` and `roles/flux_bootstrap` on the controller, and `site.yml` runs all four, NAS first. `talos-upgrade.yml` and `etcd-snapshot.yml` run the talos role's `upgrade` and `etcd-snapshot` entry points, after a play on localhost that refuses a cluster whose inventory lacks the `kubernetes` group, which would otherwise match no host and end without a word; `suspend.yml` and `resume.yml` run `roles/app_scale` on the controller, then the proxmox_vm role's `power` entry point on the Proxmox host for Home Assistant's VM; `status.yml` runs `roles/status` on the Proxmox host and, at the same time (`strategy: free`), for the cluster on the controller, then its `report` entry point on the controller. The inventory has three groups: `nas` (host `truenas`), `proxmox` (host `homeserver`) and `kubernetes` (host `homeserver-k8s`, local: the cluster is built from the workstation), and no addresses.

**The roles are generic; this setup is configuration.** Role defaults change nothing (empty lists and dicts, null for "leave alone"), and task files hold no configuration values, only variables, API namespaces and CLI verbs. Everything that describes these machines lives in tracked group_vars, apart from addresses and serials:

| File | Holds |
|---|---|
| `group_vars/all/local.yml` (git-ignored) | addresses, disk serials, the NAS's pool names when they are not `persistent` and `ephemeral`, the installer's storage when it is not `local-lvm` (`proxmox_local_vm_storage`: every VM's without a NAS, the cluster's system disks with one too), the cluster's Kubernetes section: node addresses and MACs, MetalLB's addresses, the repository Flux syncs, without a NAS the worker's size, for a test host's cluster its own credentials directory (`kubernetes_talos_config_dir`), and for remote access the switch (`tailscale_enabled`) and the LAN's prefix (`tailscale_advertise_routes`) |
| `group_vars/all/local.vault.yml` (git-ignored, encrypted) | the TrueNAS API key, the Tailscale auth key, and Home Assistant's owner password |

| `group_vars/proxmox/storage.yml` | the Proxmox storages and boot delay |
| `group_vars/all/haos.yml` | Home Assistant's switch (`haos_present`, worked out from `local.yml`'s `haos_mac`), VMID (310), size, owner, and `haos_settings_error`, which `proxmox.yml` and `homeassistant.yml` assert first |

A new setting goes in one of these files, with a neutral default in the role and a line in the role's `meta/argument_specs.yml` and `README.md`, never as a literal in a task; then `make fix TYPE=docs` brings the role's `REFERENCE.md` up to date.

**`roles/truenas`** runs on the controller (`ansible_connection: local`) and talks to the NAS's JSON-RPC 2.0 WebSocket API (`wss://<nas>/api/current`) with an API key, through custom modules in `roles/truenas/library/` and a shared client in `roles/truenas/module_utils/truenas_api.py`. The REST API is deprecated and gone in TrueNAS 26; SSH stays off on the NAS. Stages, each under its own tag: `truenas_network` (network settings, static address), `truenas_pools`, `truenas_system`, `truenas_datasets`, `truenas_snapshots` (periodic snapshot tasks, after the datasets they name), `truenas_nfs` (service settings, shares), `truenas_alerts` (outgoing mail and alert services), `truenas_services` (last, so NFS starts once its shares exist); validation and the read-only connection (`truenas_info`) run under every tag, and a stage whose variables are empty does nothing. Design facts that are easy to break:

- **Every change to the NAS goes through this role.** No UI clicks, ad-hoc API calls or SSH; a fresh install plus one run must rebuild it. Read-only API queries are fine.
- **TrueNAS rate-limits logins** to 20 per minute per client address, and every module run logs in once. Modules therefore take lists (all datasets, all services) rather than being looped over, and the client waits out the window if it is hit.
- **The static address uses TrueNAS's commit-and-check-in.** `truenas_interface` commits with a rollback timer, reconnects on the new address and checks in; if it cannot, the NAS reverts by itself. The play reaches the NAS on the static address first and falls back to `truenas_bootstrap_address`.
- **The system dataset is pinned before any pool import.** On a fresh install it reads as `boot-pool` but counts as unset, and importing a pool would move it onto that pool.
- **Pools are imported or created, never destroyed, wiped, exported or upgraded.** Creation needs `truenas_pool_allow_create` and blank disks (by serial), and is untested.
- **Modules return only the fields they manage.** `system.general.config` includes the UI certificate's private key; `tests/unit/test_truenas_client.py` checks that `truenas_config` never returns it, in check mode, applying, or failing.
- **The API key goes only to the NAS's own certificate.** Certificate validation is off (self-signed), so `truenas_api_cert_sha256` pins the certificate's SHA-256 (in `local.yml`); a server presenting anything else gets no login. Replacing the certificate means updating the pin.
- **An NFS share must name its hosts or networks.** NFS with `sec=sys` has no authentication.
- **A secret setting is compared, never printed.** `mail.config` returns the mail server's password, so `truenas_config` takes it in `secret_settings` (a `no_log` option): compared and sent like the other fields, so a rotated password reaches the NAS on the next run, and shown only as `<secret>` or `<secret, changed>`. The idempotence test rotates it and checks that neither password appears in any run's output.
- **Snapshots only where data cannot be re-created.** `persistent/proxmox/vm` keeps hourly snapshots for a day and daily for a week (it holds the worker's data disk, whose scratch data longer-lived snapshots would pin; the nightly VM backup keeps the history); with a cluster, `persistent/nextcloud` and `persistent/photoprism` keep hourly for 2 days, daily for 30, weekly for 12 weeks. The daily and weekly tasks allow empty snapshots: they fire with an hourly one, and TrueNAS destroys a batch of snapshots that are all empty unless one of its tasks allows them, so an idle dataset would otherwise keep no daily or weekly snapshot at all. Never a snapshot task on the ephemeral pool.

**`roles/proxmox_apt`** runs first in `proxmox.yml`, over the same root SSH. A fresh Proxmox install ships with the enterprise repositories enabled and no subscription, so `apt-get update` fails with 401 until they are off and the no-subscription one is on, which used to be a manual step in the web UI's Updates → Repositories panel. The role writes each entry of `proxmox_apt_sources` as a deb822 `<name>.sources` file (the Debian release read from the host's `/etc/os-release`, so a reinstall on a newer Proxmox gets its own release), prepends `Enabled: false` to each existing file named in `proxmox_apt_disabled` without rewriting the rest (as the UI does; the line goes first because a trailing blank line would make a line at the end a stanza of its own), and with `proxmox_apt_upgrade` refreshes the package lists and runs `apt-get dist-upgrade` non-interactively, keeping configuration files changed on the host. This setup turns the upgrade on, so every `make deploy TYPE=proxmox` upgrades the host: one command rather than two, and an upgrade with nothing to do is quick. A dry run writes nothing and fetches nothing: it shows the file diffs and simulates the upgrade on the lists as last refreshed, which on a fresh install means no pending upgrade until the first real run. Every run then says whether the host needs a reboot, and never reboots it: when to take the host and its VMs down is decided by hand. A reboot is needed while Debian's flag for one, `/run/reboot-required`, exists, which every boot empties. The role writes it when the upgrade changes a kernel image package (`proxmox-kernel-<release>`, signed or not; `proxmox-kernel-helper` and the meta package share the prefix and boot nothing) or a package in `proxmox_apt_reboot_packages`, here dbus, both vendors' CPU microcode, which the kernel loads only at boot, and `pve-firmware`, which drivers load as they start; dbus's own package writes it too, and the role honours it whoever wrote it. It sees only what its own upgrade unpacked: a kernel installed by hand or from the web UI, or a boot that came up on an older kernel, goes unreported. Every microcode or firmware upgrade asks for a reboot, even one that brings this hardware nothing: when in doubt, reboot. The record is made in a block's `always`, so an upgrade that fails after unpacking still leaves it, and a dry run says the same from the simulated upgrade. The commands go through `command`, not the `apt` module, so the test's fake `apt-get` can stand in for them; it answers 401 to a refresh while an enterprise repository is enabled, so the role's order (files first, then the refresh) is what the test proves, and it can fail after unpacking, which proves the record survives a failed upgrade.

**`roles/proxmox_storage`** runs over root SSH with `pvesm`, not `community.proxmox.proxmox_storage` (which only creates storage and has no `format` option). It adds the layout's NFS storages with qcow2 (`homeserver-persistent`, `homeserver-ephemeral`, and one per project pool, today `claude-on-proxmox-ephemeral`), corrects drift in content, format and mount options, refuses a storage id that points elsewhere, an export that another id already mounts (one export, one id: what a renamed id leaves behind until the old one is removed by hand) and an id Proxmox would reject, and sets the node's start-on-boot delay so VMs wait for the NAS, then, with `proxmox_storage_startall_wait`, a drop-in for `pve-guests.service` (under `proxmox_storage_systemd_dir`, followed by `systemctl daemon-reload`) that holds the start at boot until each listed storage is active in `pvesm status`, for at most `proxmox_storage_startall_wait_timeout` seconds: Proxmox starts each guest once, and one whose disk is on a storage that is not active fails and is never tried again. This setup waits up to ten minutes for the NAS's storages that hold VM disks; without a NAS the drop-in is removed. Given `proxmox_storage_local`, a list of ids of storage the node already has (any type passes; here it is the installer's own), it also checks that each exists, is not disabled and holds `images`, which fails a dry run too, and creates or changes none of them; the refusal names the variable and lists the storage Proxmox has. Its input check gives each problem its own message, and refuses a string for that list, which argument validation lets through unchanged. Whether a storage is active on the node, for these ids and the NFS storages alike, is checked only on a real run, at the end, and the failure names the storage and whether it is restricted to other nodes or not activated.

**`roles/proxmox_backup`** runs last in `proxmox.yml`, over the same root SSH, with `pvesh` under `/cluster/backup` (no `community.proxmox` module manages backup jobs). It creates each job of `proxmox_backup_jobs` and corrects the settings it manages (schedule, storage, VMIDs in any order, mode, compression, prune settings, notes template, enabled), and never deletes a job. **`roles/proxmox_vm`** runs in `kubernetes.yml`'s first play and in `homeassistant.yml`, on the Proxmox host over root SSH, with `qm` and `pvesh`; `homeassistant.yml` gives it Home Assistant's VM as play vars (`proxmox_vm_vms` and the rest), the same names `group_vars/proxmox/vms.yml` gives the cluster's. Besides ISOs it downloads images a disk is imported from (`proxmox_vm_imports`, `download-url --content import`, always with a `sha256` Proxmox checks before storing the file), creates such a disk with `<storage>:0,import-from=<volume>` (Proxmox reads a disk straight out of an OVA, `local:import/<x>.ova/<disk>`, extracting it first onto `qm create --import-working-storage`, a VM-level `import_working_storage` that must hold images and have a path; the installer's `local` holds no images, so without a NAS the owner enables them once and the role refuses until then), grows it to its size in the same run, and never imports again onto an existing VM; it passes USB devices (`usb`, by vendor:product or a mapping), which reach a running VM at once. Its tasks read the node; the `proxmox_vm_plan` filter (`roles/proxmox_vm/filter_plugins/proxmox_vm.py`, pure Python, unit-tested in `tests/unit/test_proxmox_vm_plan.py`) works out what to do, and the tasks run the commands it returns. It downloads the Talos ISO (the version and schematic in the file name; Proxmox checks it against `sha256`, the pin `kubernetes_iso_sha256`, which the role requires of every ISO, since the Image Factory publishes no checksum; the download task's own exit status is checked, since `pvesh` may exit 0 for a failed one), creates each missing VM with every option given, corrects the settings it manages (cores, memory, CPU, ballooning, start-on-boot, startup, watchdog, agent, tags, `hostpci*`, `ide2`, `boot`, which Proxmox edits when a drive is deleted), adds a configured disk a VM lacks, grows a disk configured larger, and starts a stopped VM. Proxmox writes settings back in its own forms (tags lower-cased and sorted, disks as volume ids with their size, property strings in any order, numbers as text or numbers), so each is compared normalised. It never moves, shrinks or detaches a disk, deletes a VM or an ISO, ejects the CD-ROM (a wiped node reaches maintenance mode only from it; the boot order puts the system disk first), or restarts a VM: settings that wait for a restart (on a running VM: cores, CPU, memory, ballooning, watchdog, agent, boot order, PCI devices) are reported from `.../pending` on every run until one. It refuses a VMID another VM or a container holds, **a missing VM whose VMID still has disks or backups on any storage** (files of no VMID, such as imports, aside; it is being rebuilt: restore it, `scripts/runbooks/vm-restore.md`, or set `proxmox_vm_ignore_existing_volumes`, with `make deploy TYPE=kubernetes ANSIBLE_ARGS='-e …'`, never make's own `-e`), a missing VM while an enabled storage is not active (its leftovers cannot be ruled out), a disk storage that does not exist or holds no images (pending in check mode when listed in `proxmox_vm_pending_storages`), and **the disk budget**: on thin LVM, ZFS, a directory or BTRFS, the provisioned sizes of every disk, other VMs' and containers' included (a container's volumes are listed as `rootdir`, not `images`, so the role lists every content type), plus what the run adds, never exceed the pool's `total` (never compared with what is free, which shrinks as data is written; `proxmox_vm_allow_overcommit` lifts it). A ZFS storage's `total` is its dataset's use plus the pool's free space, which the host's root filesystem shares on a ZFS install, and a directory's or BTRFS storage's is its filesystem's, so either shrinks as the host's own files grow: `proxmox_vm_host_headroom_gib` (16 here) keeps that much out of the budget. A disk already there whose serial or `backup` flag differs is set again on the same volume, and a slot is never filled while the VM keeps an `unusedN` volume (what a restore leaves of a disk its backup excluded): the role refuses and says how to attach or remove it. A storage in `proxmox_vm_pending_storages` that is missing is reported with `proxmox_vm_pending_storages_hint`, here "make deploy TYPE=proxmox adds it: run that first". NFS is not budgeted; the NAS's quota on `persistent/proxmox/vm` caps it. It warns when the VMs' memory would exceed the node's less 2 GiB, and reports each VM's MAC for checking against DHCP. `group_vars/proxmox/vms.yml` maps `kubernetes_nodes` onto VMs 300 and 301, the same two in both setups: the system disks (`serial=talos-system`) on the installer's storage, the worker's data disk (`talos-data`) on `homeserver-persistent` in qcow2 with a NAS and on the installer's storage without, its media disk (`talos-media`, `backup=0`) without a NAS, `i6300esb` watchdog, `virtio-scsi-pci`, the MAC from `kubernetes_node_macs`, and the tags `talos` and `k8s`. A built cluster moved to the other setup is refused before anything changes because the worker's data disk is on the other storage, which is why the worker always needs a data disk: `test_a_built_cluster_cannot_switch_setups` keeps that so. The backup covers both VMs in either setup, and README's "Switching setups" gives the migration by hand (`qm disk move`). `kubernetes.yml`'s first play also refuses a cluster when the inventory lacks the `kubernetes` group, which an inventory made before it does. The fake's `qm` and VM routes come from Proxmox's API documentation, not yet from a capture on the test host; its tests are marked `cluster`.

**`roles/talos`** runs in `kubernetes.yml`'s second play, on `homeserver-k8s` (`ansible_connection: local`, `group_vars/kubernetes/`), with `talosctl` and `kubectl` from `PATH`. Its parsing of their output is a filter plugin (`roles/talos/filter_plugins/talos.py`, unit-tested in `tests/unit/test_talos_filters.py`). It refuses a workstation `talosctl` whose minor release is not `talos_contract` (talosctl's defaults follow its own release), asks the Image Factory for each schematic's id (content-addressed, so safe in check mode; it answers 201) and refuses one other than `talos_schematic_pins`', gives every installer image the digest `talos_installer_digests` pins for its schematic and version (refusing a schematic in use at `talos_version` without one), and works in a scratch directory (secrets, a talosconfig for the run, rendered configurations; the patches reach talosctl inline) made with `check_mode: false` and `changed_when: false` and removed in a block's `always`. Once the bootstrap record exists, it refuses to install a node in maintenance mode that `talos_reinstall` does not name (or `talos_allow_bootstrap`, a new cluster on purpose), in a dry run too: the configuration holds the cluster's keys, and `--insecure` proves nothing about what answers at the address. It installs a node in maintenance mode with `apply-config --insecure` and then waits on its install status (`get unattendedinstallstatuses` with the talosconfig) until it reads `installed`: on Talos 1.14 the node answers with the talosconfig at once and installs in the background from the ISO (pending until a disk matches the selector, installing, waiting-for-reboot), and the installer image that `gen config` writes into its UnattendedInstallConfig makes it reboot, so `installed` means it runs from its system disk; a lasting `pending` (a disk selector that matches nothing) or `failed` fails the run with Talos's error, before bootstrap, which Talos refuses until then. Drift on a configured node is found with `apply-config --dry-run` (`No changes.`), never printed since the diff can hold secrets, and applied with `--mode no-reboot`, **never rebooted**: Talos 1.14 applies any configuration at once in that mode (`auto` means the same now; ApplyConfiguration never refuses for a reboot), so nothing is staged, an apply that fails stops the run with Talos's error lines (the output itself stays `no_log`), and after a change to the control plane the run says to restart etcd (`talosctl service etcd restart`), which reads its settings only when it starts. `talos_keep_rendered` keeps the rendered files in `talos_config_dir/rendered/` to see a diff by hand. After health it checks that every user volume the patches declare is `ready` (`get volumestatus`): one whose selector matches nothing is never mounted, and local-path would write to the system disk. **It bootstraps etcd once**: the marker `talos_config_dir/bootstrapped` records it; with the marker and etcd not `Running` (`talosctl service etcd`) it refuses and names `--recover-from`, `vm-restore.md` and `-e talos_allow_bootstrap=true`, since a second bootstrap makes a new, empty cluster over which Flux would recreate every volume empty. talosconfig (with the control plane as endpoint and node) and kubeconfig go to `talos_config_dir` (`~/.talos/homeserver`, or `local.yml`'s `kubernetes_talos_config_dir` for a second cluster such as a test host's: a `talos_config_dir` in `local.yml` would lose to `group_vars/kubernetes/`; refused inside the repository), mode 0600, and are renewed 30 days before their client certificates expire (`openssl x509 -checkend`). **Every entry point first refuses another cluster's credentials there**: a talosconfig whose endpoint is not the control plane or whose CA is not the secrets bundle's, a kubeconfig whose server is not `talos_endpoint` or whose CA is not the bundle's, so a test run never reads, replaces or hands Flux the home cluster's. The secrets bundle is `talos_secrets_file`, `talos_config_dir/secrets.yaml` (`talosctl gen secrets`, kept in the owner's password manager, never in a repository): every entry point refuses it missing, readable by others than its owner (mode 0600 or 0400) or inside the repository, reads it with `slurp` under `no_log`, checks it by its text alone (a YAML parser's error could quote a line of it) and only ever writes it with `no_log`. `group_vars/kubernetes/talos.yml` holds the patches: the install disk and user volumes selected by the by-id link QEMU names after the disk's slot, `scsi-0QEMU_QEMU_HARDDISK_drive-scsiN` (`kubernetes_disk_slots` in `group_vars/all/kubernetes.yml`, which the VMs' layout reads too: Proxmox sets `device_id=drive-scsiN`, which udev prefers to the `serial=`, and `disk.serial` is empty on virtio-scsi, both seen on the home host), a 2-minute `WatchdogTimerConfig`, the control plane's metrics bound to `0.0.0.0` (set now, since etcd's needs a reboot), Flannel's network policy agent on (`talos_patch_network_policies`), and nothing that lets the control plane run apps: it keeps Talos's taint in both setups. With `kubernetes_gpu_mapping` the worker boots the `gpu` schematic and carries the GPU plugin's label (### GPU). `make lint TYPE=talos` renders every setup through the role's own `render.yml` (`tests/talos_validate.yml`) and runs `talosctl validate --mode metal --strict` on each, then checks that each one's UnattendedInstallConfig names its installer image and leaves reboot on, which the install wait counts on; CI's kubernetes job downloads talosctl by version and checksum. The fake (`tests/integration/fake_talos.py` behind `fake_talos_bin/`) is written from talosctl v1.14.2's flags and the docs; it renders a configuration as text carrying the secrets bundle's cluster secret, which the tests prove never reaches the output, and makes real client certificates with openssl. The tests run with `HOME` set to their own directory.

**`roles/status`** runs in `status.yml` (`make status`), which make runs as a dry run with the repo's stdout callback (`callback_plugins/homeserver_status.py`: one line on what was read and how long the probes took, then the report, failures on stderr, nothing on stdout with `JSON=1`) and no log. Its main entry point reads the host the play runs on (`status_source`: `proxmox` on the Proxmox host, `cluster` on `homeserver-k8s`, empty without a cluster) and leaves its findings in the fact `status_found`; the `report` entry point, on localhost, puts every host's together, asks each app's addresses from this machine (module `status_probe`), ranks what needs attention (sources not read, problems, things to do, each with the command from `status_commands`, `group_vars/all/status.yml`, so the role names no make target itself), writes the report to `.cache/status/report.json` (mode 0600, written in the dry run too, `check_mode: false`) and shows it. **The exit code comes from that file, not from Ansible**, since `ansible-playbook` sets its own from task results and no callback can change it: the recipe exits with the report's (2 when a source could not be read, else 1 for a problem, else 0), or 3 when the run itself failed or wrote no report. **GNU make then exits 2 for any failed recipe**, whatever its code, so `make status` exits 0 or 2; the report's own code ends its last line, is `JSON=1`'s `exit`, and is the "Error N" make prints. `TYPE` is checked by make (`status_TYPES`) and again by the role. The read play has no `any_errors_fatal`: Ansible takes a host that does not answer, which every read ignores (`ignore_unreachable`), for an error under it and ends the whole run there (seen in the tests). A refused host leaves no `status_found` instead (a host with nothing to read leaves an empty one), and the report play then ends without a report, so there is never half a report. **Every command goes through the role's module `status_read`**, which runs a list at once (8 at a time, 30 s each; 15 s for the cluster) and refuses the whole task if any is not one of its exact forms (`READS` in `roles/status/library/status_read.py`: named `pvesh get` paths, `qm guest cmd` with `get-fsinfo`, `get-osinfo` or `network-get-interfaces`, `apt-get -q -s dist-upgrade`, `hostname -s`, `test -e`; `kubectl get` of nodes, pods, services, ingresses, persistentvolumes, kustomizations, helmreleases, fluxinstances, certificates and deployments (with `--show-managed-fields`), one ConfigMap, `--raw` of a node's kubelet statistics alone, `exec` of `amtool alert query` in Alertmanager's container alone; `talosctl service etcd`; `git ls-remote` over HTTPS or SSH, never `ext::`), so nothing writes or returns a secret: never `kubectl get secrets`, never `talosctl get` (the machine configuration holds every key of the cluster); `test_status_reads_only_through_status_read` keeps every other task to a short list of modules. Measured on a four-core Proxmox host (2026-10-21): every `pvesh` or `qm` call takes 1.1 to 1.3 s, Proxmox's Perl API started afresh, so the 15 reads take 25 s one after another and 8 s at once, and `apt-get -s` 0.7 s where the API's own update list takes 4.5 s; the cluster's reads take about 0.1 s each and `git ls-remote` about 1 s, so the cluster is read in about a second. A host that does not answer is ignored (`ignore_unreachable`), recorded with Ansible's message and reported, never a failure. On the Proxmox host it reads `/cluster/resources` (the node, every VM, every storage in one call), the node's status and day history, and for each of `status_vms` (`group_vars/all/status.yml`: this repo's VMs, the same as `vm_backup_vmids`, which a policy test checks) its history, pending settings and, for Home Assistant, its guest agent's filesystems, OS and address (past its Docker bridges); Talos's guest agent lists no filesystem and no OS version (seen on the NUC). Every other VM on the host, another project's, is counted in one line and never named as a problem. A VM's memory is Proxmox's view, the host's (PVE 9 shows the host's PSS when ballooning is off, as on every VM here), and the text marks it; **a cluster node's memory and disks are the guest's own, from kubelet's statistics** (`kubectl get --raw /api/v1/nodes/<node>/proxy/stats/summary`: working set plus available, `/var`, and each Talos user volume a claim lies on, which reports its whole filesystem; `status_cluster_volumes` names them by mount). The installer's storage is shown against `proxmox_vm`'s disk budget (provisioned against its size less the headroom on ZFS, directory and BTRFS), an over-budget one as a thing to do. **The cluster** is read with `talos_config_dir`'s credentials, under `no_log` (only the kubeconfig's server and each client certificate's expiry are kept, by the filter `status_credentials`); a kubeconfig naming another server than `talos_endpoint`, such as the home cluster's on a test host, is reported as unread and never used, and a cluster whose VMs are stopped is a note, not an unread source. **An app is each Ingress's backend Service's Deployment** (so the chart's Grafana too), and every other Deployment a Flux Kustomization under `k8s/apps` applies; a database (`app.kubernetes.io/component: database`) is listed under its app; states: running, starting, waiting (a Secret that does not exist yet), failing (crash loop, image pull, unschedulable, pending over ten minutes, past its progress deadline), suspended (`make suspend`'s annotation, the time from the managed fields), stopped (scaled to zero by hand), not applied (its Kustomization failed); an app a host leaves out (#86's `kubernetes_apps`) is not listed yet. **The probes**: a DNS lookup per app's name, compared with the address the Ingress says Traefik answers on, and one `GET` per URL sent to that address whatever DNS says, closed after the headers, no certificate checked (the CA exists in the cluster only in Secrets with private keys), the served certificate's issuer and expiry read with `cryptography` and matched with the Certificate objects; an `http` URL is listed only when it answers by itself rather than redirecting (Jellyfin's); missing DNS comes with `/etc/hosts` lines. Parsing, report and text are pure filters (`roles/status/filter_plugins/status.py`, `tests/unit/test_status_filters.py`, with the cluster's shapes captured from the NUC); `tests/unit/test_status_read.py` covers the read list and the parallel runs, `tests/unit/test_status_probe.py` the probe against servers in the test's process; `tests/integration/test_status.py` runs the real `status.yml`, callback and `make status` in a scratch tree against the fake Proxmox host and the fake cluster (`fake_kubectl.py` lists the new kinds, makes pods up from the Deployments and answers kubelet's statistics and amtool, `fake_talos.py` answers `git ls-remote`), with HOME and the credentials the test's own, and checks the exit codes, `JSON=1`, another cluster's kubeconfig, a stopped cluster, a host that refuses the connection, probes that get no answer, and that neither fake's state changes.

**`roles/proxmox_tailscale`** runs second in `proxmox.yml`, over the same root SSH, and only when `local.yml` sets `tailscale_enabled` or gives `tailscale_advertise_routes` (with neither, it runs no command; `tailscale_enabled: false` with routes is refused). With `tailscale_enabled` alone it joins the Proxmox host to the tailnet as a device of its own, reachable at its tailnet address: the guard is loaded all the same, forwarding is left as it is, and nothing from the tailnet is forwarded (tailscaled delivers no packet for an address the host neither holds nor advertises, and the guard drops all but the guarded hosts' allowed ports). With routes it makes the host the LAN's Tailscale subnet router, so every VM on its bridge, the NAS and the router answer from the tailnet without Tailscale of their own. It comes after `proxmox_apt` (a fresh host installs nothing until the enterprise repositories are off) and before `proxmox_storage` (whose refusals must not hold remote access back).
- **Install and upgrade.** It downloads Tailscale's signing key once, writes `tailscale.sources` (deb822), and installs `tailscale`, `tailscale-archive-keyring` (which owns the key from then on) and `nftables` with `apt-get install`, and leaves upgrades to `proxmox_apt`'s `dist-upgrade`, earlier in the same run (`proxmox_tailscale_upgrade` is off, so one switch covers every upgrade). Tailscale's own updater is off (`auto-update: false`): on Debian it runs apt on its own schedule and needs a `tailscale.list`.
- **The guard, then forwarding.** It loads a guard (below), then writes `/etc/sysctl.d/99-tailscale.conf` (`net.ipv4.ip_forward = 1` only; IPv6 forwarding would stop `vmbr0` accepting router advertisements, and IPv6 routes are refused). Forwarding is host-wide: a second interface with an address (a VLAN, a storage network) would be routed to and from the LAN too, which the guard does not filter.
- **Login.** tailscaled is enabled and started if it is down (stopped by hand, or never started at boot because the guard failed), after the guard. Before any login, a tailscaled without `tailscale0` (started with `--tun` naming another interface, or with userspace networking) is refused, since the guard filters by that name. A logged-out node is logged in once with `tailscale up --auth-key=file:<tempfile>` (`no_log`, removed in an `always`), tagged `tag:homeserver`, with every preference `up` takes, so the node never runs with Tailscale's defaults. A node stopped by hand is brought back up without a key.
- **Preferences.** It compares the routes and `proxmox_tailscale_settings` with `tailscale get --json`, which is keyed by `tailscale set`'s own flag names (accept-routes, accept-dns, ssh and auto-update all off here), and runs one `tailscale set` when they differ.
- **Never.** It never logs out, retags or restarts tailscaled, and reports instead what only the admin console can fix: an unapproved route, the wrong tags, a key that expires, a Serve configuration, Tailscale's health warnings.

**The guard** is the nftables table `inet tailnet_guard` (`/etc/nftables.d/tailnet-guard.nft`), loaded by `tailnet-guard.service` before `network-pre.target`.
- **What it drops.** Its forward chain (priority `filter - 10`; a drop in any nftables base chain is final, whatever iptables, Tailscale or Proxmox accept) drops three things: everything from `tailscale0` to `proxmox_tailscale_guard_hosts` except `proxmox_tailscale_guard_allow` (here both NAS addresses, since NFS answers on every address the NAS has, and with only the bootstrap address the shares are exported while `proxmox_storage` refuses to mount them), everything else from `tailscale0` outside the advertised prefixes (all of it without routes), and new connections from the LAN into the tailnet. In that order, so the guarded hosts' allowed ports pass even outside the prefixes; tailscaled never delivers those without a route.
- **Fail-closed.** A drop-in (`tailscaled.service.d/10-tailnet-guard.conf`) makes tailscaled `Requires=` and `After=` the guard. That covers starting: a table removed by hand while both run leaves tailscaled unguarded until the next `make deploy TYPE=proxmox`.
- **Reloads only.** The role checks each file with `nft -c` before installing it and applies changes with `systemctl reload-or-restart`: a reload when the unit is active. A plain restart would restart tailscaled through `Requires=`, and the fake refuses one. The unit has no `ExecStop`, so stopping it never removes the table.
- **Debian's nftables.service.** The role refuses to run while it is enabled or running: its `/etc/nftables.conf` begins with `flush ruleset`, and its stop command flushes too. The guard's unit has `Conflicts=` and an ordering on it, so starting it later stops the guard, and tailscaled through `Requires=`, before the flush.

The tailnet's policy, split DNS and the auth key are set by hand in Tailscale's admin console (`scripts/runbooks/tailscale.md`), the policy before the first advertisement, since a new tailnet allows everything. The role's tests have fakes of their own (`tests/integration/fake_tailscale.py` behind `fake_tailscale_bin/`, a test playbook `proxmox_tailscale.yml` and `test_tailscale.py`), written from Tailscale 1.104's flags and `get --json` as a 1.102 client prints it, not yet captured from the host.

**Without a NAS.** `nas_present` (`group_vars/all/storage.yml`) is true when `local.yml` gives the NAS either address, `truenas_static_address` or `truenas_bootstrap_address`. The addresses are the only switch: `nas_present` is never set, and the guard below refuses one given with `-e`, which would be a string that counts as true even when it says `false`. The `truenas` host stays in the inventory, and `truenas.yml` carries two `always`-tagged pre-tasks that, when it is false, say why and `end_host` before the role runs (the `always` tag is required, since `meta` tasks honour tags, and the `debug` is what gives the host a recap line). A misspelt address would look exactly like no NAS, so both `truenas.yml` and `proxmox.yml` first assert that `nas_section_error` (`storage.yml`) is empty: it names the TrueNAS settings `local.yml` still sets (certificate pin, gateway, name servers, pool disks, pool names, the alert mail's settings) when neither address is given, and with a NAS it refuses alert mail TrueNAS would refuse (a mail server without a sender address, an alert address without a mail server) and `vm_backup_storage`, which only a setup without a NAS reads, while a section deleted or left entirely blank stays Proxmox-only. `group_vars/proxmox/storage.yml` then derives an empty NFS list, `proxmox_storage_local` set to the installer's storage (with a NAS too when there is a cluster, whose system disks go there), a null boot delay and no wait at boot; `vm_storage` holds the ephemeral class alone, on the installer's storage, `local-lvm` unless `local.yml` sets `proxmox_local_vm_storage` (`local-zfs` on a ZFS install). There is no persistent class without a NAS, and no project pools. `storage.yml` only reads that variable: a `group_vars/all/` directory is read alphabetically and the last file wins, so a value set in `storage.yml` would override `local.yml`'s. The vault is still decrypted on every run, so it and `.vault_pass` must exist, as in every setup: `make vault TYPE=new` makes what is missing, `.vault_pass` with mode 0600 and an empty mapping encrypted with it (`ansible-vault encrypt` from stdin, so nothing is written unless encryption works). A vault that already opens with `.vault_pass` is left alone, one that does not open is refused, since it may be the user's with its password lost, and so is a checkout that still has `group_vars/all/vault.yml`, whose vault is moved rather than replaced. The vault exists nowhere else, so README and REBUILD tell the user to keep it in a password manager; a cluster's secrets bundle is never in it (`roles/talos` above). `tests/policy/test_roles.py` runs the argument-spec pass in both modes and `tests/integration` runs the Proxmox role without a NAS; the mode was also run against a fresh Proxmox VE 9.2.2 install, which is where the fake's `digest`, `shared` and varying `content` order come from. Storage ids say who owns a storage and what it is for, never the backend; they were `truenas-*` until 2026-10-08. The role never removes a storage and refuses an export that another id already mounts, so renaming an id means removing the old one by hand first (`pvesm remove`), which the home host still needs for its two old ids: until then every run, dry or real, refuses and names them.

**The cluster switch.** `kubernetes_present` (`group_vars/all/kubernetes.yml`) is true when `local.yml` gives `kubernetes_node_addresses`; like `nas_present` it is worked out, never set. In both setups the cluster is a control plane, which runs Talos, etcd and the API alone, and a worker that runs every app; only where the worker's disks live depends on the NAS, and without one `local.yml` must give the worker's size (`kubernetes_node_sizes`), since the defaults fit the home host. Until 2026-10-19 a setup without a NAS had a single schedulable control plane instead; one shape keeps the two setups from drifting apart. Every playbook first asserts that `kubernetes_settings_error` is empty, right after `nas_section_error`, because the Proxmox play reads the switch too: it refuses `kubernetes_present` given with `-e`, the section's other settings without node addresses (a misspelt address), node addresses other than the two nodes', a node without a locally administered lower-case MAC (`kubernetes_node_macs`, chosen by the owner and reserved in DHCP before the first run; the example's `<mac>` is refused on purpose), no `flux_sync_url` (it has no default: Flux applies that repository with cluster-admin rights), with a NAS no `truenas_static_address` (the bootstrap address alone is a DHCP lease the NAS play replaces, and the cluster's volumes and the apps' NetworkPolicies need `nas_address`), a `flux_sync_ref` other than `refs/heads/main` without `flux_sync_ref_unprotected: true` (whoever can push to the synced branch owns the cluster, and only `main` is protected; `scripts/runbooks/talos.md`), MetalLB's addresses missing, not IPv4 or outside their range (and a node address inside it), a `kubernetes_ingress_allowed_range` that is not one IPv4 CIDR, `vault_talos_secrets` in the vault in any setup, a worker without a data disk (or a data or media disk under 11 GiB: Talos's volume takes 10 GiB, and the partition table a little more), a `proxmox_address` that is not an IPv4 address (the apps' NetworkPolicies deny it as a /32, in both setups), a worker system disk under 32 GiB (every app's image and Jellyfin's transcoding scratch), a control plane with a data or media disk or under 2 GiB of memory, a node without cores or memory, a system disk under 10 GiB, with a NAS a worker data disk above three quarters of `vm_storage_persistent_quota_gib`, a worker media disk or `kubernetes_media_on_data_volume` (the media live on the NAS), and without a NAS a worker without every size, or without a media disk unless `kubernetes_media_on_data_volume` is set, or with both. `kubernetes_iso_storage` lives in `group_vars/all/kubernetes.yml`, not with the VMs, so `local.yml` can name `local-btrfs` on a BTRFS install. A host sees only its own groups' files, so whatever two plays read lives in `group_vars/all/`. With a NAS and a cluster, the NAS play creates `persistent/nextcloud`, `persistent/photoprism` and `ephemeral/frigate` (1M records, the last with a quota and no snapshots), and exports those and the existing media dataset `ephemeral/jellyfin` (its properties and NFSv4 ACLs left alone; created, through `truenas_dataset`'s `create_only`, only when missing, as after the ephemeral pool's disk is lost, since its share cannot be made without it) to the worker alone, with root mapped to root: each app's pod makes its own mount point uid 1000. gitleaks flags a MAC written out in any tracked file, so the tests build theirs at run time. `tests/policy/test_roles.py` runs the argument-spec pass in the four setups the two switches make, and checks each refusal's message.

Storage design: the NAS's two pools are named by class, never by hardware (`nas_pools` in `group_vars/all/storage.yml`; `local.yml` can name them otherwise with `truenas_pool_persistent` and `truenas_pool_ephemeral`): `persistent` is redundant, for data that cannot be re-created, and `ephemeral` has no redundancy, for data that can. Persistent VMs on `persistent/proxmox/vm` (RAIDZ1, `sync=standard`, a quota of `vm_storage_persistent_quota_gib`, 1 TiB, which counts its snapshots, so a disk that fills never fills the pool under the backups), ephemeral VMs on `ephemeral/proxmox/vm` (single disk, `sync=disabled`, 1 TiB quota on `ephemeral/proxmox` because the pool also holds the media dataset, and never a snapshot task). `vm_storage_ephemeral_reservation` puts a ZFS `reservation` on `ephemeral/proxmox`, which counts its descendants, so the media apps can never fill the pool under the VMs; a `refreservation` would not, since it excludes descendants. Both use 64K records and POSIX ACLs. A project that creates VMs on the host gets a pool of its own: an entry in `vm_storage_consumers` makes a dataset under `ephemeral/proxmox` with the ephemeral class's properties and an optional quota, exported and mounted under the project's id. The project is told that id and nothing else, and its token is granted `/storage/<id>` by hand with its own README's line; this repo manages no Proxmox users or ACLs, and never grants `Datastore.Allocate`, which Proxmox checks on `/storage` for creating, changing and removing any storage alike. Proxmox has no host-wide default storage, so a project always names its storage; its default, `local-lvm`, is right without a NAS. These two projects stay independent: nothing here reads the other's configuration, and nothing there reads this repo's.

### Workloads (`k8s/`)

**Flux applies `k8s/clusters/<setup>/`** (`nas` with a NAS, `local` without), which holds only Flux Kustomizations, each applying one path: `infra-controllers` (`k8s/infrastructure/controllers/<setup>/`: MetalLB, Traefik, cert-manager and local-path-provisioner from `common/`, plus csi-driver-nfs with a NAS), then, depending on it, `infra-configs` (`k8s/infrastructure/configs/`: what needs the controllers' CRDs or namespaces: MetalLB's address pool, Traefik's allowlist and HSTS), `infra-tls` (`k8s/infrastructure/tls/`: the cluster's CA, its issuer, the wildcard and Traefik's default certificate, on its own because nothing waits for it: a cluster that cannot decrypt the CA, such as a test host's with an age key of its own, runs everything else on Traefik's own certificate) and `infra-storage` (`k8s/infrastructure/storage/<setup>/`: the static volumes, the same names in both setups). **Every Flux Kustomization has `decryption` (`sops-age`) and `postBuild.substituteFrom` (`cluster-settings`)**, harmless where unused, so a SOPS Secret or a `${VAR}` added later never stalls one. **Each controller's Namespace, with its Pod Security label and a comment, lives in that controller's own directory**, in the same Flux Kustomization: in `configs/` it would deadlock the platform (a privileged pod rejected in an unlabelled namespace, `infra-controllers` never ready, nothing after it applied). **Substitution rules**: Flux replaces `${VAR}` in every built manifest and, with strict substitution on (the FluxInstance's patch), fails the build on one that is not a setting; shell scripts and app configs use `$var` or `$${var}` (a literal `${var}`), a ConfigMap holding a foreign template wholesale carries `kustomize.toolkit.fluxcd.io/substitute: disabled`, and an optional value uses `${VAR:=default}`. A configMapGenerator's source files take a non-YAML extension (`.tmpl`), so neither kubeconform nor `test_k8s.py` reads them as objects. local-path-provisioner is vendored whole (`controllers/common/local-path/local-path-storage.yaml`, v0.0.37) with one edit, its Namespace's labels; everything else is a kustomize patch (the StorageClass renamed `local`, default, `Retain`, `defaultVolumeType: local`; requests; the node path `/var/mnt/local-path-provisioner`; the helper image pinned by digest). Its README says how to re-vendor it, by hand, the whole file. MetalLB runs layer 2 only (`frrk8s.enabled: false`, which 0.16.1 defaults to true); Traefik (chart 41.7.1 from its OCI registry) is the default IngressClass on `LB_TRAEFIK_IP` with `allocateLoadBalancerNodePorts: false`, a finite read timeout on each entrypoint (10 minutes on `web`, for what Jellyfin's apps send, an hour on `websecure`, for uploads), and the CRD provider's legacy names set explicitly (`--providers.kubernetescrd.safeNaming=false`), since the entrypoints name their Middlewares `<namespace>-<name>@kubernetescrd` and collision-safe naming would spell them `<namespace>_<name>`, every entrypoint deleting header names that alias another (`aliasHeadersStrategy: delete`: `X_Forwarded_For` reaches a PHP or Python backend as `X-Forwarded-For`), and `web` and `websecure` refusing an encoded NUL in a path while allowing the other encoded characters, which Nextcloud's file names hold; a start can log that the allowlist does not exist for `web-to-443@internal`, a known race (traefik#9779) during which that router stays closed; csi-driver-nfs creates no StorageClass and has `feature.enableFSGroupPolicy: false`, so kubelet never chowns a whole NFS volume, and takes no volume snapshots (the NAS snapshots the datasets worth it): `externalSnapshotter.enabled` off leaves out the snapshot controller and its CRDs, and `controller.enableSnapshotter` off the controller pod's snapshot sidecar, which the chart runs either way and which, without the CRDs, logs a failure every few seconds. **Every chart is pulled by something its publisher cannot move**: Traefik's, cert-manager's, kube-prometheus-stack's and MetalLB's (its OCI artifact, the same release its Helm repository serves) by the digest beside their tag in their `OCIRepository`, and csi-driver-nfs's from upstream's Git repository at the commit tagged for its release (a `GitRepository` on the release branch, its chart path in the HelmRelease), since its Helm repository's index points versions at files on branches. `test_k8s.py` refuses an unpinned source or any `HelmRepository`, and `make lint TYPE=charts` renders each pin, refusing a tag that names another digest; a bump moves tag and digest, or commit and path, together. Every chart's components carry requests, which `make lint TYPE=charts` enforces on the rendered output with `.kube-linter-charts.yaml`. `tests/policy/test_k8s.py` follows each Flux Kustomization's path through the kustomization files to check: every Kustomization decrypts and substitutes; every `${VAR}` without a default is a key of each setup's settings (resolved through the inventory, as the role does); every namespace is declared once and every namespaced object names a declared one (or `kube-system`, `flux-system`: `UNDECLARED_NAMESPACES`; `SYSTEM_NAMESPACES` stays `kube-system`, what Pod Security exempts); a controller's namespace comes with it; no PodDisruptionBudget; and, after `make lint TYPE=charts`, the charts' host paths (`CHART_HOST_PATHS`) and privileged pods.

**The apps live in `k8s/apps/<group>/`, one Flux Kustomization each** (`apps-media`, `apps-nextcloud`, `apps-photoprism`, `apps-frigate`, `apps-homepage` in `k8s/clusters/<setup>/apps.yaml`), each depending on `infra-configs` and `infra-storage`, with `prune` and `wait`; both setups list the same apps. A group is one namespace, declared in its own `namespace.yaml`: `media` holds sonarr, radarr, prowlarr, sabnzbd, seerr (Jellyseerr's successor), jellyfin and FileBrowser Quantum (FileBrowser's archived v2.63.18 is never deployed), sharing one claim `media` on the library mounted once at `/data`, so a download moves into the library as a rename; `nextcloud` and `photoprism` each hold the app and its MariaDB as two Deployments (`nextcloud-db`, `photoprism-db`), `frigate` and `homepage` one app. Home Assistant is a VM of its own (Home Assistant OS), not a manifest. **Every app** runs one replica replaced whole (`Recreate`), Homepage aside (two, rolling one at a time, spread with a preferred anti-affinity); has liveness and readiness probes, and a startup probe where it migrates before it listens (Nextcloud's `occ upgrade`, both MariaDBs' first initialisation, PhotoPrism: ten minutes; the *arr apps and seerr: five), since a liveness probe that killed a migration half way would leave it broken; mounts no service account token (no app reads the API; Homepage's Kubernetes mode is off); gives every container `allowPrivilegeEscalation: false` under the `RuntimeDefault` seccomp profile, LinuxServer.io images keeping the default capabilities their s6 init needs but NET_RAW (raw sockets, which would let a pod forge its neighbours' packets; Frigate, PhotoPrism and both MariaDBs drop it too) and running as root until s6 drops to `PUID`/`PGID` 1000, PhotoPrism likewise (its image starts through s6-overlay too, which exits at once as a non-root user, so it starts as root and its entrypoint drops to `PHOTOPRISM_UID`/`PHOTOPRISM_GID` 1000 with setpriv, with `PHOTOPRISM_DISABLE_CHOWN` sparing the storage volume a recursive chown at every start), seerr, FileBrowser and Homepage running as 1000 with every capability dropped; reads `TZ` and its host (`<app>.${DOMAIN}`, Homepage at the apex) from the cluster's settings; is a `ClusterIP` Service behind a Traefik Ingress, Frigate's camera streams aside (`frigate-rtsp`, a LoadBalancer on `LB_FRIGATE_IP` with `allocateLoadBalancerNodePorts: false`); and labels everything `app.kubernetes.io/name`. Images are pinned: LinuxServer.io's `x.y.z-lsNNN`, the official MariaDB and FileBrowser Quantum by digest.

### Storage model

**Each app's own data is a claim on `local`**, the default StorageClass (local-path-provisioner), on the worker's data volume: a Talos user volume on the VM's data disk, which is on the NAS's persistent storage with a NAS and on the installer's storage without one, and which the nightly VM backup covers. Volumes are `Retain` and every data-holding claim, volume and namespace carries `kustomize.toolkit.fluxcd.io/prune: disabled`, so data outlives its manifest. **What several apps share, or what lives on the NAS, is a static volume** of the same name in both setups (`k8s/infrastructure/storage/<setup>/`), bound by `volumeName`/`claimRef`: `media` (the library), `nextcloud-data`, `photoprism-media` (PhotoPrism's originals and imports, one mount so an import is a rename) and `frigate-media` (recordings). With a NAS they are csi-driver-nfs volumes on the datasets `roles/truenas` exports to the worker alone (`ephemeral/jellyfin`, `persistent/nextcloud`, `persistent/photoprism`, `ephemeral/frigate`; NFS 4.2); without one, `local` volumes pinned to the worker (`DATA_NODE`): the library and the recordings on its media disk (never backed up) or, with `kubernetes_media_on_data_volume`, on its data volume, the rest on the data volume. A `local` volume makes no directory, so a Job in `local-path-storage` (`static-volume-directories`, the repository's one hostPath, `/var/mnt`) makes each, owned by 1000; it has no TTL (Flux would recreate it), so it runs once and a volume made anew needs it deleted by hand (`vm-restore.md`), and `kustomize.toolkit.fluxcd.io/force: enabled` (its pod template is immutable). **Ownership on the NAS**: the role sets no owner, the shares map root to root, and every pod that mounts `media`, `nextcloud-data` or `photoprism-media` runs an init container `chown-mount` (busybox by digest, as root with `CHOWN` alone) that makes the mount point, never anything below it, uid 1000. No pod sets `fsGroup` on an NFS volume (kubelet would chown the whole library at every start), and csi-driver-nfs has its fsGroup policy off. Jellyfin transcodes to an `emptyDir` on the worker's system disk, never the backed-up data disk.

### Networking

MetalLB (layer 2) hands out `LB_RANGE`; Traefik is the default IngressClass on `LB_TRAEFIK_IP`, HTTPS with the cluster's own CA (the Landmines' TLS entry; HTTP redirects, Jellyfin aside), and every app is `https://<app>.${DOMAIN}` (`homeserver.internal` unless `local.yml` sets `kubernetes_domain`). **A new cluster serves nothing to the LAN**: every router on Traefik's `web` and `websecure` entrypoints passes the Middleware `traefik/lan-allowlist` (`k8s/infrastructure/configs/traefik.yaml`, an `ipAllowList` of `INGRESS_ALLOWED_RANGE`), which is the loopback address, so a 403 for every client, until `local.yml` sets `kubernetes_ingress_allowed_range`, once each app's first visit is done through `kubectl port-forward` (`scripts/runbooks/first-run.md`): Nextcloud's, Jellyfin's, Seerr's and SABnzbd's wizards make their first visitor the admin, and Sonarr, Radarr and Prowlarr serve anyone, their API key included, until their first login exists. Those three also set `<APP>__AUTH__REQUIRED=Enabled`: behind Traefik every request comes from a pod's address, which they count as local, so "disabled for local addresses" would open them to the LAN. Traefik's Service keeps clients' addresses (`externalTrafficPolicy: Local`), so the range is matched against the client's own. DNS is a wildcard `*.<domain>` record for `LB_TRAEFIK_IP` in the router, not managed here. No Service opens a node port: NodePort is refused, and so is a LoadBalancer that allocates them. Home Assistant is reached by the name its DHCP reservation gives it in the router's own domain, never under the wildcard, which would send it to Traefik.

### Monitoring

kube-prometheus-stack (chart 92.0.0 from its OCI registry) in `k8s/infrastructure/monitoring/`, with its namespace `monitoring` (privileged, for node-exporter), under its own Flux Kustomization `infra-monitoring` after `infra-controllers`. One replica each of Prometheus (retention `PROMETHEUS_RETENTION`/`PROMETHEUS_RETENTION_SIZE`: 15d/15GB with a NAS, 7d/5GB without; 20Gi on `local`; every ServiceMonitor, PodMonitor and rule in the cluster), Alertmanager (the chart's default, empty receiver: add an e-mail route with a SOPS Secret when wanted; the chart's `KubeCPUOvercommit` and `KubeMemoryOvercommit` are off, since the node they assume the apps could move to is the tainted control plane, so both fire from the first minutes and never clear) and Grafana (`Recreate`, 5Gi on `local`, at `grafana.${DOMAIN}`, the admin password the chart generates: `kubectl get secret -n monitoring kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | base64 -d`). Grafana answers the LAN, so its sidecars read ConfigMaps in `monitoring` alone, through the Role in `grafana-rbac.yaml` (`rbac.namespaced`, `rbac.useExistingRole`; the chart's own role reads every Secret in the cluster, flux-system's age key included), and kube-state-metrics runs without its `secrets` collector, which lists every Secret's values; `test_k8s.py` refuses any other service account outside `kube-system` and `flux-system` that can read every Secret, bar Traefik's (its chart grants it, and narrowing it costs the IngressClass) and the Prometheus operator's (`CLUSTER_SECRET_READERS`). The control plane's controller manager and scheduler are static pods Talos labels `component: <name>`, which the chart's Services select, scraped over HTTPS without verification; etcd is not a pod on Talos, so its Service selects the API server's static pod, which runs in the control plane's host network, where etcd serves its metrics (port 2381, plain HTTP): no address is written anywhere; all three serve beyond localhost because roles/talos binds them to 0.0.0.0. The plain-HTTP scrapes (etcd, kube-proxy, CoreDNS) carry no credentials (`serviceMonitor.authorization: null`): the chart would send Prometheus's service account token with each, in clear, though none asks for one, and `test_k8s.py` refuses a rendered monitor that sends a token over HTTP. Every component has requests, which `make lint TYPE=charts` checks on the rendered chart (rendered without its test pods, which Flux never runs).

### GPU

Whether the host passes its Intel iGPU to the cluster is per host: `local.yml`'s `kubernetes_gpu_mapping`, the id of a Proxmox PCI resource mapping made by hand (`scripts/runbooks/gpu.md`, which also has the host's VT-d and `vfio-pci` steps). With it, the worker (`kubernetes_data_node`) gets `hostpci0` (`group_vars/proxmox/vms.yml`), the `gpu` schematic with Intel's i915 extension and the label `homeserver.internal/gpu: intel` (`group_vars/kubernetes/talos.yml`); Flux's `infra-gpu` applies Intel's GPU plugin from `k8s/infrastructure/gpu/`: upstream's v0.37.1 manifest, vendored with only its namespace edited, its image pinned by digest and the rest patched in the directory's `kustomization.yaml` (`-shared-dev-num=2` and that node selector), in the privileged namespace `intel-gpu-plugin`, which the directory declares (its `README.md` says how to bump it); and the settings say `GPU_I915` `1` and `FRIGATE_DETECTOR_DEVICE` `GPU`. Without it, `0` and `CPU`. The manifests are the same either way: Jellyfin and Frigate set `gpu.intel.com/i915: "${GPU_I915}"` as a limit, and a limit of `0` asks for nothing, so they schedule on a node without the plugin. Frigate's detector device is written into its configuration only when the seed copies it, at the first start, so adding a GPU later means changing it in Frigate's editor. Restarting the VM for `hostpci0` and the `make talos-upgrade` for the schematic are by hand.

## Landmines

What is easy to break, or easy to get wrong when reading the tree. `docs/` (gitignored, so absent from a fresh
clone) holds the audits and reviews behind the older entries.

- **TLS comes from the cluster's own CA, which each device must trust.** `*.homeserver.internal` cannot be validated by public ACME, so cert-manager signs a 90-day wildcard with a private root CA (`k8s/infrastructure/tls/homeserver-ca.sops.yaml`, ten years, `nameConstraints` limiting it to names under the domain and excluding every IP address, which a constraint on DNS names alone leaves open, so its key could vouch for nothing else) and renews it; Traefik serves it as its default certificate (TLSStore `default`), redirects HTTP to HTTPS and adds HSTS. The owner installs the CA's certificate on each device (`scripts/runbooks/tls.md`, which also remakes it for another domain). Jellyfin alone also answers plain HTTP (its Ingress's router priority, 1001, outranks the redirect's, 1000), since its TV and streaming-box apps cannot trust a private CA: what they send crosses the LAN in clear. A real domain with DNS-01 would remove both the device step and that exception (`TODO.md`). The old `k8s/cert-manager/` (v1.4.0, staging ACME, microk8s solver class) was deleted long before.
- **No app is privileged.** Jellyfin and Frigate used to be, for `/dev/dri`; now Intel's GPU plugin hands them the device (`gpu.intel.com/i915`), and every app namespace stays at `baseline`. The privileged namespaces are the platform's, each with a comment saying why: `metallb-system` (the speaker's host network), `local-path-storage` (its helper pods' host paths), `monitoring` (node-exporter) and `intel-gpu-plugin` (the plugin's host paths); csi-driver-nfs runs in `kube-system`, which Pod Security exempts. `PRIVILEGED_NAMESPACES` and `CHART_PRIVILEGED` in `test_k8s.py` list them. Home Assistant runs as a VM (Home Assistant OS), so its manifests went.
- **Flux holds cluster-admin, so merge rights on `main` are the cluster's admin boundary.** kustomize-controller and helm-controller apply whatever the synced branch holds, with cluster-admin. Whoever can merge to `main` (the "Protect main" ruleset: a pull request and `ci-success` required, nobody bypassing) controls the cluster, which is why `flux_sync_url` has no default and a fork syncs its own repository; another branch is unprotected, so syncing one takes `flux_sync_ref_unprotected: true` and its source suspended while it is not being tested (`scripts/runbooks/talos.md`). Read the live ruleset (`gh api repos/kawadeomkar/homeserver/rulesets/24555579`) before relying on it. No other cluster-admin principal runs in the cluster: `portainer` used to bind `cluster-admin` to its pod's ServiceAccount on three NodePorts plus an Ingress, and was deleted rather than scoped; use `k9s` or Headlamp from a workstation instead.
- **No plaintext `Secret` manifest may be committed.** Every Kubernetes Secret is a `k8s/**/*.sops.yaml` encrypted with SOPS for the cluster's age key (`.sops.yaml`: values only, `data` and `stringData`), which Flux decrypts with the `flux-system/sops-age` Secret `roles/flux_bootstrap` keeps; `k8s/README-secrets.md` says how to make one without the plaintext touching the disk, and lists the Secrets the apps need. `.gitignore` blocks `k8s/**/*secret*.yaml` in both letter cases, with negations for the safe-by-construction kinds (`*.sops.yaml`, `*.example.yaml`, `*.template.yaml`, `externalsecret*.yaml`, `secretstore*.yaml`). gitleaks's `k8s-plaintext-secret` rule (YAML and JSON under `k8s/`, where `test_k8s.py` allows nothing but YAML, `.tmpl` and `.md`) allows every `*.sops.yaml`, so `scripts/ci/check-sops-staged.sh` refuses one that was never encrypted (a document without `sops:`, or a value under `data` or `stringData` that is not `ENC[`): on the staged files in the pre-commit hook (`scripts/ci/check-staged.sh`), and on every version in the pushed commits through `check-range.sh` (pre-push and CI). `.sops.yaml` names the owner's age key as the recipient; a fork puts its own there. The homepage service-account token stub is gone, with its allowlist entry. **This repo is public** — that is also why `.claude/` and `inventory` are ignored.
- **The Tailscale subnet router masquerades every tailnet client to the Proxmox host's address**, which is exactly the address the NAS exports VM disks and backups to, with root kept as root. Two controls keep tailnet clients to the NAS's web UI, each enough alone:
  - the tailnet policy's grants, kept by hand in the admin console (`scripts/runbooks/tailscale.md`);
  - the role's fail-closed nftables guard.

  Both are allow-lists, because the NAS's mountd, statd and lock manager use random ports. Any proxy on the host itself (Tailscale Serve with a non-local target, `ssh -L`, SDN Simple-zone SNAT) connects from the trusted address unseen by the guard, and so does tailscaled itself with the debug setting `TS_DEBUG_NETSTACK_SUBNETS=1`. Reload `tailnet-guard.service`; never restart it, which restarts Tailscale.
- **Two secret systems, split by layer:** Ansible Vault (`group_vars/all/local.vault.yml`, git-ignored) for host/playbook variables, and SOPS+age for Kubernetes Secrets (`.sops.yaml`, the key and the procedure in `k8s/README-secrets.md`). Do not put k8s Secrets in `vault.yml`.
- **NetworkPolicies are enforced, so a new path between pods needs a rule.** Talos's Flannel runs its policy agent, kube-network-policies (a `KubeFlannelCNIConfig` control-plane patch, `talos_patch_network_policies`); without it every NetworkPolicy is accepted and ignored. Each app namespace has one policy over all its pods (`k8s/apps/<group>/network-policy.yaml`, which `test_k8s.py` requires): in, only its own pods, Traefik and Homepage (Frigate: its UI from Traefik and Homepage, its streams from anywhere, never its unauthenticated API on 5000, which only the kubelet's probes reach, from the node); out, anywhere but the NAS (`EGRESS_DENIED_ADDRESS`), whose NFS exports trust the worker's address, which pods' traffic leaves the node with, and the Proxmox host (`PROXMOX_ADDRESS`), whose API and SSH answer the LAN, in both setups (without a NAS both name the host; only its main address, never another it may have). In `monitoring`, Prometheus, Alertmanager and kube-state-metrics answer only that namespace and Grafana also Traefik. An app that must reach another namespace, or the NAS, needs its policy changed, or it times out. **A pod's first seconds are judged without its policy**: the agent learns a new pod's address from the API, after the pod has started, so a fresh pod's first connections go through unchecked (a test pod in a deny-all namespace reached the NAS at once and was blocked 15 seconds later), and packets from the node to it may be dropped then (a new Homepage pod's probes were, for three seconds, and retried). containerd's NRI would let the agent see a pod as it starts, but Talos keeps NRI off by default, since any pod with its socket could rewrite containers, and it would take restarting the nodes: left so (2026-10-17). Flux's own policies (the FluxInstance's) apply in `flux-system`. What a policy drops is in the agent's log on the node that dropped it, each `Packet denied` three lines after the `Evaluating packet` line naming its source and destination: `kubectl -n kube-system logs -l k8s-app=flannel -c kube-network-policies --prefix --tail=-1 | grep -B3 'Packet denied'`. Talos runs the agent at `--v=2`, which logs every packet it judges (12,000 to 15,000 lines an hour on a worker running the apps, as traffic goes, with the start of each packet in hex), and its configuration has no setting for it; kubelet's log rotation bounds it, and the API server's proxy to a pod a policy closes (`kubectl get --raw .../proxy/...` to Prometheus) times out and shows there too.
- **The nodes' firewall drops what no rule lets in, so a new port on a node needs a rule.** Talos's ingress firewall (`group_vars/kubernetes/talos.yml`: `NetworkDefaultActionConfig` blocks, each `NetworkRuleConfig` lets a port in) answers the LAN on the Talos API (50000) and, on the control plane, the Kubernetes API (6443), both behind client certificates; the rest only the nodes: etcd (the control plane alone), trustd, the kubelet, Flannel's VXLAN, MetalLB's memberlist, and, to the pod network too (talosctl's default, which `roles/talos` asks talosctl for as it renders, `talos_pod_subnets`, so that no private range is written in the repo; `make lint TYPE=talos` checks that each rendered kubelet rule names it), the kubelet and the metrics Prometheus scrapes on the nodes. Everything else to a node is dropped, kube-proxy's health checks and the node port of Traefik's Service among them, while Talos always lets in established connections, ICMP, pod-to-pod and pod-to-service traffic and pods' DNS queries, and the firewall never sees what kube-proxy forwards to pods, the load balancers' addresses included. A hostNetwork pod's new port, or a new scrape target on a node, times out until a rule names it. Try a changed rule first with `talosctl apply-config --mode try` on the rendered configuration (`talos_keep_rendered`), which reverts by itself: a rule that closes 50000 locks the role out of the node, leaving only its console in Proxmox and a reinstall.
- **The NAS's NFS shares and the VM backups trust addresses, on a flat LAN.** NFS with `sec=sys` trusts the client's address, and the shares map root to root: the cluster's to the worker's address, the VM and backup shares to the Proxmox host's. The nightly backups hold the control plane's machine configuration (every key of the cluster) and its etcd (every Secret, flux-system's age key included), so treat `homeserver-backup` as secret-level. A device that leases a node's address (an unreserved DHCP lease) or ARP-spoofs it reads them as root. The owner's answer is the network, decided 2026-10-17: DHCP reservations for every node and a servers VLAN the IoT and Wi-Fi devices cannot reach (`TODO.md`); Proxmox Backup Server's client-side encryption was considered and left out. The NAS takes only privileged source ports (`allow_nonroot: false`), and pods cannot reach it (above).
- **An app `make suspend` stopped is out of Flux's hands until `make resume`**: Flux skips it entirely, so a change merged meanwhile (an image bump) reaches it only then, and one deleted from Git meanwhile is not pruned. `kubectl get deploy -A` shows them at 0, annotated `kustomize.toolkit.fluxcd.io/reconcile: disabled`.
- Apps whose Secret does not exist yet (made by the owner, `k8s/README-secrets.md`) wait for it, and their Flux Kustomization does not become ready; the others are not held up.

## Conventions

- **Manifest layout**: `k8s/clusters/<setup>/` holds Flux Kustomizations only; `k8s/infrastructure/` the platform (a controller's directory holds its namespace); `k8s/apps/<group>/` one app group per directory, applied as a unit by its own Flux Kustomization, with a `kustomization.yaml` listing its files, `namespace.yaml`, one file per app (its claim, Deployment, Service and Ingress), and a SOPS Secret once the owner makes it. Every object names its namespace; cluster-scoped ones none. A configMapGenerator's source is a `.tmpl` file.
- **Deployments**: one replica, `Recreate`, Homepage aside; `app.kubernetes.io/name` labels and selectors.
- **Adding an app**: put it in its group's directory, or a new group with its own `namespace.yaml`, `kustomization.yaml` and a Flux Kustomization in both `k8s/clusters/*/apps.yaml` → a `ClusterIP` Service and an Ingress (`ingressClassName: traefik`, host `<app>.${DOMAIN}`) → its data on a claim of `local`, or a static volume in both `k8s/infrastructure/storage/*/` → probes, a startup probe if it migrates before it listens, requests, `allowPrivilegeEscalation: false` and the `RuntimeDefault` seccomp profile → a `${VAR}` it needs added to `flux_bootstrap_settings` (`group_vars/kubernetes/flux.yml`) and `tests/fixtures/cluster-settings.yaml` → a Secret as a SOPS file (`k8s/README-secrets.md`) → a database as a Deployment of its own labelled `app.kubernetes.io/component: database`, which `make suspend` stops after the app and `make resume` starts first → in its namespace's NetworkPolicy, any new path in or out (a new group gets a policy of its own, like the others) → if it needs more than baseline (`privileged`, a hostPath, host networking, added capabilities), a namespace labelled `pod-security.kubernetes.io/enforce: privileged` with a comment saying why, `ignore-check.kube-linter.io/<check>` annotations, and the namespace in `PRIVILEGED_NAMESPACES` (`tests/policy/test_k8s.py`) → an immutably pinned image.
- **Roles** live in `./roles` beside the playbooks at the repo root, variables prefixed with the role name (ansible-lint enforces it). `ansible.cfg` deliberately sets no `roles_path`: roles beside a playbook are found by default, while `ansible-galaxy install` then defaults to `~/.ansible/roles`, which keeps third-party code out of this public repo. No role depends on a Galaxy collection. Task names in imported task files carry a `<file> | ` prefix (ansible-lint's `name[prefix]`). Every mutating step must be skipped in check mode and report what it would do, and a second run must report no changes. `tests/integration` checks every role against stateful fakes (`fake_truenas.py`, a TLS JSON-RPC server; `fake_pve.py` behind `fake_pve_bin/`, with `apt-get` reading the scratch repository directory the test passes as `proxmox_apt_sources_dir`), running each role with this repo's configuration: a dry run, an apply, a second apply, a dry run, then drift corrected once. A new API method or command needs a matching fake, or the test fails on purpose. The fakes always answer, so `tests/unit/test_truenas_client.py` covers in process, with a scripted socket and a clock that never waits, what they never do: TrueNAS refusing a login or a call, rate-limiting logins, dropping the connection, failing or never finishing a job, and refusing an interface commit, which must discard the saved change, or never seeing the check-in, after which TrueNAS rolls the address back by itself. The fakes cannot prove the real machines behave the same, so still run check mode against the real machine first.
- **No address in any tracked file.** IP addresses, and anything else that identifies this network, are never written in a task, a role default, a template or an example — tasks reference a variable, and the real value lives only in the gitignored `group_vars/all/local.yml`. `group_vars/all/local.yml.example` is its committed counterpart and uses RFC 5737 placeholders (`192.0.2.x`). Adding such a variable means adding it to both files, and to the list `make init` asks from (`scripts/init/settings.py`; `tests/policy/test_make_init_settings.py` checks the three agree, and that every vault variable the group_vars read is asked for too). `.gitleaks.toml` writes the rule down for gitleaks, on top of its default secret rules: private, CGNAT and link-local IPv4 anywhere, and a private network written in part (its first three numbers, then `.x`, `.*` or a `/prefix`); any IPv4 in code, tests, manifests, scripts, workflows, `host_vars/` and Markdown anywhere (RFC 5737, loopback and `0.0.0.0` excepted); private IPv6; MAC addresses, with colons, dashes, or dots between groups of four; a disk's `/dev/disk/by-id/` name, which carries its model and serial, and WWNs (QEMU's virtual disks excepted); tailnet names; plaintext `Secret` manifests under `k8s/`; and, by path alone, the files that are never committed (the vault, at its path now or its old one, vault password files, `local.yml`, make init's `.init-tmp` copies of those three, a root `inventory`, `MACHINES*`, `talosconfig` and `kubeconfig` with any suffix, `*.kubeconfig`, age keys, Talos's generated `secrets.yaml`, `controlplane.yaml` and `worker.yaml`, run logs). `tests/policy/test_gitleaks_rules.py` proves each rule on generated fixtures, including what must not match (RFC 5737, loopback, image tags, version strings, QEMU's disk names, the certificate-pin placeholder). CI's `leaks` job scans the commits each change adds with these rules. The address literals the old manifests held (K8S-9) went with them; the tree has none.
- **Variables**: environment-specific values go in `local.yml` as above. Ansible secrets go in the vault, `group_vars/all/local.vault.yml` under a `vault_` prefix and are exposed by indirection from a plain variable (the old example was `discord_token: "{{ vault_discord_token }}"`). Kubernetes Secrets do not go there — see the Landmines note above.
- **Every image is pinned by tag and digest.** A tag can be moved to other contents, a digest cannot: the tag says what the image is, the digest what is pulled (`image: docker.io/linuxserver/sonarr:4.0.19.2979-ls320@sha256:…`). `tests/policy/test_k8s.py` refuses an image without a digest, in the manifests, in the charts' rendered output (`make lint TYPE=charts`), in a container's flags (cert-manager's ACME solver, the Prometheus operator's config reloader) and in a Prometheus or Alertmanager. A chart's images are pinned in its release's values, each chart by its own keys (`tag: <version>@<digest>`, or a `digest` or `sha` beside the tag, kube-prometheus-stack's `sha` without the `sha256:` prefix but kube-state-metrics' with it), so **bumping a chart means bumping the images its values pin**, whose tags are then the chart's new defaults: until then the old images run. A vendored file keeps upstream's tag and its `kustomization.yaml` adds the digest (`images:`). Resolve a digest from the registry, which needs no Docker: `crane digest <image>:<tag>`, or `docker buildx imagetools inspect`. LinuxServer.io images come from Docker Hub (the same digests as lscr.io and ghcr.io), and use the `x.y.z-lsNNN` tags, since LinuxServer.io re-points plain `x.y.z` at every build revision. Do not add `imagePullPolicy: Always`: kube-linter rejects it, and any image without a tag or tagged `latest`.
- **Resource requests on every workload** and every chart component (kube-linter requires CPU and memory requests, `make lint TYPE=charts` on the charts' output too), with limits only where a runaway can starve the node (nextcloud, jellyfin, frigate, photoprism, both MariaDBs). All values are un-measured guesses. Summed from the rendered manifests, the apps request about 2.5 vCPU and 7.5 GiB together, and the platform on the worker (the charts, the DaemonSets and CoreDNS) requested 1.3 vCPU and 2.7 GiB on a test host without a NAS (2026-10-20), so the worker that runs them needs at least 4 vCPU, 12 GiB and a 32 GiB system disk (the images filled a 14 GiB one there), which `kubernetes_settings_error`'s sizing message asks for without a NAS.
- `inventory`, `.claude/` and `docs/` are gitignored because **this repo is public** — they would otherwise publish host addresses, and `docs/MACHINES.md` also lists MAC addresses and drive serials. A fresh clone recreates `inventory` from the committed, address-free `inventory.example` (`make init` copies it).
- YAML style comes from `.yamlfmt` (basic, `---` document start, line breaks retained). `.yamllint` (160-column lines, run with `--strict`) and `.ansible-lint` (production profile, with `strict`, so its warnings fail too) both skip `k8s/`, which `make lint TYPE=k8s` covers with kubeconform and kube-linter. ansible-lint warns that it cannot import the custom modules' `module_utils`; that warning is expected. `make lint` runs both, each a TYPE of its own, plus `poetry check --lock --strict`, ruff (below), `ansible-doc` on every custom module (ansible-lint does not check `DOCUMENTATION`; the options every TrueNAS module shares are documented once, in the doc fragment `roles/truenas/doc_fragments/truenas_api.py`, which `ansible.cfg` points `ansible-doc` at), check-jsonschema on `dependabot.yml` and the workflows (SchemaStore's schemas, bundled), the role references (`make lint TYPE=docs`, below), and the Kubernetes checks (`make lint TYPE=k8s`); `make test` then runs the unit, policy, gitleaks and idempotence tests, each a TYPE too. `tests/policy` checks the repo's own rules: the lock matches `pyproject.toml` and hashes every package, no vault is tracked, its path is ignored and its example lists every secret the group_vars read, the ruleset body requires the workflow's gate job, and the roles keep their conventions (`test_roles.py`): each role default matches its argument-spec entry, each module's documentation matches its argument spec and documents its check-mode, diff-mode and platform support (`attributes`), check mode as its AnsibleModule declares it, the tracked configuration passes every role's argument specs and input checks, with `local.yml.example` and with the `local.yml` of a setup without a NAS, while both playbooks refuse NAS settings that come without an address, tasks pass only options the custom modules accept, and every option whose name looks like a secret (ansible-test's `no-log-needed` pattern) is `no_log`, bar a short list of named exceptions. The manifests keep theirs where kube-linter cannot check them (`test_k8s.py`, described in its docstring): every Flux Kustomization decrypts and substitutes, every `${VAR}` is a setting, every namespace is declared once and a controller's comes with it, no node ports, no PodDisruptionBudget, the privileged namespaces, the hostPath volumes and the service accounts that can read every Secret match lists in the test (the charts' output too, after `make lint TYPE=charts`), the apps' replicas, strategy, hardening, ingresses and labels, the shared volumes' `chown-mount` and no `fsGroup` on NFS, every Secret is SOPS-encrypted, and LinuxServer.io tags are immutable, and every quantity parses once substituted.
- **Python** is formatted and linted by ruff, configured in `ruff.toml`: 120 columns, Python 3.12, and modules and callback plugins exempt from `E402`, since their imports follow their documentation strings. `ruff format` formats; `make lint TYPE=python` checks both. The commit that first formatted everything is listed in `.git-blame-ignore-revs`, which GitHub reads and `make init` points `git blame` at; list any later reformatting commit there too. `make test TYPE=unit` also reports the modules' coverage (`.coveragerc`): a report, not a gate, since it sees only the in-process tests and not the modules the idempotence tests run inside ansible-playbook.
- **Role references** (`roles/<role>/REFERENCE.md`) are docsible's pages, written whole by `make fix TYPE=docs` from the role as it is: `meta/main.yml`, `meta/argument_specs.yml`, the defaults and vars as tables linked to their lines, and each tasks file as a table and a Mermaid graph. Never edit one by hand, and never give docsible a template or its comment annotations: a page says what the role says. A role's `README.md` stays its own, written by hand, and links to its page; `.gitattributes` marks the pages generated, so a pull request's diff folds them. `make lint TYPE=docs` (in CI's linters job) generates every page again from a copy of `roles/` in `.cache/docsible` and fails on a difference, a role without a page, and any docsible output but its "Documentation generated at" line: docsible reports a file it cannot read (in 0.8.0, one with an `!unsafe` tag), leaves it out and exits 0. The Makefile says why each flag is set. Links are relative, without `--repository-url`: `detect` would write the current branch into every link, and for a role outside a collection docsible leaves `roles/<role>/` out of the link (docsible#95). docsible 0.8.0's limits, left as they are: a block's `always` tasks are in neither the table nor the graph, the table shows no tags for a task inside a block (it reads them from top-level tasks only, so `roles/truenas`'s stage tags, the ones `make deploy TYPE=truenas TAGS=…` selects, read blank), table rows end in spaces, and `--comments` and `--task-line` stay off (the first splits a table row at a multi-line comment, the second links a task whose name holds a quote to `#L`). A Dependabot bump of docsible that changes the pages fails `make lint TYPE=docs` until `make fix TYPE=docs` is run on its branch.
- **CI** (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`, splitting `make lint test`'s types between its jobs (`test_github.py` checks that each type runs somewhere): `make -k lint` with every TYPE but the Kubernetes checks; `make test TYPE=unit,policy` and `make test TYPE=idempotence` on Python 3.13 and 3.14, on Arm runners (free for public repositories, and faster at the CPU-bound idempotence suite than x64); `make -k lint TYPE=k8s` (kubeconform, kube-linter, the charts and the Talos configurations); `leaks`, which runs `make test TYPE=gitleaks` and `scripts/ci/check-range.sh` (gitleaks over the commits the change adds, with the target branch's `.gitleaks.toml`); actionlint and zizmor (pedantic persona, so a digest-less image or a missing permissions block fails) over the workflows; shellcheck over `scripts/`; and, on pull requests only, `dependency-review`, which fails a change that adds a pip package with a known vulnerability, from GitHub's dependency graph (it cannot see the SHA-pinned actions, which zizmor's online `known-vulnerable-actions` audit covers instead). `ci-success` aggregates them, allows `dependency-review` alone to be skipped (on pushes; `tests/policy/test_github.py` checks that nothing else can be), and is the one check the "Protect main" ruleset is to require. `.github/rulesets/main.json` holds that ruleset's reviewed body, but GitHub never reads the file: it takes effect only when applied (`gh api -X PUT repos/kawadeomkar/homeserver/rulesets/24555579 --input .github/rulesets/main.json`), so read the live ruleset (`gh api repos/kawadeomkar/homeserver/rulesets/24555579`) before relying on a red PR being unmergeable. No job gets a secret (ansible-lint reads a placeholder vault password file) and none reaches the home network, so `make check` stays local. Actions are pinned to full commit SHAs with a version comment, which the repository settings require, and only an allow-list of actions may run. The allow-list also rejects `docker://` steps, so actionlint, kubeconform, kube-linter and gitleaks are downloaded by version and checked against a sha256. `.github/actionlint.yaml` declares the `ubuntu-26.04` and `ubuntu-26.04-arm` runner labels until actionlint knows them. Outside the gate, `.github/workflows/scorecard.yml` runs OpenSSF Scorecard weekly and on every push to `main`, publishes the result to the OpenSSF API and uploads it to code scanning; the API refuses results from a workflow that breaks its rules, which the file's header lists, so read them before changing it. `make init` installs git hooks for the same leak checks (below). The full plan, including what later PRs add, is `docs/CI-PLAN.md` (gitignored).
- **What CI cannot vouch for.** The gate is written by the pull request it judges: `ci-success` comes from the PR's own `.github/**`, `Makefile`, `scripts/**`, `tests/**`, `pytest.ini`, `pyproject.toml`, `poetry.lock`, `poetry.toml` and the linters' configuration (`.yamllint`, `.ansible-lint`, `ruff.toml`, `.kube-linter.yaml`, `.kube-linter-charts.yaml`), so a green check proves nothing about a change to those files; review them as the gate itself. They, with `ansible.cfg`, `roles/**`, `group_vars/**` and the playbooks, also run with the vault password, the TrueNAS API key or root SSH whenever `make check`, `make deploy`, `make suspend`, `make resume`, `make talos-upgrade` or `make etcd-snapshot` runs on the workstation, with or without a `TYPE`, so never run `make` on an unmerged outside PR in the clone that holds `.vault_pass` and `local.yml`; use a separate clone without them.
- **Git hooks** (`.pre-commit-config.yaml`, run by pre-commit from the lock; `make init` installs them): gitleaks over the staged changes, then `scripts/ci/check-sops-staged.sh` (both in `scripts/ci/check-staged.sh`), and before a push, `scripts/ci/check-range.sh` over the commits being pushed (pre-commit's refs as its `BASE` and `HEAD`), the check CI runs. Each hook runs its script directly, not through make. They need only bash and gitleaks from Homebrew (`brew install gitleaks`), so they work in any shell, with or without the virtualenv active; the linters stay in `make lint` and CI. A hook can be skipped with `--no-verify`, which is why CI's `leaks` job repeats the checks.
- **When a leak check fires.** A pushed commit is published, even on a pull-request branch. Do not merge, and close the pull request if the finding is real. Rotate a leaked secret at once: the TrueNAS API key through the role and the vault, and re-key the vault if its password was involved. For an identifier, RFC 1918 addresses are low impact, while public addresses, tailnet names, MACs and serials are higher; decide whether anything on the network needs to change. Ask GitHub Support to purge cached views and the `refs/pull/*` copies. If it reached `main`, removing it means rewriting history, which needs the ruleset's force-push rule switched off for the time and every clone re-made. Then add a fixture to `tests/policy/test_gitleaks_rules.py` for whatever the checks missed. `SECURITY.md` tells others how to report a problem privately.
- **Python dependencies** are managed with Poetry (2.x, non-package mode). Direct pins are exact (`==`) and live in `pyproject.toml`: what the playbooks need in `[project] dependencies`, and the linters, tests and hooks in the `dev` dependency group (PEP 735 `[dependency-groups]`, never `[tool.poetry.group.*.dependencies]`). `make lock` updates `poetry.lock`, which resolves once for every Python in `requires-python`, with markers, and records a sha256 for every file, which Poetry checks when it installs. It changes only what `pyproject.toml` changed (`UPDATE=<packages>` moves those on), and `poetry.toml` makes it take only releases at least 7 days old (`solver.min-release-age`). `poetry.toml` also installs wheels only, keeps the keyring closed, and lets Poetry run without `VIRTUAL_ENV` make an environment of its own in its cache, never one in the checkout; it is committed so that it overrides each user's global Poetry configuration. Poetry itself is not in the lock: each user installs it (above), `requires-poetry` says which versions work, and CI installs `POETRY_VERSION` with pipx. `make install` runs `poetry sync`, which installs exactly the main and `dev` groups and removes anything else but pip. CI makes a virtualenv of setup-python's Python in `$RUNNER_TEMP` and exports it as `VIRTUAL_ENV` before `make install`. `make lint TYPE=lock` (`poetry check --lock --strict`) fails when the lock is stale, and `tests/policy/test_lock.py` when a pin is not exact or not the locked version, or a package has no hashes. gitleaks's default rules skip `poetry.lock`, as they do every lock file; `pyproject.toml` is scanned.
- **Dependabot** proposes weekly updates, at least 7 days after each release, for the SHA-pinned actions and every package in the lock (`allow: dependency-type: all`; by default it would update only the packages `pyproject.toml` names). It re-locks with its own Poetry, which must satisfy `requires-poetry` (keep that a range: outside it Dependabot opens no PR), and it does not read `poetry.toml`. Read each PR before merging it; never merge one only because CI is green. The required check is strict, so a PR must be up to date with `main` before it merges, and Dependabot rebases only on its schedule or a conflict: after merging one of its PRs, comment `@dependabot rebase` on the others (or use "Update branch"). **It cannot see these pins, which are bumped by hand each quarter**, each together with its integrity value: `ACTIONLINT_VERSION`, `KUBECONFORM_VERSION`, `KUBE_LINTER_VERSION`, `GITLEAKS_VERSION` and `TALOSCTL_VERSION` (bumped with `talos_version`, whose minor release it must share; a policy test checks), each with its `_SHA256`, and `POETRY_VERSION`, which has none and must stay within `requires-poetry`, in `ci.yml`; `KUSTOMIZE_VERSION` and `HELM_VERSION`, each with its `_SHA256`, in `ci.yml`; `KUBE_SCHEMA_REF` with `KUBERNETES_VERSION` (Talos's default) and `KUBE_CRD_SCHEMA_REF` in the Makefile; the charts' versions, each with its digest (or csi-driver-nfs's commit and path) and the images its release pins, until Renovate takes them, and local-path-provisioner's vendored manifest (`k8s/infrastructure/controllers/common/local-path/README.md`), which stays a hand bump; the Flux Operator in `group_vars/kubernetes/flux.yml` (`flux_bootstrap_operator_version` with its `install.yaml`'s SHA-256 and its image's digest, and the FluxInstance's exact Flux release with the manifests artifact's digest), which `roles/flux_bootstrap` refuses unpinned; and the Talos pins in `group_vars/all/kubernetes.yml` (`talos_version`, `talos_contract`, `talos_kubernetes_version`, which must equal `KUBERNETES_VERSION`, a policy test checks, with the ISO's SHA-256 and each schematic's installer digest at the new version, since the Image Factory publishes no checksum), moved onto the cluster by `make talos-upgrade` (`scripts/runbooks/talos.md`); and Home Assistant OS's OVA (`haos_version` with `haos_ova_sha256`, GitHub's digest of the release asset, in `group_vars/proxmox/haos.yml`), which only ever makes a new VM, since Home Assistant updates itself (`scripts/runbooks/haos.md`). At the same bump, delete `.github/actionlint.yaml` if actionlint now knows `ubuntu-26.04`.
- **Renovate** (`renovate.json`) updates what Dependabot cannot see under `k8s/`: container images, HelmRelease chart versions and OCIRepository tags (managers `flux`, `kubernetes`, `helm-values`, `kustomize`), each release at least 7 days old where its registry gives a release time (`minimumReleaseAgeBehaviour: timestamp-optional`: only Docker Hub does, and Renovate 42's default would hold every ghcr.io and quay.io image and the OCI charts back for good; `test_k8s.py` checks it), and an image or OCI chart from any other registry (ghcr.io, quay.io, registry.k8s.io) only once approved on the Dependency Dashboard, since the age gate cannot hold it back; with `pinDigests`, so each image keeps its digest and a tag moved upstream becomes a pull request; each chart in one pull request with the images its release pins (`groupName` by directory); commits prefixed `[dependencies]`. LinuxServer.io's tags need one versioning rule per shape (`x.y.z.build-lsN` for sonarr, radarr, prowlarr; `x.y.z-lsN` for sabnzbd and nextcloud; Jellyfin's `x.y.zubuNNNN-lsN`, the Ubuntu release a compatibility; MariaDB's `x.y.z-rN-lsN`): a tag no rule parses would never be updated, security releases included, and `test_k8s.py` checks that each image matches exactly one rule. local-path-provisioner's and Intel's GPU plugin's directories are excluded (each re-vendored by hand). It does not touch the FluxInstance (Ansible's) or the Talos pins, which stay hand bumps. It runs once the owner installs the Mend Renovate app, after the ruleset split (TODO.md). Read each PR before merging: Flux deploys `main` as soon as it lands. FileBrowser Quantum publishes security releases often; a Homepage release can add a skeleton configuration file, which the emptyDir it copies its configuration into absorbs, but check its first start. `make lint TYPE=github` validates `renovate.json` against check-jsonschema's bundled schema.
