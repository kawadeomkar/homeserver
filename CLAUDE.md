# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Infrastructure repo for a homelab. It holds hand-maintained Kubernetes manifests for ~20 self-hosted services (`k8s/`) and the Ansible that configures the infrastructure machines: `roles/truenas` (the NAS, through its API), `roles/proxmox_apt` (the hypervisor's package repositories and upgrades), `roles/proxmox_tailscale` (remote access: the hypervisor as the LAN's Tailscale subnet router, behind a forwarding guard) and `roles/proxmox_storage` (its VM-disk storage on the NAS). There is no application code.

The manifests were written for a single Ubuntu host running k3s, with bulk storage on a separate TrueNAS box over NFS. That cluster had been through **minikube → microk8s → k3s**, and most manifests were originally generated by `kompose` from Docker Compose. Both migrations were left partially finished, so manifests are not uniform: assume any given file may still carry minikube/microk8s-era assumptions and verify before copying it as a template. The "Landmines" section below lists the ones that are actively broken.

## Direction of travel

**There are no live deployments.** Nothing described below is currently serving traffic, so no change
needs to preserve running state, and credentials committed in-tree were never used.

The target is three machines (hardware in `docs/MACHINES.md`, which is gitignored):

| Machine | Role |
|---|---|
| `homeserver` | **Proxmox** hypervisor; Kubernetes runs in VMs on it, with **Talos Linux** as the plan. Also the LAN's Tailscale subnet router, the one way in from outside, when `local.yml` gives `tailscale_advertise_routes` |
| `truenas` | TrueNAS Community Edition; external storage, including Proxmox's VM disks and backups. **Optional**: with no NAS address in `local.yml`, the NAS play ends by itself and VM disks stay on the Proxmox host (below) |
| `opnsense` | router and firewall |

**The Ansible layer for the old Ubuntu host is gone.** `roles/main` (host configuration), `roles/k8s`
(k3s install plus `kubectl apply`), the playbooks, `group_vars/all/vars.yml`, the Vagrant setup and the
helper scripts were deleted as throwaway — Talos has no SSH, no apt, no user accounts, an immutable root
filesystem, no bundled ingress controller or CSI driver, and enforces Pod Security Admission. They are in
the git history. The Ansible here configures the infrastructure machines (TrueNAS and Proxmox), not
Kubernetes nodes. The `k8s/` manifests are the asset that migrates.

`docs/MIGRATION-TRIAGE.md` and `docs/ISSUES.md` predate that deletion: their Ansible-layer findings are
moot, their manifest findings still apply. Some fixes that would be correct for a single Ubuntu host
(notably keeping the `/opt` hostPath storage model working) are wrong for the target.

## Commands

```bash

make linters                      # poetry check --lock, yamllint --strict, ansible-lint (production profile, strict), ruff, module docs, GitHub config schemas, role references (make lint-docs)
make docs                         # every role's REFERENCE.md, written by docsible from the role; make lint-docs fails while one is stale
make test-idempotence             # each role run repeatedly against local fakes, one pytest worker per CPU
make lint-k8s                     # make lint-kubeconform, make lint-kube-linter, then make lint-talos
make lint-talos                   # every node's Talos configuration rendered by roles/talos and validated by talosctl (skipped without it)
make lint-kubeconform             # kubeconform -strict against Kubernetes 1.37.1 (Talos's), pinned schemas
make lint-kube-linter             # kube-linter with .kube-linter.yaml

make check-truenas                # dry run of roles/truenas against the NAS, with --diff
make truenas                      # apply it; TAGS=truenas_network (or _pools, _system, _datasets, _snapshots, _nfs, _alerts) for one stage
make check-proxmox / make proxmox # the same for roles/proxmox_apt, roles/proxmox_tailscale, then roles/proxmox_storage and roles/proxmox_backup, on the Proxmox host
```

Always run tools from the project's virtualenv, never from `PATH`. On this machine that is the pyenv virtualenv `homeserver` (Python 3.14.6, under pyenv's `versions/3.14.6/envs/`); `make` uses the active virtualenv (`VIRTUAL_ENV`) and otherwise `./.venv`, and `VENV=<path>` overrides both. Poetry is the exception: it comes from `PATH` (`POETRY=<path>` overrides), installed outside the project's environment, e.g. with `pipx install poetry`. Never install it into the `homeserver` env: `poetry sync` would remove its dependencies. `make` runs it with `VIRTUAL_ENV` set to the project's environment; without one, Poetry looks for a Python of its own and finds the broken `python3`. `python3` itself resolves to a broken pyenv build (3.13.1, `libintl` dyld error), and `~/.local/bin/ansible-playbook` and `~/.local/bin/yamllint` have a dead shebang. ansible-core 2.21 treats a non-boolean conditional as a fatal error. When the shell's standard handles are non-blocking, ansible commands exit with "Ansible requires blocking IO"; redirect stdin from `/dev/null` and stdout/stderr to a file.

`kubeconform` is the usable gate for manifests — `kubectl --dry-run=client` is not, since it needs a live API server for OpenAPI validation. `kubectl` v1.36.2 (with Kustomize v5.8.1 embedded), `kubeconform` v0.8.0 and `kube-linter` v0.8.3 are what works locally. `make lint-kubeconform` runs kubeconform strictly against the Kubernetes version Talos ships, with the schemas pinned to one commit and cached in `.cache/kubeconform`. `make lint-kube-linter` runs kube-linter with `.kube-linter.yaml`: its default checks, minus three that contradict choices made here (read-only root filesystems, non-root users, memory limits), plus a check that every container requests memory and one that rejects `imagePullPolicy: Always`. It skips the four monitoring directories that kube-prometheus-stack will replace. A workload that needs what a check forbids carries an `ignore-check.kube-linter.io/<check>` annotation saying why. Both tools come from `PATH`, as gitleaks does for the leak checks (Homebrew here, pinned by version and checksum in CI); the idempotence tests also take `openssl` from `PATH`, for the fake NAS's certificate.

Vault: `ansible.cfg` sets `vault_password_file = ./.vault_pass`, so `--ask-vault-pass` is unnecessary locally. It holds `vault_truenas_api_key` (read by `group_vars/nas/connection.yml`), with remote access `vault_tailscale_auth_key` (a one-off Tailscale auth key, read by `group_vars/proxmox/tailscale.yml` and spent at the host's first login; a spent one does nothing), optionally `vault_truenas_mail_password` (the alert mail's server, read by `group_vars/nas/truenas.yml`), and `vault_discord_token`, left over from the deleted roles. Never the Talos secrets bundle: the vault is committed to this public repository, as ciphertext no stronger than `.vault_pass`, and the bundle is every key of the cluster, so it lives in `talos_config_dir` (`kubernetes_settings_error` refuses `vault_talos_secrets`). Never print its contents; check it by listing variable names only.

## Architecture

### Infrastructure Ansible

Infrastructure roles in three playbooks: `truenas.yml` runs `roles/truenas`, `proxmox.yml` runs `roles/proxmox_apt`, `roles/proxmox_tailscale`, `roles/proxmox_storage` then `roles/proxmox_backup`, `kubernetes.yml` runs `roles/proxmox_vm` on the Proxmox host and then `roles/talos` and `roles/flux_bootstrap` on the controller, and `site.yml` runs all three, NAS first. `talos-upgrade.yml` and `etcd-snapshot.yml` run the talos role's `upgrade` and `etcd-snapshot` entry points, after a play on localhost that refuses a cluster whose inventory lacks the `kubernetes` group, which would otherwise match no host and end without a word. The inventory has three groups: `nas` (host `truenas`), `proxmox` (host `homeserver`) and `kubernetes` (host `homeserver-k8s`, local: the cluster is built from the workstation), and no addresses.

**The roles are generic; this setup is configuration.** Role defaults change nothing (empty lists and dicts, null for "leave alone"), and task files hold no configuration values, only variables, API namespaces and CLI verbs. Everything that describes these machines lives in tracked group_vars, apart from addresses and serials:

| File | Holds |
|---|---|
| `group_vars/all/local.yml` (git-ignored) | addresses, disk serials, the NAS's pool names when they are not `persistent` and `ephemeral`, the installer's storage when it is not `local-lvm` (`proxmox_local_vm_storage`: every VM's without a NAS, the cluster's system disks with one too), the cluster's Kubernetes section: node addresses and MACs, the repository Flux syncs, without a NAS the worker's size, for a test host's cluster its own credentials directory (`kubernetes_talos_config_dir`), and for remote access the LAN's prefix (`tailscale_advertise_routes`) |
| `group_vars/all/vault.yml` | the TrueNAS API key, and the Tailscale auth key |
| `group_vars/all/storage.yml` | the VM storage layout, read by both plays so a share and the storage that mounts it cannot drift apart: the NAS's pool names by class (`nas_pools`: `persistent` and `ephemeral`, overridable in `local.yml`), every VM class (`vm_storage_classes`, ids `homeserver-persistent` and `homeserver-ephemeral`), the classes the setup has (`vm_storage`: both with a NAS, the ephemeral class alone without, on the installer's storage), one pool per project that creates VMs (`vm_storage_consumers`, first `claude-on-proxmox-ephemeral`), and the NFS exports derived from them; the NAS's address for whatever mounts it (`nas_address`); the space kept for the VMs on the ephemeral pool (`vm_storage_ephemeral_reservation`) and the cap on the persistent VMs' dataset (`vm_storage_persistent_quota_gib`); the installer's storage (`vm_storage_installer`: `local-lvm`, unless `local.yml` sets `proxmox_local_vm_storage`, a blank value counting as unset); and `nas_present`, worked out from the NAS addresses, which switches to a setup without a NAS, where the installer's storage is the only VM storage |
| `group_vars/all/kubernetes.yml` | the Kubernetes cluster's shape and what more than one play reads about it: `kubernetes_present`, worked out from `local.yml`'s node addresses, the cluster's two nodes, the same in both setups (`kubernetes_nodes`), and `kubernetes_settings_error`, which every playbook asserts first |
| `group_vars/nas/connection.yml`, `group_vars/proxmox/connection.yml` | how each host is reached |
| `group_vars/nas/truenas.yml` | the NAS: network, pools, settings, datasets, shares, services |
| `group_vars/proxmox/apt.yml` | the Proxmox host's repositories (no-subscription on, enterprise off), the upgrade on every run, and what needs a reboot |
| `group_vars/proxmox/storage.yml` | the Proxmox storages and boot delay |
| `group_vars/proxmox/backup.yml` | the nightly backup job: the VMs it covers (`vm_backup_vmids`: the cluster's nodes, plus `local.yml`'s `vm_backup_extra_vmids`) and where it writes (`vm_backup_target`: the NAS's `homeserver-backup`, or `local.yml`'s `vm_backup_storage` without a NAS) |
| `group_vars/proxmox/tailscale.yml` | remote access: the routes from `local.yml`, the tag, the preferences kept with `tailscale set` (Tailscale's updater off), upgrades left to `proxmox_apt`, and what the guard protects (every address `local.yml` gives the NAS and any NFS server the host mounts, tcp/443 only) |

A new setting goes in one of these files, with a neutral default in the role and a line in the role's `meta/argument_specs.yml` and `README.md`, never as a literal in a task; then `make docs` brings the role's `REFERENCE.md` up to date.

**`roles/truenas`** runs on the controller (`ansible_connection: local`) and talks to the NAS's JSON-RPC 2.0 WebSocket API (`wss://<nas>/api/current`) with an API key, through custom modules in `roles/truenas/library/` and a shared client in `roles/truenas/module_utils/truenas_api.py`. The REST API is deprecated and gone in TrueNAS 26; SSH stays off on the NAS. Stages, each under its own tag: `truenas_network` (network settings, static address), `truenas_pools`, `truenas_system`, `truenas_datasets`, `truenas_snapshots` (periodic snapshot tasks, after the datasets they name), `truenas_nfs` (service settings, shares), `truenas_alerts` (outgoing mail and alert services), `truenas_services` (last, so NFS starts once its shares exist); validation and the read-only connection (`truenas_info`) run under every tag, and a stage whose variables are empty does nothing. Design facts that are easy to break:

- **Every change to the NAS goes through this role.** No UI clicks, ad-hoc API calls or SSH; a fresh install plus one run must rebuild it. Read-only API queries are fine.
- **TrueNAS rate-limits logins** to 20 per minute per client address, and every module run logs in once. Modules therefore take lists (all datasets, all services) rather than being looped over, and the client waits out the window if it is hit.
- **The static address uses TrueNAS's commit-and-check-in.** `truenas_interface` commits with a rollback timer, reconnects on the new address and checks in; if it cannot, the NAS reverts by itself. The play reaches the NAS on the static address first and falls back to `truenas_bootstrap_address`.
- **The system dataset is pinned before any pool import.** On a fresh install it reads as `boot-pool` but counts as unset, and importing a pool would move it onto that pool.
- **Pools are imported or created, never destroyed, wiped, exported or upgraded.** Creation needs `truenas_pool_allow_create` and blank disks (by serial), and is untested.
- **Modules return only the fields they manage.** `system.general.config` includes the UI certificate's private key; `tests/unit/test_truenas_client.py` checks that `truenas_config` never returns it, in check mode, applying, or failing.
- **The API key goes only to the NAS's own certificate.** Certificate validation is off (self-signed), so `truenas_api_cert_sha256` pins the certificate's SHA-256 (in `local.yml`); a server presenting anything else gets no login. Replacing the certificate means updating the pin.
- **An NFS share must name its hosts or networks.** NFS with `sec=sys` has no authentication.
- **A secret setting is compared, never printed.** `mail.config` returns the mail server's password, so `truenas_config` takes it in `secret_settings` (a `no_log` option): compared and sent like the other fields, so a rotated password reaches the NAS on the next run, and shown only as `<secret>` or `<secret, changed>`. The idempotence test rotates it and checks that neither password appears in any run's output.
- **Snapshots only where data cannot be re-created.** `persistent/proxmox/vm` keeps hourly snapshots for a day and daily for a week (it holds whole VM disks, whose scratch data longer-lived snapshots would pin). The daily task allows empty snapshots: it fires with an hourly one, and TrueNAS destroys a batch of snapshots that are all empty unless one of its tasks allows them, so an idle dataset would otherwise keep no daily snapshot at all. Never a snapshot task on the ephemeral pool.

**`roles/proxmox_apt`** runs first in `proxmox.yml`, over the same root SSH. A fresh Proxmox install ships with the enterprise repositories enabled and no subscription, so `apt-get update` fails with 401 until they are off and the no-subscription one is on, which used to be a manual step in the web UI's Updates → Repositories panel. The role writes each entry of `proxmox_apt_sources` as a deb822 `<name>.sources` file (the Debian release read from the host's `/etc/os-release`, so a reinstall on a newer Proxmox gets its own release), prepends `Enabled: false` to each existing file named in `proxmox_apt_disabled` without rewriting the rest (as the UI does; the line goes first because a trailing blank line would make a line at the end a stanza of its own), and with `proxmox_apt_upgrade` refreshes the package lists and runs `apt-get dist-upgrade` non-interactively, keeping configuration files changed on the host. This setup turns the upgrade on, so every `make proxmox` upgrades the host: one command rather than two, and an upgrade with nothing to do is quick. A dry run writes nothing and fetches nothing: it shows the file diffs and simulates the upgrade on the lists as last refreshed, which on a fresh install means no pending upgrade until the first real run. Every run then says whether the host needs a reboot, and never reboots it: when to take the host and its VMs down is decided by hand. A reboot is needed while Debian's flag for one, `/run/reboot-required`, exists, which every boot empties. The role writes it when the upgrade changes a kernel image package (`proxmox-kernel-<release>`, signed or not; `proxmox-kernel-helper` and the meta package share the prefix and boot nothing) or a package in `proxmox_apt_reboot_packages`, here dbus, both vendors' CPU microcode, which the kernel loads only at boot, and `pve-firmware`, which drivers load as they start; dbus's own package writes it too, and the role honours it whoever wrote it. It sees only what its own upgrade unpacked: a kernel installed by hand or from the web UI, or a boot that came up on an older kernel, goes unreported. Every microcode or firmware upgrade asks for a reboot, even one that brings this hardware nothing: when in doubt, reboot. The record is made in a block's `always`, so an upgrade that fails after unpacking still leaves it, and a dry run says the same from the simulated upgrade. The commands go through `command`, not the `apt` module, so the test's fake `apt-get` can stand in for them; it answers 401 to a refresh while an enterprise repository is enabled, so the role's order (files first, then the refresh) is what the test proves, and it can fail after unpacking, which proves the record survives a failed upgrade.

**`roles/proxmox_storage`** runs over root SSH with `pvesm`, not `community.proxmox.proxmox_storage` (which only creates storage and has no `format` option). It adds the layout's NFS storages with qcow2 (`homeserver-persistent`, `homeserver-ephemeral`, and one per project pool, today `claude-on-proxmox-ephemeral`), corrects drift in content, format and mount options, refuses a storage id that points elsewhere, an export that another id already mounts (one export, one id: what a renamed id leaves behind until the old one is removed by hand) and an id Proxmox would reject, and sets the node's start-on-boot delay so VMs wait for the NAS, then, with `proxmox_storage_startall_wait`, a drop-in for `pve-guests.service` (under `proxmox_storage_systemd_dir`, followed by `systemctl daemon-reload`) that holds the start at boot until each listed storage is active in `pvesm status`, for at most `proxmox_storage_startall_wait_timeout` seconds: Proxmox starts each guest once, and one whose disk is on a storage that is not active fails and is never tried again. This setup waits up to ten minutes for the NAS's storages that hold VM disks; without a NAS the drop-in is removed. Given `proxmox_storage_local`, a list of ids of storage the node already has (any type passes; here it is the installer's own), it also checks that each exists, is not disabled and holds `images`, which fails a dry run too, and creates or changes none of them; the refusal names the variable and lists the storage Proxmox has. Its input check gives each problem its own message, and refuses a string for that list, which argument validation lets through unchanged. Whether a storage is active on the node, for these ids and the NFS storages alike, is checked only on a real run, at the end, and the failure names the storage and whether it is restricted to other nodes or not activated.

**`roles/proxmox_backup`** runs last in `proxmox.yml`, over the same root SSH, with `pvesh` under `/cluster/backup` (no `community.proxmox` module manages backup jobs). It creates each job of `proxmox_backup_jobs` and corrects the settings it manages (schedule, storage, VMIDs in any order, mode, compression, prune settings, notes template, enabled), and never deletes a job. It refuses a job whose storage does not exist, is disabled or holds no backups, and a `dir` or `btrfs` storage without `is_mountpoint` (`off` counts as unset, as Proxmox reads it): with its USB disk unplugged, vzdump would fill the node's root filesystem, taking pmxcfs and every VM down. In check mode a storage listed in `proxmox_backup_pending_storages` (the NFS storages `proxmox_storage` adds on a real run) is reported as pending, so a dry run on a fresh host passes; its plan task counts as a change in a dry run when there is something to do. This setup has one job, `vm-nightly` at 02:00, kept seven days and four weeks, owned by no single project: the cluster's VMs and any `vm_backup_extra_vmids`, with or without a cluster. The notes template is Proxmox's own `{{guestname}}`, a string literal inside `group_vars/proxmox/backup.yml`'s expression, so Ansible never templates it; written as a plain value it would need `!unsafe`. Without a NAS and without `vm_backup_storage` there is no job, and a post-task of `proxmox.yml` (tagged `always`) says which VMs go unbacked. The fake's job shape comes from Proxmox's API schema, not a capture: the role reads the prune settings as text or as an object. Restoring is by hand, `scripts/runbooks/vm-restore.md`, which also has the isolated drill (`--unique`, link down). Its tests are marked `cluster`, run from a test playbook of their own (`tests/integration/proxmox_backup.yml`).

**`roles/proxmox_vm`** runs in `kubernetes.yml`'s first play, on the Proxmox host over root SSH, with `qm` and `pvesh`. Its tasks read the node; the `proxmox_vm_plan` filter (`roles/proxmox_vm/filter_plugins/proxmox_vm.py`, pure Python, unit-tested in `tests/unit/test_proxmox_vm_plan.py`) works out what to do, and the tasks run the commands it returns. It downloads the Talos ISO (the version and schematic in the file name; Proxmox checks it against `sha256`, the pin `kubernetes_iso_sha256`, which the role requires of every ISO, since the Image Factory publishes no checksum; the download task's own exit status is checked, since `pvesh` may exit 0 for a failed one), creates each missing VM with every option given, corrects the settings it manages (cores, memory, CPU, ballooning, start-on-boot, startup, watchdog, agent, tags, `hostpci*`, `ide2`, `boot`, which Proxmox edits when a drive is deleted), adds a configured disk a VM lacks, grows a disk configured larger, and starts a stopped VM. Proxmox writes settings back in its own forms (tags lower-cased and sorted, disks as volume ids with their size, property strings in any order, numbers as text or numbers), so each is compared normalised. It never moves, shrinks or detaches a disk, deletes a VM or an ISO, ejects the CD-ROM (a wiped node reaches maintenance mode only from it; the boot order puts the system disk first), or restarts a VM: settings that wait for a restart (on a running VM: cores, CPU, memory, ballooning, watchdog, agent, boot order, PCI devices) are reported from `.../pending` on every run until one. It refuses a VMID another VM or a container holds, **a missing VM whose VMID still has disks or backups on any storage** (files of no VMID, such as imports, aside; it is being rebuilt: restore it, `scripts/runbooks/vm-restore.md`, or set `proxmox_vm_ignore_existing_volumes`, with `make kubernetes ANSIBLE_ARGS='-e …'`, never make's own `-e`), a missing VM while an enabled storage is not active (its leftovers cannot be ruled out), a disk storage that does not exist or holds no images (pending in check mode when listed in `proxmox_vm_pending_storages`), and **the disk budget**: on thin LVM, ZFS, a directory or BTRFS, the provisioned sizes of every disk, other VMs' and containers' included (a container's volumes are listed as `rootdir`, not `images`, so the role lists every content type), plus what the run adds, never exceed the pool's `total` (never compared with what is free, which shrinks as data is written; `proxmox_vm_allow_overcommit` lifts it). A ZFS storage's `total` is its dataset's use plus the pool's free space, which the host's root filesystem shares on a ZFS install, and a directory's or BTRFS storage's is its filesystem's, so either shrinks as the host's own files grow: `proxmox_vm_host_headroom_gib` (16 here) keeps that much out of the budget. A disk already there whose serial or `backup` flag differs is set again on the same volume, and a slot is never filled while the VM keeps an `unusedN` volume (what a restore leaves of a disk its backup excluded): the role refuses and says how to attach or remove it. A storage in `proxmox_vm_pending_storages` that is missing is reported with `proxmox_vm_pending_storages_hint`, here "make proxmox adds it: run that first". NFS is not budgeted; the NAS's quota on `persistent/proxmox/vm` caps it. It warns when the VMs' memory would exceed the node's less 2 GiB, and reports each VM's MAC for checking against DHCP. `group_vars/proxmox/vms.yml` maps `kubernetes_nodes` onto VMs 300 and 301, the same two in both setups: the system disks (`serial=talos-system`) on the installer's storage, the worker's data disk (`talos-data`) on `homeserver-persistent` in qcow2 with a NAS and on the installer's storage without, its media disk (`talos-media`, `backup=0`) without a NAS, `i6300esb` watchdog, `virtio-scsi-pci`, the MAC from `kubernetes_node_macs`, and the tags `talos` and `k8s`. A built cluster moved to the other setup is refused before anything changes because the worker's data disk is on the other storage, which is why the worker always needs a data disk: `test_a_built_cluster_cannot_switch_setups` keeps that so. The backup covers both VMs in either setup, and README's "Switching setups" gives the migration by hand (`qm disk move`). `kubernetes.yml`'s first play also refuses a cluster when the inventory lacks the `kubernetes` group, which an inventory made before it does. The fake's `qm` and VM routes come from Proxmox's API documentation, not yet from a capture on the test host; its tests are marked `cluster`.

**`roles/talos`** runs in `kubernetes.yml`'s second play, on `homeserver-k8s` (`ansible_connection: local`, `group_vars/kubernetes/`), with `talosctl` and `kubectl` from `PATH`. Its parsing of their output is a filter plugin (`roles/talos/filter_plugins/talos.py`, unit-tested in `tests/unit/test_talos_filters.py`). It refuses a workstation `talosctl` whose minor release is not `talos_contract` (talosctl's defaults follow its own release), asks the Image Factory for each schematic's id (content-addressed, so safe in check mode; it answers 201) and refuses one other than `talos_schematic_pins`', gives every installer image the digest `talos_installer_digests` pins for its schematic and version (refusing a schematic in use at `talos_version` without one), and works in a scratch directory (secrets, a talosconfig for the run, rendered configurations; the patches reach talosctl inline) made with `check_mode: false` and `changed_when: false` and removed in a block's `always`. Drift on a configured node is found with `apply-config --dry-run` (`No changes.`), never printed since the diff can hold secrets, and applied with `--mode no-reboot`, **never rebooted**: Talos 1.14 applies any configuration at once in that mode (`auto` means the same now; ApplyConfiguration never refuses for a reboot), so nothing is staged, an apply that fails stops the run with Talos's error lines (the output itself stays `no_log`), and after a change to the control plane the run says to restart etcd (`talosctl service etcd restart`), which reads its settings only when it starts. `talos_keep_rendered` keeps the rendered files in `talos_config_dir/rendered/` to see a diff by hand. The secrets bundle is `talos_secrets_file`, `talos_config_dir/secrets.yaml` (`talosctl gen secrets`, kept in the owner's password manager, never in a repository): every entry point refuses it missing, readable by others than its owner (mode 0600 or 0400) or inside the repository, reads it with `slurp` under `no_log`, checks it by its text alone (a YAML parser's error could quote a line of it) and only ever writes it with `no_log`. `group_vars/kubernetes/talos.yml` holds the patches: the install disk and user volumes selected by the by-id link QEMU names after the disk's slot, `scsi-0QEMU_QEMU_HARDDISK_drive-scsiN` (`kubernetes_disk_slots` in `group_vars/all/kubernetes.yml`, which the VMs' layout reads too: Proxmox sets `device_id=drive-scsiN`, which udev prefers to the `serial=`, and `disk.serial` is empty on virtio-scsi, both seen on the home host), a 2-minute `WatchdogTimerConfig`, the control plane's metrics bound to `0.0.0.0` (set now, since etcd's needs a reboot), and nothing that lets the control plane run apps: it keeps Talos's taint in both setups. `make lint-talos` renders every setup through the role's own `render.yml` (`tests/talos_validate.yml`) and runs `talosctl validate --mode metal --strict` on each, then checks that each one's UnattendedInstallConfig names its installer image and leaves reboot on, which the install wait counts on; CI's kubernetes job downloads talosctl by version and checksum. The tests run with `HOME` set to their own directory.

**`roles/flux_bootstrap`** runs after `talos` in the same play, with `kubectl --kubeconfig ~/.talos/homeserver/kubeconfig`. **`roles/proxmox_tailscale`** runs second in `proxmox.yml`, over the same root SSH, and only when `local.yml` gives `tailscale_advertise_routes` (empty, it runs no command). It makes the Proxmox host the LAN's Tailscale subnet router, so every VM on its bridge, the NAS and the router answer from the tailnet without Tailscale of their own. It comes after `proxmox_apt` (a fresh host installs nothing until the enterprise repositories are off) and before `proxmox_storage` (whose refusals must not hold remote access back).
- **Install and upgrade.** It downloads Tailscale's signing key once, writes `tailscale.sources` (deb822), and installs `tailscale`, `tailscale-archive-keyring` (which owns the key from then on) and `nftables` with `apt-get install`, and leaves upgrades to `proxmox_apt`'s `dist-upgrade`, earlier in the same run (`proxmox_tailscale_upgrade` is off, so one switch covers every upgrade). Tailscale's own updater is off (`auto-update: false`): on Debian it runs apt on its own schedule and needs a `tailscale.list`.
- **The guard, then forwarding.** It loads a guard (below), then writes `/etc/sysctl.d/99-tailscale.conf` (`net.ipv4.ip_forward = 1` only; IPv6 forwarding would stop `vmbr0` accepting router advertisements, and IPv6 routes are refused). Forwarding is host-wide: a second interface with an address (a VLAN, a storage network) would be routed to and from the LAN too, which the guard does not filter.
- **Login.** tailscaled is enabled and started if it is down (stopped by hand, or never started at boot because the guard failed), after the guard. Before any login, a tailscaled without `tailscale0` (started with `--tun` naming another interface, or with userspace networking) is refused, since the guard filters by that name. A logged-out node is logged in once with `tailscale up --auth-key=file:<tempfile>` (`no_log`, removed in an `always`), tagged `tag:homeserver`, with every preference `up` takes, so the node never runs with Tailscale's defaults. A node stopped by hand is brought back up without a key.
- **Preferences.** It compares the routes and `proxmox_tailscale_settings` with `tailscale get --json`, which is keyed by `tailscale set`'s own flag names (accept-routes, accept-dns, ssh and auto-update all off here), and runs one `tailscale set` when they differ.
- **Never.** It never logs out, retags or restarts tailscaled, and reports instead what only the admin console can fix: an unapproved route, the wrong tags, a key that expires, a Serve configuration, Tailscale's health warnings.

**The guard** is the nftables table `inet tailnet_guard` (`/etc/nftables.d/tailnet-guard.nft`), loaded by `tailnet-guard.service` before `network-pre.target`.
- **What it drops.** Its forward chain (priority `filter - 10`; a drop in any nftables base chain is final, whatever iptables, Tailscale or Proxmox accept) drops three things: everything from `tailscale0` to `proxmox_tailscale_guard_hosts` except `proxmox_tailscale_guard_allow` (here both NAS addresses, since NFS answers on every address the NAS has, and with only the bootstrap address the shares are exported while `proxmox_storage` refuses to mount them), everything from `tailscale0` outside the advertised prefixes, and new connections from the LAN into the tailnet.
- **Fail-closed.** A drop-in (`tailscaled.service.d/10-tailnet-guard.conf`) makes tailscaled `Requires=` and `After=` the guard. That covers starting: a table removed by hand while both run leaves tailscaled unguarded until the next `make proxmox`.
- **Reloads only.** The role checks each file with `nft -c` before installing it and applies changes with `systemctl reload-or-restart`: a reload when the unit is active. A plain restart would restart tailscaled through `Requires=`, and the fake refuses one. The unit has no `ExecStop`, so stopping it never removes the table.
- **Debian's nftables.service.** The role refuses to run while it is enabled or running: its `/etc/nftables.conf` begins with `flush ruleset`, and its stop command flushes too. The guard's unit has `Conflicts=` and an ordering on it, so starting it later stops the guard, and tailscaled through `Requires=`, before the flush.

The tailnet's policy, split DNS and the auth key are set by hand in Tailscale's admin console (`scripts/runbooks/tailscale.md`), the policy before the first advertisement, since a new tailnet allows everything. The role's tests have fakes of their own (`tests/integration/fake_tailscale.py` behind `fake_tailscale_bin/`, a test playbook `proxmox_tailscale.yml` and `test_tailscale.py`), written from Tailscale 1.104's flags and `get --json` as a 1.102 client prints it, not yet captured from the host.

**Without a NAS.** `nas_present` (`group_vars/all/storage.yml`) is true when `local.yml` gives the NAS either address, `truenas_static_address` or `truenas_bootstrap_address`. The addresses are the only switch: `nas_present` is never set, and the guard below refuses one given with `-e`, which would be a string that counts as true even when it says `false`. The `truenas` host stays in the inventory, and `truenas.yml` carries two `always`-tagged pre-tasks that, when it is false, say why and `end_host` before the role runs (the `always` tag is required, since `meta` tasks honour tags, and the `debug` is what gives the host a recap line). A misspelt address would look exactly like no NAS, so both `truenas.yml` and `proxmox.yml` first assert that `nas_section_error` (`storage.yml`) is empty: it names the TrueNAS settings `local.yml` still sets (certificate pin, gateway, name servers, pool disks, pool names, the alert mail's settings) when neither address is given, and with a NAS it refuses alert mail TrueNAS would refuse (a mail server without a sender address, an alert address without a mail server) and `vm_backup_storage`, which only a setup without a NAS reads, while a section deleted or left entirely blank stays Proxmox-only. `group_vars/proxmox/storage.yml` then derives an empty NFS list, `proxmox_storage_local` set to the installer's storage (with a NAS too when there is a cluster, whose system disks go there), a null boot delay and no wait at boot; `vm_storage` holds the ephemeral class alone, on the installer's storage, `local-lvm` unless `local.yml` sets `proxmox_local_vm_storage` (`local-zfs` on a ZFS install). There is no persistent class without a NAS, and no project pools. `storage.yml` only reads that variable: a `group_vars/all/` directory is read alphabetically and the last file wins, so a value set in `storage.yml` would override `local.yml`'s. The vault is still decrypted on every run and `.vault_pass` must exist, so a user without a NAS runs `make vault-init`. It creates `.vault_pass` with mode 0600 if there is none, encrypts an empty mapping over `group_vars/all/vault.yml` (`ansible-vault create` refuses an existing path, hence `encrypt`), and marks the file `skip-worktree` so the user's vault never reaches a commit; a vault that already opens with `.vault_pass` is left alone, and one that does not open but is not the tracked vault either (git's index blob) is refused, since it may be the user's with its password lost. That vault is the user's alone and exists nowhere else, so README and REBUILD tell the user to keep it in a password manager, and README's way past the `git pull` that refuses when the tracked vault changes sets the user's vault aside and puts it back, never making a new one; a cluster's secrets bundle is never in it (`roles/talos` above). `tests/policy/test_roles.py` runs the argument-spec pass in both modes and `tests/integration` runs the Proxmox role without a NAS; the mode was also run against a fresh Proxmox VE 9.2.2 install, which is where the fake's `digest`, `shared` and varying `content` order come from. Storage ids say who owns a storage and what it is for, never the backend; they were `truenas-*` until 2026-10-08. The role never removes a storage and refuses an export that another id already mounts, so renaming an id means removing the old one by hand first (`pvesm remove`), which the home host still needs for its two old ids: until then every run, dry or real, refuses and names them.

**The cluster switch.** `kubernetes_present` (`group_vars/all/kubernetes.yml`) is true when `local.yml` gives `kubernetes_node_addresses`; like `nas_present` it is worked out, never set. In both setups the cluster is a control plane, which runs Talos, etcd and the API alone, and a worker that runs every app; only where the worker's disks live depends on the NAS, and without one `local.yml` must give the worker's size (`kubernetes_node_sizes`), since the defaults fit the home host. Until 2026-10-19 a setup without a NAS had a single schedulable control plane instead; one shape keeps the two setups from drifting apart. Every playbook first asserts that `kubernetes_settings_error` is empty, right after `nas_section_error`, because the Proxmox play reads the switch too: it refuses `kubernetes_present` given with `-e`, the section's other settings without node addresses (a misspelt address), node addresses other than the two nodes', a node without a locally administered lower-case MAC (`kubernetes_node_macs`, chosen by the owner and reserved in DHCP before the first run; the example's `<mac>` is refused on purpose), no `flux_sync_url` (it has no default: Flux applies that repository with cluster-admin rights), a `flux_sync_ref` other than `refs/heads/main` without `flux_sync_ref_unprotected: true` (whoever can push to the synced branch owns the cluster, and only `main` is protected; `scripts/runbooks/talos.md`), `vault_talos_secrets` in the vault in any setup, a worker without a data disk, a control plane with a data or media disk or under 2 GiB of memory, a system disk under 10 GiB, with a NAS a worker data disk above three quarters of `vm_storage_persistent_quota_gib`, a worker media disk or `kubernetes_media_on_data_volume` (the media live on the NAS), and without a NAS a worker without every size, or without a media disk unless `kubernetes_media_on_data_volume` is set, or with both. `kubernetes_iso_storage` lives in `group_vars/all/kubernetes.yml`, not with the VMs, so `local.yml` can name `local-btrfs` on a BTRFS install. A host sees only its own groups' files, so whatever two plays read lives in `group_vars/all/`. gitleaks flags a MAC written out in any tracked file, so the tests build theirs at run time. `tests/policy/test_roles.py` runs the argument-spec pass in the four setups the two switches make, and checks each refusal's message.

Storage design: the NAS's two pools are named by class, never by hardware (`nas_pools` in `group_vars/all/storage.yml`; `local.yml` can name them otherwise with `truenas_pool_persistent` and `truenas_pool_ephemeral`): `persistent` is redundant, for data that cannot be re-created, and `ephemeral` has no redundancy, for data that can. Persistent VMs on `persistent/proxmox/vm` (RAIDZ1, `sync=standard`, a quota of `vm_storage_persistent_quota_gib`, 1 TiB, which counts its snapshots, so a disk that fills never fills the pool under the backups), ephemeral VMs on `ephemeral/proxmox/vm` (single disk, `sync=disabled`, 1 TiB quota on `ephemeral/proxmox` because the pool also holds the media dataset, and never a snapshot task). `vm_storage_ephemeral_reservation` puts a ZFS `reservation` on `ephemeral/proxmox`, which counts its descendants, so the media apps can never fill the pool under the VMs; a `refreservation` would not, since it excludes descendants. Both use 64K records and POSIX ACLs. A project that creates VMs on the host gets a pool of its own: an entry in `vm_storage_consumers` makes a dataset under `ephemeral/proxmox` with the ephemeral class's properties and an optional quota, exported and mounted under the project's id. The project is told that id and nothing else, and its token is granted `/storage/<id>` by hand with its own README's line; this repo manages no Proxmox users or ACLs, and never grants `Datastore.Allocate`, which Proxmox checks on `/storage` for creating, changing and removing any storage alike. Proxmox has no host-wide default storage, so a project always names its storage; its default, `local-lvm`, is right without a NAS. These two projects stay independent: nothing here reads the other's configuration, and nothing there reads this repo's.

### Workloads (`k8s/`)

**Nothing in this repo applies the manifests.** The deleted `k8s` role ran one `kubectl apply -f <dir>` per service directory and then a single `kubectl wait` for every pod in every namespace, in this order: `00-namespaces`, `homeassistant`, `prometheus`, `grafana`, `node-exporter`, `dashdot`, `homepage`, `homarr`, `dashy`, `jellyfin`, `sonarr`, `radarr`, `prowlarr`, `jellyseerr`, `nextcloud`, `filebrowser`. `frigate`, `photoprism`, `sabnzbd` and `kube-state-metrics` were never wired in, so nothing has ever applied them. On the new cluster Flux applies them (`roles/flux_bootstrap`): it syncs `k8s/clusters/nas` or `k8s/clusters/local`, which are empty until the manifests are wired in.

**Shared namespaces are applied first.** `k8s/00-namespaces/` holds namespaces used by more than one service directory — currently only `monitoring` (prometheus, grafana, dashdot) — so it has to be applied before any service directory. Each service directory otherwise owns its own `0-namespace.yaml`. Do not re-add a `monitoring` declaration to an individual directory: duplicate Namespace objects are idempotent under `kubectl apply` but make `kubectl kustomize` fail outright, and under Flux would let pruning one Kustomization cascade-delete the namespace.

### Storage model

Two patterns coexist; check which one a service uses before touching its volumes.

**A. hostPath under `/opt` (most services).** The Deployment mounts `/opt/<service>/...` directly — sonarr, radarr, prowlarr, sabnzbd, jellyseerr, homarr, dashy, frigate, filebrowser. These directories used to be created by the deleted host role, owned by the login user with mode `0755`; **nothing creates them now**. The LinuxServer.io containers run with `PUID`/`PGID` `1000` and `TZ=America/Los_Angeles`, and that uid matching the directories' owner was the whole reason the hostPath mounts were writable — a hostPath nobody pre-creates is made root-owned by kubelet/containerd, and the container fails to write.

File-shaped hostPaths need care whoever creates the parent: `/opt/frigate/config.yml` has no `type:`, so it is created as a *directory*, which breaks that container. `/opt/dashy/config.yml` and `/opt/filebrowser/filebrowser.db` are `FileOrCreate`, which creates an empty root-owned file only when the parent directory already exists — it never creates parents, so with nothing creating `/opt/<service>` those pods stay in `ContainerCreating`.

`sonarr`, `radarr`, and `sabnzbd` all mount the same `/opt/media/data` at `/data` — the single-mount layout that keeps hardlinks/atomic moves working. Do not split it into per-app paths.

**This whole pattern is a Pod Security Admission problem, not just a Talos-persistence one.** `hostPath` is a `baseline` control, so every one of these workloads violates `baseline` — 12 workloads in 12 namespaces, with 24 hostPath volumes between them, and 8 of the namespaces carry no exemption label. `tests/policy/test_k8s.py` lists every hostPath volume, in pods and in PersistentVolumes, so a new one fails and a converted one must be struck off the list. Two refinements: a `hostPath` inside a *PersistentVolume* consumed via PVC is **not** a violation (PSA reads pod specs only, so grafana's `/opt/grafana` PV passes), and `type: File`/`FileOrCreate` does **not** exempt one. The fix is the hostPath→PVC conversion, not more exemption labels.

**B. NFS PV/PVC (stateful services).** homeassistant, jellyfin, nextcloud, photoprism use `storageClassName: nfs`, `ReadWriteMany`, `persistentVolumeReclaimPolicy: Retain`, and PVCs bound by explicit `volumeName`. There is no NFS provisioner — PVs are hand-written. Grafana and Prometheus are a third case: PV/PVC with `storageClassName: manual` over a `hostPath` (`/opt/grafana`, `/opt/prometheus`).

NFS endpoints are inconsistent across manifests: `truenas.local` (hass, nextcloud-db, photoprism-db) vs a hard-coded IP address (jellyfin, nextcloud-server, photoprism-server). Export roots differ too (`/mnt/nvme/store/...` vs `/mnt/ephemeral/...`), and the NAS has since been reinstalled: it has no `nvme` pool, and `roles/truenas` exports only the two Proxmox VM datasets, to the Proxmox host alone. Confirm the live NAS address and export before adding a PV rather than copying a neighbour.

### Networking — three overlapping exposure mechanisms

Every service tends to carry all of these at once:

1. **NodePort** — most `service.yaml` files are `type: NodePort` with a hand-assigned port, in a registry that only exists implicitly (the exceptions are `homeassistant`, `nextcloud/service-db`, and both photoprism services, which are `ClusterIP`): `30000` homepage, `30001` prometheus, `30004` sonarr, `30005` grafana, `30006-30009` jellyfin, `30010` radarr, `30011` prowlarr, `30012` node-exporter, `30014` nextcloud, `30016` dashdot, `30017` jellyseerr, `30018` homarr, `30019` dashy, `30020` filebrowser, `30021` sabnzbd, `30022` frigate. Check this list before picking a new one — and note that Kubernetes assigns eight more ports in this range itself, so the registry is incomplete by construction: `nextcloud/service-server.yaml`'s port 443 and frigate's 8554 and 8555 (TCP and UDP) declare no `nodePort:`, and jellyfin's two LoadBalancer Services allocate node ports for their four ports by default. `tests/policy/test_k8s.py` requires every other port to name a `nodePort` no other Service uses, and lists those eight; the list may only shrink.
2. **Ingress** — hosts are `<service>.homeserver.internal`. Only `k8s/homeassistant/ingress.yaml:8` sets `ingressClassName: traefik`; the rest are class-less and land on Traefik only because k3s marks its IngressClass default. Their `nginx.ingress.kubernetes.io/*` annotations (notably `rewrite-target`) are inert under Traefik. DNS for `*.homeserver.internal` is not managed in this repo.
3. **LoadBalancer Services** — only `k8s/jellyfin/ingress.yaml` still has them (`jellyfin-lb-udp`/`-tcp`, for DLNA 1900/udp and discovery 7359/udp, which must bypass an HTTP ingress). Nothing in this repo installs MetalLB. Under k3s that went unnoticed, because **k3s ships ServiceLB (klipper-lb)**, which reconciles these via hostPorts rather than leaving them `<pending>`. Talos has no ServiceLB equivalent, so a LoadBalancer implementation must be installed there or they will hang.

**Historical note — the `ingress`-namespace landmine is gone.** 16 `ingress.yaml` files used to declare a `type: LoadBalancer` Service in `namespace: ingress` (a namespace no manifest created) selecting `name: nginx-ingress-microk8s`, a controller pod that does not exist under k3s. They were deleted; `k8s/photoprism/ingress.yaml`, which was an unedited copy of radarr's, was rewritten. If you see that shape in an old branch or a stale server-side checkout, it is dead weight, not configuration.

Naming: `ingress.yaml` now contains an Ingress (all 18 of them), plus jellyfin's two `*-lb-*` Services as the sole exception. `service.yaml` is the NodePort. A `-lb` suffix means a LoadBalancer Service.

### Monitoring

`prometheus` (namespace `monitoring`) scrapes via Kubernetes SD — `kubernetes-apiservers`, `-nodes`, `-pods`, `-cadvisor`, `-service-endpoints`, plus a static `kube-state-metrics.kube-system.svc.cluster.local:8080` and an `alertmanager.monitoring.svc:9093` target that nothing deploys. `node-exporter` is a DaemonSet in `kube-system` (Talos exempts that namespace from PSA by default); `grafana` and `dashdot` are in `monitoring`.

**None of it has ever run**, so treat it as untested. The defects that would have stopped it collecting anything were fixed in the manifests: Prometheus has a ServiceAccount and binding in `monitoring`, Grafana's datasource uses in-cluster DNS, the TSDB sits on a 20Gi PV with 15d/15GB retention, and `kube-state-metrics` (never deployed by the old role) has a real ClusterRoleBinding. Still open: the `kubernetes-pods` job matches nothing because no pod carries `prometheus.io/scrape`; the alerting rules are a placeholder that always fires at the nonexistent Alertmanager (K8S-26); Prometheus's Deployment has no `strategy: Recreate` despite its hostPath PV; and Prometheus (uid 1000) and Grafana (uid 472) both run as non-root against hostPath directories that nothing creates or chowns, since `fsGroup` is not applied to hostPath volumes. `kube-prometheus-stack` would replace the whole tree.

## Landmines

`docs/ISSUES.md` (gitignored, so absent from a fresh clone) holds the full audit behind this section:
46 findings with file/line references, fix plans, verification steps, and a suggested order of work.
`docs/MIGRATION-TRIAGE.md` says which survive the Proxmox/Talos move; `docs/reviews/` holds two review
passes over the change stack. Read them before starting any repair — and note that because `docs/` is
gitignored, none of it reaches a clone, so the findings referenced below may have no local backing.

- **There is no TLS anywhere.** Every Ingress is plain HTTP. The old `k8s/cert-manager/` (v1.4.0, staging ACME, microk8s solver class, `commonName: homeserver.homes`) was deleted as unsalvageable — that is not a decision against TLS, which needs a real domain and a DNS-01 solver because `*.homeserver.internal` cannot be validated by public ACME.
- `k8s/homeassistant/claim1-persistentvolumeclaim.yaml` and `docker-default-networkpolicy.yaml` are intentionally comment-only tombstones for kompose artifacts. Don't "restore" them.
- `privileged: true` remains on 4 workloads: `jellyfin` and `frigate` (`/dev/dri` transcoding), `dashdot` (host inspection), `node-exporter` (host metrics). Their namespaces carry `pod-security.kubernetes.io/enforce: privileged`, except node-exporter which relies on `kube-system` being exempt. `homeassistant` keeps `NET_ADMIN`/`NET_RAW`/`NET_BROADCAST` without full privilege — still above `baseline`, so its namespace is labelled too. Note it has **no `hostNetwork: true` anywhere**, so the mDNS/SSDP discovery those capabilities exist for cannot actually work. kube-linter flags all of these; the four outside the monitoring tree it skips (jellyfin, frigate, dashdot, homeassistant) carry `ignore-check.kube-linter.io/<check>` annotations saying why.
- `nextcloud` and `photoprism` each split app and database across a Deployment *and* a StatefulSet, in opposite directions: nextcloud is Deployment `nextcloud` + StatefulSet `nextcloud-db`, photoprism is StatefulSet `photoprism` + Deployment `photoprism-mariadb`. Neither pair is a duplicate — check the object name before assuming which file is the app.
- **Flux holds cluster-admin, so merge rights on `main` are the cluster's admin boundary.** kustomize-controller and helm-controller apply whatever the synced branch holds, with cluster-admin. Whoever can merge to `main` (the "Protect main" ruleset: a pull request and `ci-success` required, nobody bypassing) controls the cluster, which is why `flux_sync_url` has no default and a fork syncs its own repository; another branch is unprotected, so syncing one takes `flux_sync_ref_unprotected: true` and its source suspended while it is not being tested (`scripts/runbooks/talos.md`). Read the live ruleset (`gh api repos/kawadeomkar/homeserver/rulesets/24555579`) before relying on it. No other cluster-admin principal runs in the cluster: `portainer` used to bind `cluster-admin` to its pod's ServiceAccount on three NodePorts plus an Ingress, and was deleted rather than scoped; use `k9s` or Headlamp from a workstation instead.
- **No plaintext `Secret` manifest may be committed.** Every Kubernetes Secret is a `k8s/**/*.sops.yaml` encrypted with SOPS for the cluster's age key (`.sops.yaml`: values only, `data` and `stringData`), which Flux decrypts with the `flux-system/sops-age` Secret `roles/flux_bootstrap` keeps; `k8s/README-secrets.md` says how to make one without the plaintext touching the disk. `.gitignore` blocks `k8s/**/*secret*.yaml` in both letter cases, with negations for the safe-by-construction kinds (`*.sops.yaml`, `*.example.yaml`, `*.template.yaml`, `externalsecret*.yaml`, `secretstore*.yaml`). gitleaks's `k8s-plaintext-secret` rule (YAML and JSON under `k8s/`) allows every `*.sops.yaml`, so `scripts/ci/check-sops-staged.sh` refuses one that was never encrypted (a document without `sops:`, or a value under `data` or `stringData` that is not `ENC[`): on the staged files in the pre-commit hook (`make secrets-staged`), and on every version in the pushed commits through `check-range.sh` (pre-push and CI). `.sops.yaml` names the owner's age key as the recipient; a fork puts its own there. The one tracked Secret, `k8s/homepage/secret.yaml`, is a `kubernetes.io/service-account-token` stub with no data: Kubernetes fills in the token, so it holds nothing secret. **This repo is public** — that is also why `.claude/` and `inventory` are ignored.
- **The Tailscale subnet router masquerades every tailnet client to the Proxmox host's address**, which is exactly the address the NAS exports VM disks and backups to, with root kept as root. Two controls keep tailnet clients to the NAS's web UI, each enough alone:
  - the tailnet policy's grants, kept by hand in the admin console (`scripts/runbooks/tailscale.md`);
  - the role's fail-closed nftables guard.

  Both are allow-lists, because the NAS's mountd, statd and lock manager use random ports. Any proxy on the host itself (Tailscale Serve with a non-local target, `ssh -L`, SDN Simple-zone SNAT) connects from the trusted address unseen by the guard, and so does tailscaled itself with the debug setting `TS_DEBUG_NETSTACK_SUBNETS=1`. Reload `tailnet-guard.service`; never restart it, which restarts Tailscale.
- **Two secret systems, split by layer:** Ansible Vault (`group_vars/all/vault.yml`) for host/playbook variables, and SOPS+age for Kubernetes Secrets (`.sops.yaml`, the key and the procedure in `k8s/README-secrets.md`). Do not put k8s Secrets in `vault.yml`.
- **The nodes' firewall drops what no rule lets in, so a new port on a node needs a rule.** Talos's ingress firewall (`group_vars/kubernetes/talos.yml`: `NetworkDefaultActionConfig` blocks, each `NetworkRuleConfig` lets a port in) answers the LAN on the Talos API (50000) and, on the control plane, the Kubernetes API (6443), both behind client certificates; the rest only the nodes: etcd (the control plane alone), trustd, the kubelet, Flannel's VXLAN, MetalLB's memberlist, and, to the pod network too (talosctl's default, which `roles/talos` asks talosctl for as it renders, `talos_pod_subnets`, so that no private range is written in the repo; `make lint-talos` checks that each rendered kubelet rule names it), the kubelet and the metrics Prometheus scrapes on the nodes. Everything else to a node is dropped, kube-proxy's health checks and the node port of Traefik's Service among them, while Talos always lets in established connections, ICMP, pod-to-pod and pod-to-service traffic and pods' DNS queries, and the firewall never sees what kube-proxy forwards to pods, the load balancers' addresses included. A hostNetwork pod's new port, or a new scrape target on a node, times out until a rule names it. Try a changed rule first with `talosctl apply-config --mode try` on the rendered configuration (`talos_keep_rendered`), which reverts by itself: a rule that closes 50000 locks the role out of the node, leaving only its console in Proxmox and a reinstall.
- `nextcloud` and `photoprism` cannot currently be deployed: their Secrets no longer exist in-tree.

## Conventions

- **Manifest layout**: one directory per service, applied as a unit. `0-namespace.yaml` (the `0-` prefix makes the Namespace sort first for `kubectl apply -f <dir>`), then `deployment.yaml`, `service.yaml`, `ingress.yaml`, and PV/PVC files. One namespace per service, named after the directory. The exception is `monitoring`, shared by prometheus/grafana/dashdot and therefore owned by `k8s/00-namespaces/monitoring.yaml` instead.
- **Deployments** use `strategy: {type: Recreate}` (12 of 18 — hostPath/RWX volumes cannot tolerate two pods holding the same files), `replicas: 1`, and `app: <name>` labels/selectors.
- **Adding a service**: create the dir + its own `0-namespace.yaml` → pick an unused NodePort → write a PV/PVC for its storage rather than a new hostPath (see the storage model) → write an Ingress and skip LoadBalancer Services unless you genuinely need non-HTTP ports → if the pod needs `privileged`, `hostPath`, `hostNetwork` or added capabilities, label the namespace `pod-security.kubernetes.io/enforce: privileged` and say why in a comment, annotate the workload for each kube-linter check it fails (`ignore-check.kube-linter.io/<check>: "<why>"`), and add the namespace to `PRIVILEGED_NAMESPACES` in `tests/policy/test_k8s.py` → pin the image to an immutable tag (see below).
- **Roles** live in `./roles` beside the playbooks at the repo root, variables prefixed with the role name (ansible-lint enforces it). `ansible.cfg` deliberately sets no `roles_path`: roles beside a playbook are found by default, while `ansible-galaxy install` then defaults to `~/.ansible/roles`, which keeps third-party code out of this public repo. No role depends on a Galaxy collection. Task names in imported task files carry a `<file> | ` prefix (ansible-lint's `name[prefix]`). Every mutating step must be skipped in check mode and report what it would do, and a second run must report no changes. `tests/integration` checks every role against stateful fakes (`fake_truenas.py`, a TLS JSON-RPC server; `fake_pve.py` behind `fake_pve_bin/`, with `apt-get` reading the scratch repository directory the test passes as `proxmox_apt_sources_dir`), running each role with this repo's configuration: a dry run, an apply, a second apply, a dry run, then drift corrected once. A new API method or command needs a matching fake, or the test fails on purpose. The fakes always answer, so `tests/unit/test_truenas_client.py` covers in process, with a scripted socket and a clock that never waits, what they never do: TrueNAS refusing a login or a call, rate-limiting logins, dropping the connection, failing or never finishing a job, and refusing an interface commit, which must discard the saved change, or never seeing the check-in, after which TrueNAS rolls the address back by itself. The fakes cannot prove the real machines behave the same, so still run check mode against the real machine first.
- **No address in any tracked file.** IP addresses, and anything else that identifies this network, are never written in a task, a role default, a template or an example — tasks reference a variable, and the real value lives only in the gitignored `group_vars/all/local.yml`. `group_vars/all/local.yml.example` is its committed counterpart and uses RFC 5737 placeholders (`192.0.2.x`). Adding such a variable means adding it to both files. `.gitleaks.toml` writes the rule down for gitleaks, on top of its default secret rules: private, CGNAT and link-local IPv4 anywhere, and a private network written in part (its first three numbers, then `.x`, `.*` or a `/prefix`); any IPv4 in code, tests, manifests, scripts, workflows, `host_vars/` and Markdown anywhere (RFC 5737, loopback and `0.0.0.0` excepted); private IPv6; MAC addresses, with colons, dashes, or dots between groups of four; a disk's `/dev/disk/by-id/` name, which carries its model and serial, and WWNs (QEMU's virtual disks excepted); tailnet names; plaintext `Secret` manifests under `k8s/`; and, by path alone, the files that are never committed (vault password files, `local.yml`, a root `inventory`, `MACHINES*`, `talosconfig` and `kubeconfig` with any suffix, `*.kubeconfig`, age keys, Talos's generated `secrets.yaml`, `controlplane.yaml` and `worker.yaml`, run logs). `tests/policy/test_gitleaks_rules.py` proves each rule on generated fixtures, including what must not match (RFC 5737, loopback, image tags, version strings, QEMU's disk names, the certificate-pin placeholder). CI's `leaks` job scans the commits each change adds with these rules, so the 16 address literals in 7 `k8s/` files, which predate them (K8S-9), only fail a change that touches their lines.
- **Variables**: environment-specific values go in `local.yml` as above. Ansible secrets go in `group_vars/all/vault.yml` under a `vault_` prefix and are exposed by indirection from a plain variable (the old example was `discord_token: "{{ vault_discord_token }}"`). Kubernetes Secrets do not go there — see the Landmines note above.
- **Image tags are pinned, and the pin must be immutable.** LinuxServer.io re-points its plain `x.y.z` tags at every build revision, so those images use the `x.y.z-lsNNN` form (`linuxserver/sonarr:4.0.19.2979-ls320`), which `tests/policy/test_k8s.py` checks. Do not add `imagePullPolicy: Always` — on a pinned tag it is redundant, and on a mutable one it is what silently defeats the pin. kube-linter rejects it, and any image without a tag or tagged `latest`. There is no Renovate, so bumps are manual.
- **Resource requests on every workload** (kube-linter requires CPU and memory requests outside the monitoring tree), with limits only where a runaway can starve the node (nextcloud, jellyfin, frigate, photoprism, both MariaDBs, prometheus). All values are un-measured guesses — nothing has ever run. Aggregate: ~3.3 vCPU / ~9.6 GiB of requests, so a node needs ~4 vCPU and ~11 GiB before system overhead.
- `inventory`, `.claude/` and `docs/` are gitignored because **this repo is public** — they would otherwise publish host addresses, and `docs/MACHINES.md` also lists MAC addresses and drive serials. A fresh clone recreates `inventory` from the committed, address-free `inventory.example` (`make init` copies it).
- YAML style comes from `.yamlfmt` (basic, `---` document start, line breaks retained). `.yamllint` (160-column lines, run with `--strict`) and `.ansible-lint` (production profile, with `strict`, so its warnings fail too) both skip `k8s/`, which `make lint-k8s` covers with kubeconform and kube-linter. ansible-lint warns that it cannot import the custom modules' `module_utils`; that warning is expected. `make lint` runs both, plus `poetry check --lock --strict`, ruff (below), `ansible-doc` on every custom module (ansible-lint does not check `DOCUMENTATION`; the options every TrueNAS module shares are documented once, in the doc fragment `roles/truenas/doc_fragments/truenas_api.py`, which `ansible.cfg` points `ansible-doc` at), check-jsonschema on `dependabot.yml` and the workflows (SchemaStore's schemas, bundled), the role references (`make lint-docs`, below), and the unit and policy tests. `tests/policy` checks the repo's own rules: the lock matches `pyproject.toml` and hashes every package, every tracked vault file is encrypted, the ruleset body requires the workflow's gate job, and the roles keep their conventions (`test_roles.py`): each role default matches its argument-spec entry, each module's documentation matches its argument spec and documents its check-mode, diff-mode and platform support (`attributes`), check mode as its AnsibleModule declares it, the tracked configuration passes every role's argument specs and input checks, with `local.yml.example` and with the `local.yml` of a setup without a NAS, while both playbooks refuse NAS settings that come without an address, tasks pass only options the custom modules accept, and every option whose name looks like a secret (ansible-test's `no-log-needed` pattern) is `no_log`, bar a short list of named exceptions. The manifests keep theirs where kube-linter cannot check them (`test_k8s.py`): every node port is named and unique, each namespace is declared once by its owner and every namespaced object names one, the privileged namespaces and the hostPath volumes match lists in the test, only those namespaces and `kube-system` hold pods that `baseline` rejects for privilege, every Secret is SOPS-encrypted, and LinuxServer.io tags are immutable.
- **Python** is formatted and linted by ruff, configured in `ruff.toml`: 120 columns, Python 3.12, and modules exempt from `E402`, since their imports follow their documentation strings. `ruff format` formats; `make lint-python` checks both. The commit that first formatted everything is listed in `.git-blame-ignore-revs`, which GitHub reads and `make init` points `git blame` at; list any later reformatting commit there too. `make test` also reports the modules' coverage (`.coveragerc`): a report, not a gate, since it sees only the in-process tests and not the modules the idempotence tests run inside ansible-playbook.
- **Role references** (`roles/<role>/REFERENCE.md`) are docsible's pages, written whole by `make docs` from the role as it is: `meta/main.yml`, `meta/argument_specs.yml`, the defaults and vars as tables linked to their lines, and each tasks file as a table and a Mermaid graph. Never edit one by hand, and never give docsible a template or its comment annotations: a page says what the role says. A role's `README.md` stays its own, written by hand, and links to its page; `.gitattributes` marks the pages generated, so a pull request's diff folds them. `make lint-docs` (in `make linters`, so CI) generates every page again from a copy of `roles/` in `.cache/docsible` and fails on a difference, a role without a page, and any docsible output but its "Documentation generated at" line: docsible reports a file it cannot read (in 0.8.0, one with an `!unsafe` tag), leaves it out and exits 0. The Makefile says why each flag is set. Links are relative, without `--repository-url`: `detect` would write the current branch into every link, and for a role outside a collection docsible leaves `roles/<role>/` out of the link (docsible#95). docsible 0.8.0's limits, left as they are: a block's `always` tasks are in neither the table nor the graph, the table shows no tags for a task inside a block (it reads them from top-level tasks only, so `roles/truenas`'s stage tags, the ones `make truenas TAGS=…` selects, read blank), table rows end in spaces, and `--comments` and `--task-line` stay off (the first splits a table row at a multi-line comment, the second links a task whose name holds a quote to `#L`). A Dependabot bump of docsible that changes the pages fails `lint-docs` until `make docs` is run on its branch.
- **CI** (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`: `make -k linters`; `make test` and `make test-idempotence` on Python 3.13 and 3.14, on Arm runners (free for public repositories, and faster at the CPU-bound idempotence suite than x64); `make -k lint-k8s` (kubeconform and kube-linter); `leaks`, which runs `make test-gitleaks-rules` and `scripts/ci/check-range.sh` (gitleaks over the commits the change adds, with the target branch's `.gitleaks.toml`); actionlint and zizmor (pedantic persona, so a digest-less image or a missing permissions block fails) over the workflows; shellcheck over `scripts/`; and, on pull requests only, `dependency-review`, which fails a change that adds a pip package with a known vulnerability, from GitHub's dependency graph (it cannot see the SHA-pinned actions, which zizmor's online `known-vulnerable-actions` audit covers instead). `ci-success` aggregates them, allows `dependency-review` alone to be skipped (on pushes; `tests/policy/test_github.py` checks that nothing else can be), and is the one check the "Protect main" ruleset is to require. `.github/rulesets/main.json` holds that ruleset's reviewed body, but GitHub never reads the file: it takes effect only when applied (`gh api -X PUT repos/kawadeomkar/homeserver/rulesets/24555579 --input .github/rulesets/main.json`), so read the live ruleset (`gh api repos/kawadeomkar/homeserver/rulesets/24555579`) before relying on a red PR being unmergeable. No job gets a secret (ansible-lint reads a placeholder vault password file) and none reaches the home network, so `make check-*` stays local. Actions are pinned to full commit SHAs with a version comment, which the repository settings require, and only an allow-list of actions may run. The allow-list also rejects `docker://` steps, so actionlint, kubeconform, kube-linter and gitleaks are downloaded by version and checked against a sha256. `.github/actionlint.yaml` declares the `ubuntu-26.04` and `ubuntu-26.04-arm` runner labels until actionlint knows them. Outside the gate, `.github/workflows/scorecard.yml` runs OpenSSF Scorecard weekly and on every push to `main`, publishes the result to the OpenSSF API and uploads it to code scanning; the API refuses results from a workflow that breaks its rules, which the file's header lists, so read them before changing it. `make init` installs git hooks for the same leak checks (below). The full plan, including what later PRs add, is `docs/CI-PLAN.md` (gitignored).
- **What CI cannot vouch for.** The gate is written by the pull request it judges: `ci-success` comes from the PR's own `.github/**`, `Makefile`, `scripts/**`, `tests/**`, `pytest.ini`, `pyproject.toml`, `poetry.lock`, `poetry.toml` and the linters' configuration (`.yamllint`, `.ansible-lint`, `ruff.toml`, `.kube-linter.yaml`), so a green check proves nothing about a change to those files; review them as the gate itself. They, with `ansible.cfg`, `roles/**`, `group_vars/**` and the playbooks, also run with the vault password, the TrueNAS API key or root SSH whenever `make check-*`, `make truenas`, `make proxmox` or `make site` runs on the workstation, so never run `make` on an unmerged outside PR in the clone that holds `.vault_pass` and `local.yml`; use a separate clone without them.
- **Git hooks** (`.pre-commit-config.yaml`, run by pre-commit from the lock; `make init` installs them): gitleaks over the staged changes, then `scripts/ci/check-sops-staged.sh` (`make secrets-staged`), and before a push, `scripts/ci/check-range.sh` over the commits being pushed (`make secrets-push`), the check CI runs. They need only bash and gitleaks from Homebrew (`brew install gitleaks`), so they work in any shell, with or without the virtualenv active; the linters stay in `make lint` and CI. A hook can be skipped with `--no-verify`, which is why CI's `leaks` job repeats the checks.
- **When a leak check fires.** A pushed commit is published, even on a pull-request branch. Do not merge, and close the pull request if the finding is real. Rotate a leaked secret at once: the TrueNAS API key through the role and the vault, and re-key the vault if its password was involved. For an identifier, RFC 1918 addresses are low impact, while public addresses, tailnet names, MACs and serials are higher; decide whether anything on the network needs to change. Ask GitHub Support to purge cached views and the `refs/pull/*` copies. If it reached `main`, removing it means rewriting history, which needs the ruleset's force-push rule switched off for the time and every clone re-made. Then add a fixture to `tests/policy/test_gitleaks_rules.py` for whatever the checks missed. `SECURITY.md` tells others how to report a problem privately.
- **Python dependencies** are managed with Poetry (2.x, non-package mode). Direct pins are exact (`==`) and live in `pyproject.toml`: what the playbooks need in `[project] dependencies`, and the linters, tests and hooks in the `dev` dependency group (PEP 735 `[dependency-groups]`, never `[tool.poetry.group.*.dependencies]`). `make lock` updates `poetry.lock`, which resolves once for every Python in `requires-python`, with markers, and records a sha256 for every file, which Poetry checks when it installs. It changes only what `pyproject.toml` changed (`UPDATE=<packages>` moves those on), and `poetry.toml` makes it take only releases at least 7 days old (`solver.min-release-age`). `poetry.toml` also installs wheels only, keeps the keyring closed, and puts the environment in `./.venv` when none is active; it is committed so that it overrides each user's global Poetry configuration. Poetry itself is not in the lock: each user installs it (above), `requires-poetry` says which versions work, and CI installs `POETRY_VERSION` with pipx. `make venv` runs `poetry sync`, which installs exactly the main and `dev` groups and removes anything else but pip. `make lint-lock` (`poetry check --lock --strict`) fails when the lock is stale, and `tests/policy/test_lock.py` when a pin is not exact or not the locked version, or a package has no hashes. gitleaks's default rules skip `poetry.lock`, as they do every lock file; `pyproject.toml` is scanned.
- **Dependabot** proposes weekly updates, at least 7 days after each release, for the SHA-pinned actions and every package in the lock (`allow: dependency-type: all`; by default it would update only the packages `pyproject.toml` names). It re-locks with its own Poetry, which must satisfy `requires-poetry` (keep that a range: outside it Dependabot opens no PR), and it does not read `poetry.toml`. Read each PR before merging it; never merge one only because CI is green. The required check is strict, so a PR must be up to date with `main` before it merges, and Dependabot rebases only on its schedule or a conflict: after merging one of its PRs, comment `@dependabot rebase` on the others (or use "Update branch"). **It cannot see these pins, which are bumped by hand each quarter**, each together with its integrity value: `ACTIONLINT_VERSION`, `KUBECONFORM_VERSION`, `KUBE_LINTER_VERSION`, `GITLEAKS_VERSION` and `TALOSCTL_VERSION` (bumped with `talos_version`, whose minor release it must share; a policy test checks), each with its `_SHA256`, and `POETRY_VERSION`, which has none and must stay within `requires-poetry`, in `ci.yml`; `KUBE_SCHEMA_REF` with `KUBERNETES_VERSION` (Talos's default) in the Makefile; and the Talos pins in `group_vars/all/kubernetes.yml` (`talos_version`, `talos_contract`, `talos_kubernetes_version`, which must equal `KUBERNETES_VERSION`, a policy test checks, with the ISO's SHA-256 and each schematic's installer digest at the new version, since the Image Factory publishes no checksum), moved onto the cluster by `make talos-upgrade` (`scripts/runbooks/talos.md`); and the Flux Operator in `group_vars/kubernetes/flux.yml` (`flux_bootstrap_operator_version` with its `install.yaml`'s SHA-256 and its image's digest, and the FluxInstance's exact Flux release with the manifests artifact's digest), which `roles/flux_bootstrap` refuses unpinned. At the same bump, delete `.github/actionlint.yaml` if actionlint now knows `ubuntu-26.04`.
