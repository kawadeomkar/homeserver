# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Ansible control-node repo that provisions one Ubuntu homeserver and runs ~20 self-hosted services on single-node k3s. No application code — it is Ansible (host configuration) plus hand-maintained Kubernetes manifests (workloads). The host is reached over Tailscale; bulk storage lives on a separate TrueNAS box exported over NFS.

The cluster has been through **minikube → microk8s → k3s**, and most manifests were originally generated by `kompose` from Docker Compose. Both migrations were left partially finished, so manifests are not uniform: assume any given file may still carry minikube/microk8s-era assumptions and verify before copying it as a template. The "Landmines" section below lists the ones that are actively broken.

## Direction of travel

**There are no live deployments.** Nothing described below is currently serving traffic, so no change
needs to preserve running state, and credentials committed in-tree were never used.

The target architecture is **Proxmox** as hypervisor with multiple VMs running **Talos Linux** for
Kubernetes; the NAS stays as external storage. That makes the entire Ansible layer (`roles/main`,
`roles/k8s`) throwaway — Talos has no SSH, no apt, no user accounts, an immutable root filesystem, no
bundled ingress controller or CSI driver, and enforces Pod Security Admission. The `k8s/` manifests are
the only asset that migrates.

Before fixing anything in `roles/`, check `docs/MIGRATION-TRIAGE.md` — most Ansible-layer defects are
deliberately "won't fix," and some fixes that are correct for a single Ubuntu host (notably the
`/opt` hostPath storage model) are wrong for the target.

## Commands

```bash
ansible-galaxy install -r requirements.yml     # required first — geerlingguy.docker + 3 collections

ansible-playbook playbook.yaml                 # full run: main → geerlingguy.docker → k8s
ansible-playbook playbook.yaml --tags setup    # base system + docker only (roles: main, docker)
ansible-playbook playbook.yaml --tags k8s      # k3s install + setup + provision only
ansible-playbook setup-playbook.yml            # k8s role alone (no tags defined on it)
ansible-playbook playbook.yaml --check         # dry run
ansible-playbook playbook.yaml --syntax-check

yamllint .                                     # lint
ansible-lint playbook.yaml
```

Only two tags exist: `setup` and `k8s` (`playbook.yaml:6-12`). There is no per-task tagging, so narrower runs need `--start-at-task` or a temporary playbook.

Vault: `ansible.cfg` sets `vault_password_file = ./.vault_pass`, so `--ask-vault-pass` is unnecessary locally. Edit secrets with `ansible-vault edit group_vars/all/vault.yml`.

Local VM: `vagrant up` provisions Ubuntu 22.04 via `playbook.yaml` and expects an extra vault file `@vm-vault.enc` (`Vagrantfile:24-26`) that is gitignored and not present.

### Local toolchain is currently broken

`~/.local/bin/ansible-playbook` **and** `~/.local/bin/yamllint` both have a shebang pointing at pyenv Python `3.9.2`, which no longer exists, so they die with `bad interpreter`. `.vscode/settings.json` pins the same dead interpreter. `ansible-lint` is not installed at all. Reinstall (e.g. `pipx install --include-deps ansible ansible-lint yamllint`) before concluding a playbook failure is a repo problem.

What *does* work for manifests: `kubectl` v1.36.2 (with Kustomize v5.8.1 embedded) and `kubeconform` v0.8.0. Offline schema validation is the usable gate — `kubectl --dry-run=client` is not, since it needs a live API server for OpenAPI validation:

```bash
kubeconform -summary -ignore-missing-schemas -skip CustomResourceDefinition \
  $(find k8s -name '*.yaml' ! -name 'cert-manager-1.4.0.yaml')
```

### Broken helper scripts — prefer raw `ansible-playbook`

- `run_tests.sh`, `run_vagrant.sh` — reference `playbook.yml`; the file is `playbook.yaml`. `run_tests.sh` also passes `--check-syntax` instead of `--syntax-check`.
- `run_homeserver.sh` — passes `-e @vault.enc`, which does not exist; vault is already wired via `ansible.cfg`.
- `k8srun.sh` — pre-k3s minikube script; applies a `k8s/ingress` directory that no longer exists.

## Architecture

### Layer 1 — host configuration (`roles/main`)

`tasks/main.yml` is a dispatcher of `include_tasks`, one file per concern, gated on variables rather than tags:

| Include | Gate | Notes |
|---|---|---|
| `setup.yml` | always | user + groups, passwordless sudo, apt upgrade, `packages`, pip k8s libs; deletes the PEP 668 `EXTERNALLY-MANAGED` marker |
| `ssh.yml` | always | hardens `sshd_config` line-by-line, `AllowUsers` from `security_ssh_allowed_users`, validates with `sshd -T` |
| `env.yml` | `is_hosting_music_bot` | writes `DISCORD_TOKEN` to `/etc/environment` |
| `tailscale.yml` | `tailscale_auth_key is defined` | repo + `tailscale up --advertise-routes --advertise-exit-node`; also sets IP forwarding sysctls |
| `filesystem.yml` | always | creates `/opt/<service_dirs>` — see storage model below |
| `nfs.yml` | `is_nfs` (default false) | mounts the NAS at `nfs_path` and mirrors `service_dirs` onto it |
| `fail2ban.yml` | `ansible_os_family == "Debian"` | installs only; jail config is a TODO |

Not wired in: `ubuntu-ufw.yml` (commented out until ingress ports settle), `setup-pihole.yml` (needs router DNS), `acl.yml` (never referenced).

`tailscale_auth_key` and `tailscale_advertise_routes` are undefined in plain vars — they must come from vault or `-e`, and Tailscale silently no-ops if the key is absent. `security_fail2ban_jail_local` / `security_fail2ban_local` are referenced only inside commented-out blocks.

### Layer 2 — workloads (`roles/k8s`)

`tasks/main.yml` runs `install_k3s` → `setup` → `provision`.

- `install_k3s.yml` — curls `get.k3s.io` (pinned by `k3s_version`, empty = latest stable), waits for node readiness, copies `/etc/rancher/k3s/k3s.yaml` to `~{{ username }}/.kube/config`, exports `KUBECONFIG` and kubectl completion in `.bashrc`.
- `setup.yml` — overlaps `install_k3s` (both create `.kube` and add completion); remainder is a commented-out `/etc/hosts` plan.
- `provision.yml` — a flat list of `kubectl apply -f {{ k8s_manifests_path }}/<service>`, then one `kubectl wait --for=condition=ready pods --all --all-namespaces`.
- `install_helm.yml` and `teardown.yml` (drain all nodes + `k3s-killall.sh`) exist but are **not included** by `main.yml` — invoke explicitly. Both are still untracked in git, along with `roles/k8s/defaults/`.

**`provision.yml` ordering is load-bearing.** `monitoring` is created by `k8s/prometheus/0-monitoring-namespace.yaml`, but grafana, node-exporter, cadvisor, and dashdot all put their objects in `monitoring` without declaring it. They only apply cleanly because prometheus comes first in the list. Keep that order; do not alphabetize.

**Adding a directory under `k8s/` does not deploy it.** Currently unwired in `provision.yml`: `cert-manager`, `frigate`, `photoprism`, `sabnzbd`, `kube-state-metrics`, `kubernetes-dashboard`.

### The manifest path is remote, and nothing syncs it

`k8s_manifests_path` = `{{ homeserver_repo_path }}/k8s` = **`/homeserver/k8s` on the target host**, not this working copy. `provision.yml` applies from there, so local edits have no effect until the server-side checkout is updated — and no task does that. `roles/main/tasks/setup.yml` does not clone the repo (the README claims it does), and `is_prod_run` in `roles/k8s/defaults/main.yml` — documented as the dev-sync vs prod-pull switch — is not referenced by any task. Treat "get manifests onto the server" as a manual step, and as the most likely reason a manifest change appears to do nothing.

### Storage model

Two patterns coexist; check which one a service uses before touching its volumes.

**A. hostPath under `/opt` (most services).** The Deployment mounts `/opt/<service>/...` directly — sonarr, radarr, prowlarr, sabnzbd, jellyseerr, homarr, dashy, frigate, filebrowser. These paths are created by `roles/main/tasks/filesystem.yml` from the `service_dirs` list in `group_vars/all/vars.yml`, owned by `{{ username }}`, mode `0755`. The LinuxServer.io containers run with `PUID`/`PGID` `1000` and `TZ=America/Los_Angeles`, matching `nfs_owner_uid`/`nfs_owner_gid`; that uid alignment is the whole reason the hostPath mounts are writable. **Adding a hostPath means adding the path to `service_dirs`** — otherwise kubelet/containerd creates it root-owned and the container fails to write.

Current gaps between manifests and `service_dirs`: `/opt/homarr/data`, `/opt/media/data/incomplete`, `/opt/dashy/config.yml` (`FileOrCreate` → empty file), `/opt/frigate/config.yml` and `/opt/filebrowser/filebrowser.db` (no `type:` → created as *directories*, which breaks those containers). `filesystem.yml` has a commented-out block acknowledging the config-file half of this.

`sonarr`, `radarr`, and `sabnzbd` all mount the same `/opt/media/data` at `/data` — the single-mount layout that keeps hardlinks/atomic moves working. Do not split it into per-app paths.

**B. NFS PV/PVC (stateful services).** homeassistant, jellyfin, nextcloud, photoprism use `storageClassName: nfs`, `ReadWriteMany`, `persistentVolumeReclaimPolicy: Retain`, and PVCs bound by explicit `volumeName`. There is no NFS provisioner — PVs are hand-written. Grafana is a third case: PV/PVC with `storageClassName: manual` over a `hostPath` of `/opt/grafana`.

NFS endpoints are inconsistent across manifests: `truenas.local` (hass, nextcloud-db, photoprism-db) vs `10.0.0.64` (jellyfin, nextcloud-server, photoprism-server), while `group_vars` declares a third address `nfs_ip: 10.0.25.65` with `nfs_src_path: /mnt/nvme_gen3`. Export roots differ too (`/mnt/nvme/store/...` vs `/mnt/ephemeral/...`). Confirm the live NAS address before adding a PV rather than copying a neighbour.

### Networking — three overlapping exposure mechanisms

Every service tends to carry all of these at once:

1. **NodePort** — most `service.yaml` files are `type: NodePort` with a hand-assigned port, in a registry that only exists implicitly (the exceptions are `homeassistant`, `nextcloud/service-db`, and both photoprism services, which are `ClusterIP`): `30000` homepage, `30001` prometheus, `30004` sonarr, `30005` grafana, `30006-30009` jellyfin, `30010` radarr, `30011` prowlarr, `30012` node-exporter, `30013` cadvisor, `30014` nextcloud, `30016` dashdot, `30017` jellyseerr, `30018` homarr, `30019` dashy, `30020` filebrowser, `30021` sabnzbd, `30022` frigate, `30776/30777/30779` portainer. Check this list before picking a new one.
2. **Ingress** — hosts are `<service>.homeserver.internal`. Only `k8s/homeassistant/ingress.yaml:8` sets `ingressClassName: traefik`; the rest are class-less and land on Traefik only because k3s marks its IngressClass default. Their `nginx.ingress.kubernetes.io/*` annotations (notably `rewrite-target`) are inert under Traefik. DNS for `*.homeserver.internal` is not managed in this repo.
3. **MetalLB LoadBalancer Services** — see below. MetalLB is **not installed** by any role, and `metallb_cidr` in `group_vars` is unused.

**The `ingress`-namespace landmine.** 16 files named `ingress.yaml` declare a `type: LoadBalancer` Service in `namespace: ingress` — a namespace no manifest creates — with `selector: {name: nginx-ingress-microk8s}`, the microk8s controller pod that does not exist under k3s: `cadvisor`, `dashdot`, `dashy`, `filebrowser`, `frigate`, `homarr`, `homepage`, `jellyseerr`, `nextcloud`, `node-exporter`, `photoprism`, `portainer`, `prowlarr`, `radarr`, `sabnzbd`, `sonarr`. `kubectl apply -f` on those directories fails unless the `ingress` namespace was created out-of-band on the server, and even when it applies, the Service selects nothing. `loadBalancerIP`s are in `192.168.1.0/24`, which matches neither `lan_subnet` (`10.0.0.0/24`) nor the Tailscale address in `inventory`; `192.168.1.19` is assigned twice (radarr and photoprism) and homepage claims `192.168.1.0`, a network address.

The two files that have been cleaned up show the intended end state: `k8s/homeassistant/ingress.yaml` (Traefik Ingress only, no LoadBalancer) and `k8s/jellyfin/ingress.yaml` (LoadBalancer Services moved into the app namespace with an `app:` selector, for DLNA/discovery UDP that must bypass Traefik).

Note the naming trap: `ingress.yaml` usually contains Services, sometimes plus an Ingress. `service.yaml` is the NodePort. Read both.

### Monitoring

`prometheus` (namespace `monitoring`) scrapes via Kubernetes SD — `kubernetes-apiservers`, `-nodes`, `-pods`, `-cadvisor`, `-service-endpoints`, plus a static `kube-state-metrics.kube-system.svc.cluster.local:8080` and an `alertmanager.monitoring.svc:9093` target that nothing deploys. `kube-state-metrics` lives in `kube-system` and is not in `provision.yml`, so that scrape job currently has no backend. `cadvisor` is a DaemonSet, `node-exporter` is a plain Deployment (inconsistent for a per-node exporter). `cadvisor/0-namespace.yaml` creates a `cadvisor` namespace that nothing uses — all its objects are in `monitoring`.

## Landmines

`docs/ISSUES.md` (gitignored, may not exist in a fresh clone) holds the full audit behind this section:
34 findings with file/line references, fix plans, verification steps, and a suggested order of work.
Read it before starting any repair.

- Manifest edits don't reach the cluster without manually updating `/homeserver/k8s` (see above).
- `k8s/photoprism/ingress.yaml` is an unedited copy of radarr's: it declares `radarr-lb` and `radarr-ingress` in namespaces `ingress`/`radarr`. Applying `k8s/photoprism` would touch radarr's routing, not photoprism's. It is not in `provision.yml`, so the bug is latent.
- `k8s/cert-manager/` pins v1.4.0 (2021) and its `ClusterIssuer` uses `solvers[].http01.ingress.class: public` (microk8s) against Let's Encrypt **staging**, with `commonName: homeserver.homes` — unrelated to the `*.homeserver.internal` hosts everywhere else. The bundled `cert-manager-1.4.0.yaml` is gitignored and lint-excluded. Nothing applies any of it; TLS is effectively not configured.
- `k8s/homeassistant/claim1-persistentvolumeclaim.yaml` and `docker-default-networkpolicy.yaml` are intentionally comment-only tombstones for kompose artifacts. Don't "restore" them.
- `privileged: true` appears in 8 manifests across 7 services (hass, nextcloud ×2, jellyfin, dashdot, frigate, cadvisor, node-exporter) — several inherited from kompose rather than needed. hass additionally takes `NET_ADMIN`/`NET_RAW`/`NET_BROADCAST` for device discovery.
- `nextcloud` and `photoprism` each split app and database across a Deployment *and* a StatefulSet, in opposite directions: nextcloud is Deployment `nextcloud` + StatefulSet `nextcloud-db`, photoprism is StatefulSet `photoprism` + Deployment `photoprism-mariadb`. Neither pair is a duplicate — check the object name before assuming which file is the app.
- `photoprism` has two conflicting Secrets both named `photoprism-secrets` (`1-secret-photoprism.yaml` using `data:`, `secret.yaml` using `stringData:`), holding placeholder values that are not valid base64 — applying that directory fails. Its `1-secret-mariadb.yaml` also carries `NEXTCLOUD_*` keys copied from nextcloud.
- Secrets for nextcloud/photoprism MariaDB are committed as base64 `data:` in `k8s/*/1-secret-*.yaml` — base64 is not encryption. New secrets belong in `group_vars/all/vault.yml`, not in manifests.

## Conventions

- **Manifest layout**: one directory per service, applied as a unit. `0-namespace.yaml` (the `0-` prefix makes the Namespace sort first for `kubectl apply -f <dir>`), then `deployment.yaml`, `service.yaml`, `ingress.yaml`, and PV/PVC files. One namespace per service, named after the directory; monitoring components share `monitoring`.
- **Deployments** use `strategy: {type: Recreate}` (15 of 21 — hostPath/RWX volumes cannot tolerate two pods holding the same files), `replicas: 1`, and `app: <name>` labels/selectors.
- **Adding a service**: create the dir + namespace file → pick an unused NodePort → hostPath paths also added to `service_dirs` (or write a PV/PVC) → set `ingressClassName: traefik` and skip the MetalLB Service unless you genuinely need non-HTTP ports → add the `kubectl apply` step to `provision.yml` in an order that respects namespace creation.
- **Variables**: cross-role values in `group_vars/all/vars.yml` (paths, NFS, k8s, `service_dirs`); role tunables in `roles/<role>/defaults/main.yml`. Secrets go in `group_vars/all/vault.yml` and are exposed by indirection (`discord_token: "{{ vault_discord_token }}"`).
- `inventory` is gitignored, so a fresh clone must recreate it; it holds a Tailscale IP. `ansible.cfg` pins `ansible_user = omkar` and `private_key_file = ~/.ssh/hs`, while `roles/main/defaults/main.yml` installs `ssh_public_key_file: ~/.ssh/hs.pub` — the key pair is assumed to exist locally.
- `roles/geerlingguy.docker` is galaxy-installed, gitignored, and lint-excluded — never edit it. `roles/containers` (docker-compose) is legacy and unreferenced by `playbook.yaml`; `docker/` retains only a `certbot` directory (the `docker-compose.yml` that `roles/containers/tasks/start.yml` invokes is gone).
- `.ansible-lint` skips `name[casing]`, `no-changed-when`, `ignore-errors`; task naming is mixed-case as a result. YAML style comes from `.yamlfmt` (basic, `---` document start, line breaks retained).
- `TODO.md` is the running backlog (fail2ban jails, UFW per-port rules, `package` over `apt`, split defaults/vars, real domain instead of mDNS) and matches the commented-out task files.
