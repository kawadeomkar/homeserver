# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Ansible control-node repo that provisions one Ubuntu homeserver and runs ~20 self-hosted services on single-node k3s. No application code — it is Ansible (host configuration) plus hand-maintained Kubernetes manifests (workloads). The host is reached over Tailscale; bulk storage lives on a separate TrueNAS box exported over NFS.

The cluster has been through **minikube → microk8s → k3s**, and most manifests were originally generated by `kompose` from Docker Compose. Both migrations were left partially finished, so manifests are not uniform: assume any given file may still carry minikube/microk8s-era assumptions and verify before copying it as a template. The "Landmines" section below lists the ones that are actively broken.

## Direction of travel

**There are no live deployments.** Nothing described below is currently serving traffic, so no change
needs to preserve running state, and credentials committed in-tree were never used.

The target architecture is **Proxmox** as hypervisor with multiple VMs running **Talos Linux** for
Kubernetes; the NAS stays as external storage. That makes the entire Ansible layer (`roles/main`,
`roles/k8s`) throwaway — Talos has no SSH, no apt, no user accounts, an immutable root filesystem, no
bundled ingress controller or CSI driver, and enforces Pod Security Admission. The `k8s/` manifests are
the only asset that migrates.

Before fixing anything in `roles/`, check `docs/MIGRATION-TRIAGE.md` — most Ansible-layer defects are
deliberately "won't fix," and some fixes that are correct for a single Ubuntu host (notably the
`/opt` hostPath storage model) are wrong for the target.

## Commands

```bash
ansible-galaxy install -r requirements.yml     # required first — geerlingguy.docker + 3 collections

ansible-playbook playbook.yaml                 # full run: main → geerlingguy.docker → k8s
ansible-playbook playbook.yaml --tags setup    # base system + docker only (roles: main, docker)
ansible-playbook playbook.yaml --tags k8s      # k3s install + setup + provision only
ansible-playbook setup-playbook.yml            # k8s role alone (no tags defined on it)
ansible-playbook playbook.yaml --check         # dry run
ansible-playbook playbook.yaml --syntax-check

yamllint .                                     # lint
ansible-lint playbook.yaml
```

Only two tags exist: `setup` and `k8s` (`playbook.yaml:6-12`). There is no per-task tagging, so narrower runs need `--start-at-task` or a temporary playbook.

Vault: `ansible.cfg` sets `vault_password_file = ./.vault_pass`, so `--ask-vault-pass` is unnecessary locally. Edit secrets with `ansible-vault edit group_vars/all/vault.yml`.

Local VM: `vagrant up` provisions Ubuntu 22.04 via `playbook.yaml` and expects an extra vault file `@vm-vault.enc` (`Vagrantfile:24-26`) that is gitignored and not present.

### Local toolchain is currently broken

`~/.local/bin/ansible-playbook` **and** `~/.local/bin/yamllint` both have a shebang pointing at pyenv Python `3.9.2`, which no longer exists, so they die with `bad interpreter`. `.vscode/settings.json` pins the same dead interpreter. `ansible-lint` is not installed at all. Reinstall (e.g. `pipx install --include-deps ansible ansible-lint yamllint`) before concluding a playbook failure is a repo problem.

What *does* work for manifests: `kubectl` v1.36.2 (with Kustomize v5.8.1 embedded) and `kubeconform` v0.8.0. Offline schema validation is the usable gate — `kubectl --dry-run=client` is not, since it needs a live API server for OpenAPI validation:

```bash
kubeconform -summary -ignore-missing-schemas $(find k8s -name '*.yaml')
```

### Broken helper scripts — prefer raw `ansible-playbook`

- `run_tests.sh`, `run_vagrant.sh` — reference `playbook.yml`; the file is `playbook.yaml`. `run_tests.sh` also passes `--check-syntax` instead of `--syntax-check`.
- `run_homeserver.sh` — passes `-e @vault.enc`, which does not exist; vault is already wired via `ansible.cfg`.
- `k8srun.sh` — pre-k3s minikube script; applies a `k8s/ingress` directory that no longer exists.

## Architecture

### Layer 1 — host configuration (`roles/main`)

`tasks/main.yml` is a dispatcher of `include_tasks`, one file per concern, gated on variables rather than tags:

| Include | Gate | Notes |
|---|---|---|
| `setup.yml` | always | user + groups, passwordless sudo, apt upgrade, `packages`, pip k8s libs; deletes the PEP 668 `EXTERNALLY-MANAGED` marker |
| `ssh.yml` | always | hardens `sshd_config` line-by-line, `AllowUsers` from `security_ssh_allowed_users`, validates with `sshd -T` |
| `env.yml` | `is_hosting_music_bot` | writes `DISCORD_TOKEN` to `/etc/environment` |
| `tailscale.yml` | `tailscale_auth_key is defined` | repo + `tailscale up --advertise-routes --advertise-exit-node`; also sets IP forwarding sysctls |
| `filesystem.yml` | always | creates `/opt/<service_dirs>` — see storage model below |
| `nfs.yml` | `is_nfs` (default false) | mounts the NAS at `nfs_path` and mirrors `service_dirs` onto it |
| `fail2ban.yml` | `ansible_os_family == "Debian"` | installs only; jail config is a TODO |

Not wired in: `ubuntu-ufw.yml` (commented out until ingress ports settle), `setup-pihole.yml` (needs router DNS), `acl.yml` (never referenced).

`tailscale_auth_key` and `tailscale_advertise_routes` are undefined in plain vars — they must come from vault or `-e`, and Tailscale silently no-ops if the key is absent. `security_fail2ban_jail_local` / `security_fail2ban_local` are referenced only inside commented-out blocks.

### Layer 2 — workloads (`roles/k8s`)

`tasks/main.yml` runs `install_k3s` → `setup` → `provision`.

- `install_k3s.yml` — curls `get.k3s.io` (pinned by `k3s_version`, empty = latest stable), waits for node readiness, copies `/etc/rancher/k3s/k3s.yaml` to `~{{ username }}/.kube/config`, exports `KUBECONFIG` and kubectl completion in `.bashrc`.
- `setup.yml` — overlaps `install_k3s` (both create `.kube` and add completion); remainder is a commented-out `/etc/hosts` plan.
- `provision.yml` — a flat list of `kubectl apply -f {{ k8s_manifests_path }}/<service>`, then one `kubectl wait --for=condition=ready pods --all --all-namespaces`.
- `install_helm.yml` and `teardown.yml` (drain all nodes + `k3s-killall.sh`) exist but are **not included** by `main.yml` — invoke explicitly. Nothing in the repo actually uses Helm yet.

**Shared namespaces are applied first.** `k8s/00-namespaces/` holds namespaces used by more than one service directory — currently only `monitoring` (prometheus, grafana, dashdot) — and `provision.yml` applies it as its first task. Each service directory otherwise owns its own `0-namespace.yaml`. Do not re-add a `monitoring` declaration to an individual directory: duplicate Namespace objects are idempotent under `kubectl apply` but make `kubectl kustomize` fail outright, and under Flux would let pruning one Kustomization cascade-delete the namespace.

**Adding a directory under `k8s/` does not deploy it.** Currently unwired in `provision.yml`: `frigate`, `photoprism`, `sabnzbd`, `kube-state-metrics`.

### The manifest path is remote, and nothing syncs it

`k8s_manifests_path` = `{{ homeserver_repo_path }}/k8s` = **`/homeserver/k8s` on the target host**, not this working copy. `provision.yml` applies from there, so local edits have no effect until the server-side checkout is updated — and no task does that. `roles/main/tasks/setup.yml` does not clone the repo (the README claims it does), and `is_prod_run` in `roles/k8s/defaults/main.yml` — documented as the dev-sync vs prod-pull switch — is not referenced by any task. Treat "get manifests onto the server" as a manual step, and as the most likely reason a manifest change appears to do nothing.

### Storage model

Two patterns coexist; check which one a service uses before touching its volumes.

**A. hostPath under `/opt` (most services).** The Deployment mounts `/opt/<service>/...` directly — sonarr, radarr, prowlarr, sabnzbd, jellyseerr, homarr, dashy, frigate, filebrowser. These paths are created by `roles/main/tasks/filesystem.yml` from the `service_dirs` list in `group_vars/all/vars.yml`, owned by `{{ username }}`, mode `0755`. The LinuxServer.io containers run with `PUID`/`PGID` `1000` and `TZ=America/Los_Angeles`, matching `nfs_owner_uid`/`nfs_owner_gid`; that uid alignment is the whole reason the hostPath mounts are writable. **Adding a hostPath means adding the path to `service_dirs`** — otherwise kubelet/containerd creates it root-owned and the container fails to write.

Current gaps between manifests and `service_dirs`: `/opt/homarr/data`, `/opt/media/data/incomplete`, `/opt/dashy/config.yml` (`FileOrCreate` → empty file), `/opt/frigate/config.yml` and `/opt/filebrowser/filebrowser.db` (no `type:` → created as *directories*, which breaks those containers). `filesystem.yml` has a commented-out block acknowledging the config-file half of this.

`sonarr`, `radarr`, and `sabnzbd` all mount the same `/opt/media/data` at `/data` — the single-mount layout that keeps hardlinks/atomic moves working. Do not split it into per-app paths.

**This whole pattern is a Pod Security Admission problem, not just a Talos-persistence one.** `hostPath` is a `baseline` control, so every one of these workloads violates `baseline` — 19 workloads across 12 namespaces, of which 8 namespaces carry no exemption label. Two refinements: a `hostPath` inside a *PersistentVolume* consumed via PVC is **not** a violation (PSA reads pod specs only, so grafana's `/opt/grafana` PV passes), and `type: File`/`FileOrCreate` does **not** exempt one. The fix is the hostPath→PVC conversion, not more exemption labels.

**B. NFS PV/PVC (stateful services).** homeassistant, jellyfin, nextcloud, photoprism use `storageClassName: nfs`, `ReadWriteMany`, `persistentVolumeReclaimPolicy: Retain`, and PVCs bound by explicit `volumeName`. There is no NFS provisioner — PVs are hand-written. Grafana is a third case: PV/PVC with `storageClassName: manual` over a `hostPath` of `/opt/grafana`.

NFS endpoints are inconsistent across manifests: `truenas.local` (hass, nextcloud-db, photoprism-db) vs `10.0.0.64` (jellyfin, nextcloud-server, photoprism-server), while `group_vars` declares a third address `nfs_ip: 10.0.25.65` with `nfs_src_path: /mnt/nvme_gen3`. Export roots differ too (`/mnt/nvme/store/...` vs `/mnt/ephemeral/...`). Confirm the live NAS address before adding a PV rather than copying a neighbour.

### Networking — three overlapping exposure mechanisms

Every service tends to carry all of these at once:

1. **NodePort** — most `service.yaml` files are `type: NodePort` with a hand-assigned port, in a registry that only exists implicitly (the exceptions are `homeassistant`, `nextcloud/service-db`, and both photoprism services, which are `ClusterIP`): `30000` homepage, `30001` prometheus, `30004` sonarr, `30005` grafana, `30006-30009` jellyfin, `30010` radarr, `30011` prowlarr, `30012` node-exporter, `30014` nextcloud, `30016` dashdot, `30017` jellyseerr, `30018` homarr, `30019` dashy, `30020` filebrowser, `30021` sabnzbd, `30022` frigate, `30776/30777/30779` portainer. Check this list before picking a new one — and note `nextcloud/service-server.yaml` declares a NodePort for port 443 with no explicit `nodePort:`, so one more port in this range is auto-assigned and the registry is incomplete by construction.
2. **Ingress** — hosts are `<service>.homeserver.internal`. Only `k8s/homeassistant/ingress.yaml:8` sets `ingressClassName: traefik`; the rest are class-less and land on Traefik only because k3s marks its IngressClass default. Their `nginx.ingress.kubernetes.io/*` annotations (notably `rewrite-target`) are inert under Traefik. DNS for `*.homeserver.internal` is not managed in this repo.
3. **LoadBalancer Services** — only `k8s/jellyfin/ingress.yaml` still has them (`jellyfin-lb-udp`/`-tcp`, for DLNA 1900/udp and discovery 7359/udp, which must bypass an HTTP ingress). MetalLB is **not installed** by any role and `metallb_cidr` is unused — but **k3s ships ServiceLB (klipper-lb) and nothing disables it**, so these are reconciled via hostPorts rather than sitting `<pending>`. Talos has no ServiceLB equivalent, so a LoadBalancer implementation must be installed there or they will hang.

**Historical note — the `ingress`-namespace landmine is gone.** 16 `ingress.yaml` files used to declare a `type: LoadBalancer` Service in `namespace: ingress` (a namespace no manifest created) selecting `name: nginx-ingress-microk8s`, a controller pod that does not exist under k3s. They were deleted; `k8s/photoprism/ingress.yaml`, which was an unedited copy of radarr's, was rewritten. If you see that shape in an old branch or a stale server-side checkout, it is dead weight, not configuration.

Naming: `ingress.yaml` now contains an Ingress (all 20 of them), plus jellyfin's two `*-lb-*` Services as the sole exception. `service.yaml` is the NodePort. A `-lb` suffix means a LoadBalancer Service.

### Monitoring

`prometheus` (namespace `monitoring`) scrapes via Kubernetes SD — `kubernetes-apiservers`, `-nodes`, `-pods`, `-cadvisor`, `-service-endpoints`, plus a static `kube-state-metrics.kube-system.svc.cluster.local:8080` and an `alertmanager.monitoring.svc:9093` target that nothing deploys. `node-exporter` is a DaemonSet in `kube-system` (Talos exempts that namespace from PSA by default); `grafana` and `dashdot` are in `monitoring`.

**None of it produces data as committed**, and the reasons are worth knowing before debugging a dashboard: Prometheus's ClusterRoleBinding targets a ServiceAccount in a `prometheus` namespace that no manifest creates, so every Kubernetes SD job gets 403; Grafana's datasource hardcodes `http://10.0.0.36:30001` instead of in-cluster DNS; Prometheus's TSDB is an `emptyDir` with no retention while Grafana's *dashboards* get a 10Gi PV; the `kubernetes-pods` job matches nothing because no pod carries `prometheus.io/scrape`; and the alerting rules are a placeholder that always fires at the nonexistent Alertmanager. `kube-state-metrics` is not in `provision.yml` and could not work anyway — its `cluster-role-binding.yaml` is a byte-identical copy of `deployment.yaml`, so no binding exists. Tracked as K8S-19 through K8S-26 in `docs/ISSUES.md`; `kube-prometheus-stack` would replace the whole tree.

## Landmines

`docs/ISSUES.md` (gitignored, so absent from a fresh clone) holds the full audit behind this section:
46 findings with file/line references, fix plans, verification steps, and a suggested order of work.
`docs/MIGRATION-TRIAGE.md` says which survive the Proxmox/Talos move; `docs/reviews/` holds two review
passes over the change stack. Read them before starting any repair — and note that because `docs/` is
gitignored, none of it reaches a clone, so the findings referenced below may have no local backing.

- Manifest edits don't reach the cluster without manually updating `/homeserver/k8s` (see above).
- **There is no TLS anywhere.** Every Ingress is plain HTTP. The old `k8s/cert-manager/` (v1.4.0, staging ACME, microk8s solver class, `commonName: homeserver.homes`) was deleted as unsalvageable — that is not a decision against TLS, which needs a real domain and a DNS-01 solver because `*.homeserver.internal` cannot be validated by public ACME.
- `k8s/homeassistant/claim1-persistentvolumeclaim.yaml` and `docker-default-networkpolicy.yaml` are intentionally comment-only tombstones for kompose artifacts. Don't "restore" them.
- `privileged: true` remains on 4 workloads: `jellyfin` and `frigate` (`/dev/dri` transcoding), `dashdot` (host inspection), `node-exporter` (host metrics). Their namespaces carry `pod-security.kubernetes.io/enforce: privileged`, except node-exporter which relies on `kube-system` being exempt. `homeassistant` keeps `NET_ADMIN`/`NET_RAW`/`NET_BROADCAST` without full privilege — still above `baseline`, so its namespace is labelled too. Note it has **no `hostNetwork: true` anywhere**, so the mDNS/SSDP discovery those capabilities exist for cannot actually work.
- **`portainer` binds `cluster-admin`** to the ServiceAccount its pod runs under, exposed on three NodePorts and an Ingress. That principal can create privileged pods in any namespace *and relabel namespaces*, so every PSA label above is advisory while it exists (SEC-2). `filebrowser` separately mounts host `/` **writable** at `/srv` and serves it unauthenticated (SEC-3).
- `nextcloud` and `photoprism` each split app and database across a Deployment *and* a StatefulSet, in opposite directions: nextcloud is Deployment `nextcloud` + StatefulSet `nextcloud-db`, photoprism is StatefulSet `photoprism` + Deployment `photoprism-mariadb`. Neither pair is a duplicate — check the object name before assuming which file is the app.
- **No plaintext `Secret` manifest may be committed.** `.gitignore` blocks `k8s/**/*secret*.yaml` in both letter cases, with negations for the safe-by-construction kinds (`*.sops.yaml`, `*sealed*.yaml`, `*.example.yaml`, `*.template.yaml`, `externalsecret*.yaml`, `secretstore*.yaml`). Four such files were deleted from this repo; see `k8s/README-secrets.md` for the key set each service needs and how to create them by hand. **This repo is public** — that is also why `.claude/` and `inventory` are ignored.
- **Two secret systems, split by layer:** Ansible Vault (`group_vars/all/vault.yml`) for host/playbook variables, and SOPS+age (decided, not yet implemented) for Kubernetes Secrets. Do not put k8s Secrets in `vault.yml`; `provision.yml` shells out to `kubectl` and never templates them.
- `nextcloud` and `photoprism` cannot currently be deployed: their Secrets no longer exist in-tree. `provision.yml` still applies nextcloud behind an unguarded `kubectl wait --all --all-namespaces`, so a `--tags k8s` run aborts rather than skipping it.

## Conventions

- **Manifest layout**: one directory per service, applied as a unit. `0-namespace.yaml` (the `0-` prefix makes the Namespace sort first for `kubectl apply -f <dir>`), then `deployment.yaml`, `service.yaml`, `ingress.yaml`, and PV/PVC files. One namespace per service, named after the directory. The exception is `monitoring`, shared by prometheus/grafana/dashdot and therefore owned by `k8s/00-namespaces/monitoring.yaml` instead.
- **Deployments** use `strategy: {type: Recreate}` (15 of 21 — hostPath/RWX volumes cannot tolerate two pods holding the same files), `replicas: 1`, and `app: <name>` labels/selectors.
- **Adding a service**: create the dir + its own `0-namespace.yaml` → pick an unused NodePort → hostPath paths also added to `service_dirs` (or write a PV/PVC) → write an Ingress and skip LoadBalancer Services unless you genuinely need non-HTTP ports → if the pod needs `privileged`, `hostPath`, `hostNetwork` or added capabilities, label the namespace `pod-security.kubernetes.io/enforce: privileged` and say why in a comment → pin the image to an immutable tag (see below) → add the `kubectl apply` step to `provision.yml`.
- **Variables**: cross-role values in `group_vars/all/vars.yml` (paths, NFS, k8s, `service_dirs`); role tunables in `roles/<role>/defaults/main.yml`. Host/playbook secrets go in `group_vars/all/vault.yml`, exposed by indirection (`discord_token: "{{ vault_discord_token }}"`). Kubernetes Secrets do not — see the Landmines note above.
- **Image tags are pinned, and the pin must be immutable.** LinuxServer.io re-points its plain `x.y.z` tags at every build revision, so those images use the `x.y.z-lsNNN` form (`linuxserver/sonarr:4.0.19.2979-ls320`). Do not add `imagePullPolicy: Always` — on a pinned tag it is redundant, and on a mutable one it is what silently defeats the pin. There is no Renovate, so bumps are manual.
- **Resource requests on every workload**, with limits only where a runaway can starve the node (nextcloud, jellyfin, frigate, photoprism, both MariaDBs, prometheus). All values are un-measured guesses — nothing has ever run. Aggregate: ~3.3 vCPU / ~9.6 GiB of requests, so a node needs ~4 vCPU and ~11 GiB before system overhead.
- `inventory` and `.claude/` are gitignored because **this repo is public** — both would otherwise publish the Tailscale host address. A fresh clone must recreate `inventory`. `ansible.cfg` pins `ansible_user = omkar` and `private_key_file = ~/.ssh/hs`, while `roles/main/defaults/main.yml` installs `ssh_public_key_file: ~/.ssh/hs.pub` — the key pair is assumed to exist locally.
- `roles/geerlingguy.docker` is galaxy-installed, gitignored, and lint-excluded — never edit it. `roles/containers` (docker-compose) is legacy and unreferenced by `playbook.yaml`; `docker/` retains only a `certbot` directory (the `docker-compose.yml` that `roles/containers/tasks/start.yml` invokes is gone).
- `.ansible-lint` skips `name[casing]`, `no-changed-when`, `ignore-errors` (plus a bogus fourth entry, `ignore_errors`, which is the Ansible keyword and not a rule id); task naming is mixed-case as a result. YAML style comes from `.yamlfmt` (basic, `---` document start, line breaks retained). **Nothing is enforced mechanically**: there is no CI, no pre-commit hook, and no `.yamllint` config — so once the local toolchain is repaired, default-rule `yamllint .` will fail on at least one long line.
- `TODO.md` is the running backlog. Most of its Ansible-layer items (fail2ban jails, UFW rules, the username list) are superseded by the Talos migration, which removes the layer they configure — it now marks those explicitly.
- **Commit style**: history before the current change stack used short lowercase subjects with no body; the stack uses Conventional Commits with an explanatory body. Follow the latter.
