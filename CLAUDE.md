# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Infrastructure repo for a homelab. It holds hand-maintained Kubernetes manifests for ~20 self-hosted services (`k8s/`) and the Ansible that configures the infrastructure machines: `roles/truenas` (the NAS, through its API) and `roles/proxmox_storage` (the hypervisor's VM-disk storage on the NAS). There is no application code.

The manifests were written for a single Ubuntu host running k3s, with bulk storage on a separate TrueNAS box over NFS. That cluster had been through **minikube → microk8s → k3s**, and most manifests were originally generated by `kompose` from Docker Compose. Both migrations were left partially finished, so manifests are not uniform: assume any given file may still carry minikube/microk8s-era assumptions and verify before copying it as a template. The "Landmines" section below lists the ones that are actively broken.

## Direction of travel

**There are no live deployments.** Nothing described below is currently serving traffic, so no change
needs to preserve running state, and credentials committed in-tree were never used.

The target is three machines (hardware in `docs/MACHINES.md`, which is gitignored):

| Machine | Role |
|---|---|
| `homeserver` | **Proxmox** hypervisor; Kubernetes runs in VMs on it, with **Talos Linux** as the plan |
| `truenas` | TrueNAS Community Edition; external storage, including Proxmox's VM disks |
| `opnsense` | router and firewall |

**The Ansible layer for the old Ubuntu host is gone.** `roles/main` (host configuration), `roles/k8s`
(k3s install plus `kubectl apply`), the playbooks, `group_vars/all/vars.yml`, the Vagrant setup and the
helper scripts were deleted as throwaway — Talos has no SSH, no apt, no user accounts, an immutable root
filesystem, no bundled ingress controller or CSI driver, and enforces Pod Security Admission. They are in
the git history. The Ansible here configures the infrastructure machines (TrueNAS and Proxmox), not
Kubernetes nodes. The `k8s/` manifests are the asset that migrates.

`docs/MIGRATION-TRIAGE.md` and `docs/ISSUES.md` predate that deletion: their Ansible-layer findings are
moot, their manifest findings still apply. Some fixes that would be correct for a single Ubuntu host
(notably keeping the `/opt` hostPath storage model working) are wrong for the target.

## Commands

```bash
make venv PYTHON=<python 3.12+>   # .venv from the hash-locked requirements.txt (--require-hashes)
make init                         # also copies inventory and group_vars/all/local.yml from their examples
make lint                         # make linters, then the unit tests (make test)
make linters                      # yamllint --strict, ansible-lint (production profile), module docs
make test-idempotence             # each role run repeatedly against local fakes (about 30 s)
make lint-kubeconform             # kubeconform -strict against Kubernetes 1.37.1 (Talos's), pinned schemas
make lock                         # regenerate requirements.txt, with hashes, after editing requirements.in
make check-truenas                # dry run of roles/truenas against the NAS, with --diff
make truenas                      # apply it; TAGS=truenas_network (or _pools, _system, _datasets, _nfs) for one stage
make check-proxmox / make proxmox # the same for roles/proxmox_storage on the Proxmox host
make vault-edit                   # secrets
```

Always run tools from the project's virtualenv, never from `PATH`. On this machine that is the pyenv virtualenv `homeserver` (Python 3.14.6, under pyenv's `versions/3.14.6/envs/`); `make` uses the active virtualenv (`VIRTUAL_ENV`) and otherwise `./.venv`, and `VENV=<path>` overrides both. `python3` itself resolves to a broken pyenv build (3.13.1, `libintl` dyld error), and `~/.local/bin/ansible-playbook` and `~/.local/bin/yamllint` have a dead shebang. ansible-core 2.21 treats a non-boolean conditional as a fatal error. When the shell's standard handles are non-blocking, ansible commands exit with "Ansible requires blocking IO"; redirect stdin from `/dev/null` and stdout/stderr to a file.

`kubeconform` is the usable gate for manifests — `kubectl --dry-run=client` is not, since it needs a live API server for OpenAPI validation. `kubectl` v1.36.2 (with Kustomize v5.8.1 embedded) and `kubeconform` v0.8.0 are what works locally. `make lint-kubeconform` runs it strictly against the Kubernetes version Talos ships, with the schemas pinned to one commit and cached in `.cache/kubeconform`; it is the one target whose tool comes from `PATH` (Homebrew here). The idempotence tests also take `openssl` from `PATH`, for the fake NAS's certificate.

Vault: `ansible.cfg` sets `vault_password_file = ./.vault_pass`, so `--ask-vault-pass` is unnecessary locally. It holds `vault_truenas_api_key` (read by `group_vars/nas/connection.yml`) and `vault_discord_token`, left over from the deleted roles. Never print its contents; check it by listing variable names only.

## Architecture

### Infrastructure Ansible

Two roles, each with its own playbook (`site.yml` runs both, NAS first). The inventory has two groups, `nas` (host `truenas`) and `proxmox` (host `homeserver`), and no addresses.

**The roles are generic; this setup is configuration.** Role defaults change nothing (empty lists and dicts, null for "leave alone"), and task files hold no configuration values, only variables, API namespaces and CLI verbs. Everything that describes these machines lives in tracked group_vars, apart from addresses and serials:

| File | Holds |
|---|---|
| `group_vars/all/local.yml` (git-ignored) | addresses, disk serials |
| `group_vars/all/vault.yml` | the TrueNAS API key |
| `group_vars/all/storage.yml` | the VM storage layout (dataset and Proxmox storage id per VM class), read by both plays so a share and the storage that mounts it cannot drift apart |
| `group_vars/nas/connection.yml`, `group_vars/proxmox/connection.yml` | how each host is reached |
| `group_vars/nas/truenas.yml` | the NAS: network, pools, settings, datasets, shares, services |
| `group_vars/proxmox/storage.yml` | the Proxmox storages and boot delay |

A new setting goes in one of these files, with a neutral default in the role and a line in the role's `meta/argument_specs.yml` and `README.md`, never as a literal in a task.

**`roles/truenas`** runs on the controller (`ansible_connection: local`) and talks to the NAS's JSON-RPC 2.0 WebSocket API (`wss://<nas>/api/current`) with an API key, through custom modules in `roles/truenas/library/` and a shared client in `roles/truenas/module_utils/truenas_api.py`. The REST API is deprecated and gone in TrueNAS 26; SSH stays off on the NAS. Stages, each under its own tag: `truenas_network` (network settings, static address), `truenas_pools`, `truenas_system`, `truenas_datasets`, `truenas_nfs` (service settings, shares), `truenas_services` (last, so NFS starts once its shares exist); validation and the read-only connection (`truenas_info`) run under every tag, and a stage whose variables are empty does nothing. Design facts that are easy to break:

- **Every change to the NAS goes through this role.** No UI clicks, ad-hoc API calls or SSH; a fresh install plus one run must rebuild it. Read-only API queries are fine.
- **TrueNAS rate-limits logins** to 20 per minute per client address, and every module run logs in once. Modules therefore take lists (all datasets, all services) rather than being looped over, and the client waits out the window if it is hit.
- **The static address uses TrueNAS's commit-and-check-in.** `truenas_interface` commits with a rollback timer, reconnects on the new address and checks in; if it cannot, the NAS reverts by itself. The play reaches the NAS on the static address first and falls back to `truenas_bootstrap_address`.
- **The system dataset is pinned before any pool import.** On a fresh install it reads as `boot-pool` but counts as unset, and importing a pool would move it onto that pool.
- **Pools are imported or created, never destroyed, wiped, exported or upgraded.** Creation needs `truenas_pool_allow_create` and blank disks (by serial), and is untested.
- **Modules return only the fields they manage.** `system.general.config` includes the UI certificate's private key.
- **The API key goes only to the NAS's own certificate.** Certificate validation is off (self-signed), so `truenas_api_cert_sha256` pins the certificate's SHA-256 (in `local.yml`); a server presenting anything else gets no login. Replacing the certificate means updating the pin.
- **An NFS share must name its hosts or networks.** NFS with `sec=sys` has no authentication.

**`roles/proxmox_storage`** runs over root SSH with `pvesm`, not `community.proxmox.proxmox_storage` (which only creates storage and has no `format` option). It adds `truenas-persistent` and `truenas-ephemeral` as NFS storages with qcow2, corrects drift in content, format and mount options, refuses a storage id that points elsewhere, and sets the node's start-on-boot delay so VMs wait for the NAS.

Storage design: persistent VMs on `nvme_gen3/proxmox/vm` (RAIDZ1, `sync=standard`), ephemeral VMs on `ephemeral/proxmox/vm` (single disk, `sync=disabled`, 1 TiB quota on `ephemeral/proxmox` because the pool also holds the media dataset, and never a snapshot task). Both use 64K records and POSIX ACLs.

### Workloads (`k8s/`)

**Nothing in this repo applies the manifests.** The deleted `k8s` role ran one `kubectl apply -f <dir>` per service directory and then a single `kubectl wait` for every pod in every namespace, in this order: `00-namespaces`, `homeassistant`, `prometheus`, `grafana`, `node-exporter`, `dashdot`, `homepage`, `homarr`, `dashy`, `jellyfin`, `sonarr`, `radarr`, `prowlarr`, `jellyseerr`, `nextcloud`, `filebrowser`. `frigate`, `photoprism`, `sabnzbd` and `kube-state-metrics` were never wired in, so nothing has ever applied them. How manifests will reach the new cluster is undecided; the removed role's notes named GitOps as its replacement.

**Shared namespaces are applied first.** `k8s/00-namespaces/` holds namespaces used by more than one service directory — currently only `monitoring` (prometheus, grafana, dashdot) — so it has to be applied before any service directory. Each service directory otherwise owns its own `0-namespace.yaml`. Do not re-add a `monitoring` declaration to an individual directory: duplicate Namespace objects are idempotent under `kubectl apply` but make `kubectl kustomize` fail outright, and under Flux would let pruning one Kustomization cascade-delete the namespace.

### Storage model

Two patterns coexist; check which one a service uses before touching its volumes.

**A. hostPath under `/opt` (most services).** The Deployment mounts `/opt/<service>/...` directly — sonarr, radarr, prowlarr, sabnzbd, jellyseerr, homarr, dashy, frigate, filebrowser. These directories used to be created by the deleted host role, owned by the login user with mode `0755`; **nothing creates them now**. The LinuxServer.io containers run with `PUID`/`PGID` `1000` and `TZ=America/Los_Angeles`, and that uid matching the directories' owner was the whole reason the hostPath mounts were writable — a hostPath nobody pre-creates is made root-owned by kubelet/containerd, and the container fails to write.

File-shaped hostPaths need care whoever creates the parent: `/opt/frigate/config.yml` has no `type:`, so it is created as a *directory*, which breaks that container. `/opt/dashy/config.yml` and `/opt/filebrowser/filebrowser.db` are `FileOrCreate`, which creates an empty root-owned file only when the parent directory already exists — it never creates parents, so with nothing creating `/opt/<service>` those pods stay in `ContainerCreating`.

`sonarr`, `radarr`, and `sabnzbd` all mount the same `/opt/media/data` at `/data` — the single-mount layout that keeps hardlinks/atomic moves working. Do not split it into per-app paths.

**This whole pattern is a Pod Security Admission problem, not just a Talos-persistence one.** `hostPath` is a `baseline` control, so every one of these workloads violates `baseline` — 19 workloads across 12 namespaces, of which 8 namespaces carry no exemption label. Two refinements: a `hostPath` inside a *PersistentVolume* consumed via PVC is **not** a violation (PSA reads pod specs only, so grafana's `/opt/grafana` PV passes), and `type: File`/`FileOrCreate` does **not** exempt one. The fix is the hostPath→PVC conversion, not more exemption labels.

**B. NFS PV/PVC (stateful services).** homeassistant, jellyfin, nextcloud, photoprism use `storageClassName: nfs`, `ReadWriteMany`, `persistentVolumeReclaimPolicy: Retain`, and PVCs bound by explicit `volumeName`. There is no NFS provisioner — PVs are hand-written. Grafana and Prometheus are a third case: PV/PVC with `storageClassName: manual` over a `hostPath` (`/opt/grafana`, `/opt/prometheus`).

NFS endpoints are inconsistent across manifests: `truenas.local` (hass, nextcloud-db, photoprism-db) vs `10.0.0.64` (jellyfin, nextcloud-server, photoprism-server). Export roots differ too (`/mnt/nvme/store/...` vs `/mnt/ephemeral/...`), and the NAS has since been reinstalled: it has no `nvme` pool, and `roles/truenas` exports only the two Proxmox VM datasets, to the Proxmox host alone. Confirm the live NAS address and export before adding a PV rather than copying a neighbour.

### Networking — three overlapping exposure mechanisms

Every service tends to carry all of these at once:

1. **NodePort** — most `service.yaml` files are `type: NodePort` with a hand-assigned port, in a registry that only exists implicitly (the exceptions are `homeassistant`, `nextcloud/service-db`, and both photoprism services, which are `ClusterIP`): `30000` homepage, `30001` prometheus, `30004` sonarr, `30005` grafana, `30006-30009` jellyfin, `30010` radarr, `30011` prowlarr, `30012` node-exporter, `30014` nextcloud, `30016` dashdot, `30017` jellyseerr, `30018` homarr, `30019` dashy, `30020` filebrowser, `30021` sabnzbd, `30022` frigate. Check this list before picking a new one — and note `nextcloud/service-server.yaml` declares a NodePort for port 443 with no explicit `nodePort:`, so one more port in this range is auto-assigned and the registry is incomplete by construction.
2. **Ingress** — hosts are `<service>.homeserver.internal`. Only `k8s/homeassistant/ingress.yaml:8` sets `ingressClassName: traefik`; the rest are class-less and land on Traefik only because k3s marks its IngressClass default. Their `nginx.ingress.kubernetes.io/*` annotations (notably `rewrite-target`) are inert under Traefik. DNS for `*.homeserver.internal` is not managed in this repo.
3. **LoadBalancer Services** — only `k8s/jellyfin/ingress.yaml` still has them (`jellyfin-lb-udp`/`-tcp`, for DLNA 1900/udp and discovery 7359/udp, which must bypass an HTTP ingress). Nothing in this repo installs MetalLB. Under k3s that went unnoticed, because **k3s ships ServiceLB (klipper-lb)**, which reconciles these via hostPorts rather than leaving them `<pending>`. Talos has no ServiceLB equivalent, so a LoadBalancer implementation must be installed there or they will hang.

**Historical note — the `ingress`-namespace landmine is gone.** 16 `ingress.yaml` files used to declare a `type: LoadBalancer` Service in `namespace: ingress` (a namespace no manifest created) selecting `name: nginx-ingress-microk8s`, a controller pod that does not exist under k3s. They were deleted; `k8s/photoprism/ingress.yaml`, which was an unedited copy of radarr's, was rewritten. If you see that shape in an old branch or a stale server-side checkout, it is dead weight, not configuration.

Naming: `ingress.yaml` now contains an Ingress (all 18 of them), plus jellyfin's two `*-lb-*` Services as the sole exception. `service.yaml` is the NodePort. A `-lb` suffix means a LoadBalancer Service.

### Monitoring

`prometheus` (namespace `monitoring`) scrapes via Kubernetes SD — `kubernetes-apiservers`, `-nodes`, `-pods`, `-cadvisor`, `-service-endpoints`, plus a static `kube-state-metrics.kube-system.svc.cluster.local:8080` and an `alertmanager.monitoring.svc:9093` target that nothing deploys. `node-exporter` is a DaemonSet in `kube-system` (Talos exempts that namespace from PSA by default); `grafana` and `dashdot` are in `monitoring`.

**None of it has ever run**, so treat it as untested. The defects that would have stopped it collecting anything were fixed in the manifests: Prometheus has a ServiceAccount and binding in `monitoring`, Grafana's datasource uses in-cluster DNS, the TSDB sits on a 20Gi PV with 15d/15GB retention, and `kube-state-metrics` (never deployed by the old role) has a real ClusterRoleBinding. Still open: the `kubernetes-pods` job matches nothing because no pod carries `prometheus.io/scrape`; the alerting rules are a placeholder that always fires at the nonexistent Alertmanager (K8S-26); Prometheus's Deployment has no `strategy: Recreate` despite its hostPath PV; and Prometheus (uid 1000) and Grafana (uid 472) both run as non-root against hostPath directories that nothing creates or chowns, since `fsGroup` is not applied to hostPath volumes. `kube-prometheus-stack` would replace the whole tree.

## Landmines

`docs/ISSUES.md` (gitignored, so absent from a fresh clone) holds the full audit behind this section:
46 findings with file/line references, fix plans, verification steps, and a suggested order of work.
`docs/MIGRATION-TRIAGE.md` says which survive the Proxmox/Talos move; `docs/reviews/` holds two review
passes over the change stack. Read them before starting any repair — and note that because `docs/` is
gitignored, none of it reaches a clone, so the findings referenced below may have no local backing.

- **There is no TLS anywhere.** Every Ingress is plain HTTP. The old `k8s/cert-manager/` (v1.4.0, staging ACME, microk8s solver class, `commonName: homeserver.homes`) was deleted as unsalvageable — that is not a decision against TLS, which needs a real domain and a DNS-01 solver because `*.homeserver.internal` cannot be validated by public ACME.
- `k8s/homeassistant/claim1-persistentvolumeclaim.yaml` and `docker-default-networkpolicy.yaml` are intentionally comment-only tombstones for kompose artifacts. Don't "restore" them.
- `privileged: true` remains on 4 workloads: `jellyfin` and `frigate` (`/dev/dri` transcoding), `dashdot` (host inspection), `node-exporter` (host metrics). Their namespaces carry `pod-security.kubernetes.io/enforce: privileged`, except node-exporter which relies on `kube-system` being exempt. `homeassistant` keeps `NET_ADMIN`/`NET_RAW`/`NET_BROADCAST` without full privilege — still above `baseline`, so its namespace is labelled too. Note it has **no `hostNetwork: true` anywhere**, so the mDNS/SSDP discovery those capabilities exist for cannot actually work.
- **No cluster-admin principal runs in the cluster.** `portainer` used to bind `cluster-admin` to the ServiceAccount its pod ran under, on three NodePorts plus an Ingress — which made every PSA label above advisory, since that principal could create privileged pods anywhere and relabel namespaces. It was deleted rather than scoped (portainer's upstream manifests ship that binding by design). Use `k9s` or Headlamp from a workstation instead; if portainer is ever reinstated, that binding is the thing to fix first.
- `nextcloud` and `photoprism` each split app and database across a Deployment *and* a StatefulSet, in opposite directions: nextcloud is Deployment `nextcloud` + StatefulSet `nextcloud-db`, photoprism is StatefulSet `photoprism` + Deployment `photoprism-mariadb`. Neither pair is a duplicate — check the object name before assuming which file is the app.
- **No plaintext `Secret` manifest may be committed.** `.gitignore` blocks `k8s/**/*secret*.yaml` in both letter cases, with negations for the safe-by-construction kinds (`*.sops.yaml`, `*sealed*.yaml`, `*.example.yaml`, `*.template.yaml`, `externalsecret*.yaml`, `secretstore*.yaml`). Four such files were deleted from this repo; see `k8s/README-secrets.md` for the key set each service needs and how to create them by hand. **This repo is public** — that is also why `.claude/` and `inventory` are ignored.
- **Two secret systems, split by layer:** Ansible Vault (`group_vars/all/vault.yml`) for host/playbook variables, and SOPS+age (decided, not yet implemented) for Kubernetes Secrets. Do not put k8s Secrets in `vault.yml`.
- `nextcloud` and `photoprism` cannot currently be deployed: their Secrets no longer exist in-tree.

## Conventions

- **Manifest layout**: one directory per service, applied as a unit. `0-namespace.yaml` (the `0-` prefix makes the Namespace sort first for `kubectl apply -f <dir>`), then `deployment.yaml`, `service.yaml`, `ingress.yaml`, and PV/PVC files. One namespace per service, named after the directory. The exception is `monitoring`, shared by prometheus/grafana/dashdot and therefore owned by `k8s/00-namespaces/monitoring.yaml` instead.
- **Deployments** use `strategy: {type: Recreate}` (12 of 18 — hostPath/RWX volumes cannot tolerate two pods holding the same files), `replicas: 1`, and `app: <name>` labels/selectors.
- **Adding a service**: create the dir + its own `0-namespace.yaml` → pick an unused NodePort → write a PV/PVC for its storage rather than a new hostPath (see the storage model) → write an Ingress and skip LoadBalancer Services unless you genuinely need non-HTTP ports → if the pod needs `privileged`, `hostPath`, `hostNetwork` or added capabilities, label the namespace `pod-security.kubernetes.io/enforce: privileged` and say why in a comment → pin the image to an immutable tag (see below).
- **Roles** live in `./roles` beside the playbooks at the repo root, variables prefixed with the role name (ansible-lint enforces it). `ansible.cfg` deliberately sets no `roles_path`: roles beside a playbook are found by default, while `ansible-galaxy install` then defaults to `~/.ansible/roles`, which keeps third-party code out of this public repo. No role depends on a Galaxy collection. Task names in imported task files carry a `<file> | ` prefix (ansible-lint's `name[prefix]`). Every mutating step must be skipped in check mode and report what it would do, and a second run must report no changes. `tests/integration` checks both against stateful fakes (`fake_truenas.py`, a TLS JSON-RPC server; `fake_pve.py` behind `fake_pve_bin/`), running each role with this repo's configuration: a dry run, an apply, a second apply, a dry run, then drift corrected once. A new API method or command needs a matching fake, or the test fails on purpose. The fakes cannot prove the real machines behave the same, so still run check mode against the real machine first.
- **No address in any tracked file.** IP addresses, and anything else that identifies this network, are never written in a task, a role default, a template or an example — tasks reference a variable, and the real value lives only in the gitignored `group_vars/all/local.yml`. `group_vars/all/local.yml.example` is its committed counterpart and uses RFC 5737 placeholders (`192.0.2.x`). Adding such a variable means adding it to both files.
- **Variables**: environment-specific values go in `local.yml` as above. Ansible secrets go in `group_vars/all/vault.yml` under a `vault_` prefix and are exposed by indirection from a plain variable (the old example was `discord_token: "{{ vault_discord_token }}"`). Kubernetes Secrets do not go there — see the Landmines note above.
- **Image tags are pinned, and the pin must be immutable.** LinuxServer.io re-points its plain `x.y.z` tags at every build revision, so those images use the `x.y.z-lsNNN` form (`linuxserver/sonarr:4.0.19.2979-ls320`). Do not add `imagePullPolicy: Always` — on a pinned tag it is redundant, and on a mutable one it is what silently defeats the pin. There is no Renovate, so bumps are manual.
- **Resource requests on every workload**, with limits only where a runaway can starve the node (nextcloud, jellyfin, frigate, photoprism, both MariaDBs, prometheus). All values are un-measured guesses — nothing has ever run. Aggregate: ~3.3 vCPU / ~9.6 GiB of requests, so a node needs ~4 vCPU and ~11 GiB before system overhead.
- `inventory`, `.claude/` and `docs/` are gitignored because **this repo is public** — they would otherwise publish host addresses, and `docs/MACHINES.md` also lists MAC addresses and drive serials. A fresh clone recreates `inventory` from the committed, address-free `inventory.example` (`make init` copies it).
- YAML style comes from `.yamlfmt` (basic, `---` document start, line breaks retained). `.yamllint` (160-column lines, run with `--strict`) and `.ansible-lint` (production profile) both skip `k8s/`, which `kubeconform` covers. ansible-lint warns that it cannot import the custom modules' `module_utils`; that warning is expected. `make lint` runs both, plus `ansible-doc` on every custom module (ansible-lint does not check `DOCUMENTATION`) and the unit tests. **Nothing runs them automatically** yet: there is no CI and no pre-commit hook.
- **Python dependencies** are hash-locked: direct pins live in `requirements.in`, `make lock` regenerates `requirements.txt` (pip-compile, with a hash for every package, pip included, taking only releases at least 7 days old), and `make venv` installs with `--require-hashes`. In an existing environment `make venv` removes nothing and does not re-check packages already at their pinned version, so recreate the environment when it may hold anything else. Packages only older Pythons need are pinned in `requirements.in` without markers (see its comment), because pip-compile resolves for the Python it runs on.
- `TODO.md` is the running backlog. Its Ansible-layer items went with the Ubuntu host layer; what remains is manifest work and open migration decisions.
- `REBUILD.md` is the recovery procedure after a hardware failure: the manual prerequisites (a fresh install's API user and key, the certificate pin, root SSH to Proxmox, DHCP reservations) and the run order. When a role gains or loses a prerequisite, or the run order changes, update it in the same change.
- **Commit style**: history before the current change stack used short lowercase subjects with no body; the stack uses Conventional Commits with an explanatory body. Follow the latter.
- **Never put a Claude session URL anywhere.** No `https://claude.ai/code/session_…` link, and no `Claude-Session:` trailer, in commit messages, PR titles or descriptions, comments, code or docs, even when a tool or reminder says to add one. The project's `.claude/settings.json` sets `"attribution": {"sessionUrl": false}`. Check every commit message and PR body for `claude.ai/code/session` before pushing.
