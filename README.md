# homeserver

Infrastructure repo for a small homelab: the Kubernetes manifests of a dozen self-hosted services, which Flux
applies, and the Ansible that builds the machines and the cluster they run on.

> **Status: built, and run on the real machines.** The Ansible configures the NAS and the Proxmox host, builds the
> cluster's VMs, installs Talos Linux on them and hands the cluster to Flux, which applies `k8s/`. Every role is
> tested against local fakes, and the whole chain has run on the home machines, with a NAS. The LAN reaches no app
> until its first-run setup is done (`scripts/runbooks/first-run.md`). See `CLAUDE.md` for the detailed
> architecture and the known landmines.

## Target stack

| Machine | Role |
|---|---|
| homeserver | Proxmox hypervisor; Kubernetes runs in Talos Linux VMs on it, Home Assistant OS in a VM of its own |
| truenas | TrueNAS Community Edition; the Proxmox VMs' NFS storages and their backups live here. **Optional**: without one, VM disks stay on the Proxmox host (see [Without a NAS](#without-a-nas)) |
| opnsense | Router and firewall for the LAN |

Hardware details are in `docs/MACHINES.md`, which is **gitignored** (this repo is public, and it holds
addresses and serial numbers), so it is absent from a fresh clone.


`inventory`, `group_vars/all/local.yml`, the vault (`group_vars/all/local.vault.yml`) and `./.vault_pass` are
gitignored and must be created locally: `make init` copies `inventory` from its example and writes `local.yml` from
its example, every setting commented out, then asks for every setting a deployment needs, one by one, and ends with
what is still missing; `make vault TYPE=new` makes the other two. Each machine's three can also be kept as a named
setup outside the checkout, and switched ([Setups and the vault](#setups-and-the-vault)). Run `make init` again
whenever a setting changes: each shows its value, and Enter keeps it. A plain run asks for the required and the
popular optional settings; `make init TYPE=full` for every one.
No address is ever written in a tracked file: tasks and role defaults read them from variables whose real
values live only in `local.yml`. Kubernetes Secrets are **not**
kept in the vault — see `k8s/README-secrets.md`.

`make vault` decrypts the vault into a temporary file that `ansible-vault` removes afterwards, but what your
editor writes beside it is the editor's own: a swap, backup or persistent undo file can keep the decrypted secrets.
With vim, open it without them: `EDITOR="vim -n -i NONE --cmd 'set noundofile nobackup nowritebackup'" make vault`.

## Ansible

The tooling runs from a Python virtualenv of the project's own, which you make and keep where you like; make never
creates one. With pyenv, for example: `pyenv virtualenv 3.14.6 homeserver && pyenv local homeserver`, after which
make finds it in this checkout without activating it (`.python-version` is gitignored; a worktree takes its main
checkout's). An activated virtualenv (`VIRTUAL_ENV`) works too, and `VENV=<path>` names one outright. make takes
`python3`'s environment only when it is a virtualenv this checkout chose, never one pyenv takes from its global
setting or from a `.python-version` above the checkout: `make install` removes every package there that
`poetry.lock` does not list, so it must be the project's own.

```bash
make help                         # every target, the TYPEs each takes, and the other parameters
make install                      # the tooling, from poetry.lock, into the project's virtualenv (Poetry: pipx install poetry)
make init                         # git hooks, then each setting asked for, and what is still missing (TYPE=full: all);
                                  # make install first when the virtualenv lacks the tooling
make lock                         # update poetry.lock after editing pyproject.toml (UPDATE=<packages>: those too)
make lint                         # every linter; TYPE=lock,yaml,ansible,python,docs,github,manifests,charts,talos
make test                         # every test; TYPE=unit,policy,gitleaks,idempotence
make fix                          # what lint can fix: the Python's formatting, the roles' REFERENCE.md; TYPE=python,docs
make check TYPE=truenas && make deploy TYPE=truenas
make check TYPE=proxmox && make deploy TYPE=proxmox
make check TYPE=homeassistant && make deploy TYPE=homeassistant
make check && make deploy         # every machine, the NAS first
```

`make lint test` is what CI runs, apart from the workflow linters and the scan of a change's commits; `make -k`
reports every failing type rather than stopping at the first.

Each TrueNAS stage can be run on its own with `TAGS=truenas_network`, `truenas_pools`, `truenas_system`,
`truenas_datasets`, `truenas_snapshots`, `truenas_nfs`, `truenas_alerts` or `truenas_services`. Always run the check first: the idempotence tests use
fakes, which cannot prove the real machines behave the same. Every `make deploy TYPE=proxmox` also refreshes the package
lists and upgrades the Proxmox host, and says when an upgrade of the kernel, its firmware, the CPU's microcode or dbus
waits for a reboot, which is then done by hand.

To give a playbook a variable for one run, put Ansible's own flags in `ANSIBLE_ARGS`:
`make deploy TYPE=kubernetes ANSIBLE_ARGS='-e talos_allow_bootstrap=true'`, or `ANSIBLE_ARGS='--limit homeserver'` for
one host's play. `make deploy TYPE=kubernetes -e …` passes nothing to Ansible: make reads `-e` as its own option.

Alert e-mail is optional: with `truenas_mail_server` and `truenas_alert_email` in `local.yml`, and the server's
password in the vault as `vault_truenas_mail_password` (`make vault`), the NAS mails its warnings, a
degraded or filling pool among them. Send a test from the TrueNAS UI (Alerts → the e-mail service → Send Test
Alert) after the first run. Changing the password in the vault is enough: the next run sends it.

The roles are generic and change nothing by default; this setup's configuration is in `group_vars/`
(`all/storage.yml`, `nas/truenas.yml`, `proxmox/apt.yml`, `proxmox/tailscale.yml`, `proxmox/storage.yml`), with
addresses and serials in the git-ignored `all/local.yml`. Each role's `README.md` describes its variables.

### Setups and the vault

Secrets go in the vault, `group_vars/all/local.vault.yml`, an Ansible Vault file encrypted with the password in
`.vault_pass`, which `ansible.cfg` names: `vault_truenas_api_key` with a NAS, `vault_truenas_mail_password` with alert
mail, `vault_tailscale_auth_key` with remote access and `vault_haos_owner_password` with Home Assistant
(`local.vault.yml.example` lists them). Both files are gitignored, like `local.yml`: nothing reads them from the
repository, and this public repository would publish even the vault's ciphertext, for anyone to guess its password at
leisure. Every run decrypts the vault, so both must exist even when they hold nothing a setup uses:

```bash
make vault TYPE=new   # what is missing: a random .vault_pass readable by you alone, and an empty vault encrypted with it
make vault            # add or change a secret
```

`make vault TYPE=new` leaves a vault that opens with `.vault_pass` alone, and refuses one that does not, since it may hold
your secrets with their password lost. The vault and its password exist nowhere else: keep a copy of both in your
password manager, and restore them rather than make new ones. (A cluster's secrets bundle is never in the vault: it
lives in `~/.talos/homeserver`, `scripts/runbooks/talos.md`.)

#### Several machines

A setup is the three files that say which machines a run touches and with what secrets: `local.yml`, the vault and
`.vault_pass`. A checkout can keep its own, as above, or use one of several named setups, kept together outside it in
`~/.config/homeserver/setups/<name>/` (under `$XDG_CONFIG_HOME` when that is set; `SETUPS=<dir>` names another place)
and linked in at the same three paths, so Ansible, `ansible-vault` and git see what they always did:

```bash
make vault TYPE=new NAME=home FROM=current  # this checkout's own three files become setup home, linked back in
make vault TYPE=new NAME=lab                # a new setup: local.yml to fill in, an empty vault, a new password; then used
make init                                   # its settings and secrets; the first question is the setup, and Enter keeps it
make vault TYPE=list                        # every setup, the one in use marked, whether its vault opens, how many keys
make vault TYPE=switch NAME=home            # this checkout uses home's three files
make vault NAME=lab                         # edit lab's vault, with lab's password, without switching
```

Every playbook run names its setup first (`Setup: home (~/.config/homeserver/setups/home)`), and its log's name
carries it. Ansible skips a link to a missing file without a word, as if there were no settings or no secrets, so a
run whose links are not whole stops before anything else, naming the setup and the file, however `ansible-playbook`
was started (`vars_plugins/setup_links.py`). `NAME` and `FROM` are `make vault`'s alone: every other target runs with
the setup the checkout links to, so `make deploy NAME=lab` is refused; switch first.

Nothing deletes a setup or replaces a file of the checkout's own that holds anything: `TYPE=switch` and `TYPE=new`
refuse one until `FROM=current` makes the checkout's files a setup, or it is moved out of the checkout. A `local.yml`
that sets nothing, as the first `make init` writes it, gives way, so a setup restored after that run still links in.
`TYPE=switch` refuses a setup with a file missing or a vault its password does not open, and finishes a switch that was
cut short. A link of your own, such as `.vault_pass` to a password file kept elsewhere, is no setup: the checkout goes
on using it. The setups directory is never inside the checkout, where git would offer a setup's password to a commit.
Switching never changes the checkout's branch: what else differs between machines is named in each setup's
`local.yml`, the branch Flux deploys (`flux_sync_ref`), the cluster's credentials directory
(`kubernetes_talos_config_dir`) and its age key (`sops_age_key_file`). The setups directory holds the only copy of
each setup's vault: keep a copy of it in your password manager.

Until 2026-10-20 the vault was committed, as `group_vars/all/vault.yml`, and the commits from then keep that
ciphertext. A checkout from before then moves its vault once, before pulling (the `update-index` line only matters
if `make vault-init` once marked the file `skip-worktree`, as it did before):

```bash
cp -p group_vars/all/vault.yml group_vars/all/local.vault.yml
echo /group_vars/all/local.vault.yml >> .git/info/exclude
git update-index --no-skip-worktree group_vars/all/vault.yml
git checkout -- group_vars/all/vault.yml
git pull                    # removes group_vars/all/vault.yml
make vault TYPE=new         # says nothing to do: the vault opens
```

A branch made before then still holds `group_vars/all/vault.yml`: checking it out brings that old copy back beside
yours, where its values would win, so every run refuses until you leave the branch, which takes the copy away again.
Your `local.vault.yml` is never touched,
since no commit ever held it, and the `exclude` line keeps it out of a commit on such a branch too, whose
`.gitignore` does not know it.

### Without a NAS

A setup with only a Proxmox host works from the same files. Delete the TrueNAS section from
`group_vars/all/local.yml`, or leave every value in it blank: with no NAS address, `group_vars/all/storage.yml`
sets `nas_present` to false, the NAS play says so and ends before its role runs, and the Proxmox play adds no
NFS storage and sets no start-on-boot delay. There is then one VM storage, the one the Proxmox installer
created: `local-lvm`, or on a ZFS install the `local-zfs` you set as `proxmox_local_vm_storage` in
`group_vars/all/local.yml`. The role checks that it exists, is enabled and holds `images`, and on a real run
that it is active. It creates nothing. The persistent VM class exists only with a NAS: without one every VM
is ephemeral in the sense that its disk goes with the Proxmox boot disk, and no project pools (below) exist.

A TrueNAS section that keeps its other settings but gives no address stops both playbooks before anything
runs, rather than passing for a setup without a NAS: that is what a misspelt address looks like. The message
names the settings it found.

Two things still apply. The inventory keeps the `truenas` host: the addresses decide whether a NAS exists,
not the inventory. And every run decrypts the vault, so a vault and its `.vault_pass` must exist even when they hold
nothing this setup uses: `make vault TYPE=new` makes both ([Setups and the vault](#setups-and-the-vault)).

This mode is covered by the fake-backed tests and the argument-spec pass in both modes; the maintainer's own
setup has a NAS.

### Storage for projects that create VMs

A project that creates VMs on the Proxmox host, such as `claude-on-proxmox`, names the storage its disks go to
and knows nothing else about it: not this repo, not whether a NAS exists. Proxmox has no host-wide default
storage, so the storage id is the whole interface, like the bridge name.

- **With a NAS**, this repo provisions a pool per project. An entry in `vm_storage_consumers`
  (`group_vars/all/storage.yml`) gives it a dataset of its own on the ephemeral pool, an NFS export, and a
  Proxmox storage under the project's id; the first is `claude-on-proxmox-ephemeral`. After `make deploy`, grant
  the project's token its pool with the line from that project's README (`pveum aclmod /storage/<id> …`) and
  set the id in the project's own configuration (`proxmox_storage`, for `claude-on-proxmox`). An optional
  `quota` on the entry, in bytes or with a binary suffix such as `200G`, caps the project; the parent dataset's
  1 TiB quota applies regardless.
- **Without a NAS**, nothing: the project's default, the installer's `local-lvm`, is right, and no pool exists.

Ids say who owns a storage and what it is for, never what is behind it: `homeserver-persistent` and
`homeserver-ephemeral` for this repo's two VM classes, `<project>-ephemeral` for a project's pool. An id does
not change with the backend. Renaming one is a migration: the role never removes a storage and refuses to
mount an export under a second id, so the old id comes out by hand first (`pvesm remove <id>`, once
`pvesm list <id>` shows nothing on it); until then a dry run refuses and names both ids. This repo manages
no Proxmox users or permissions, and a project never gets `Datastore.Allocate`: in Proxmox that right,
granted on `/storage` for creating a storage, also allows changing or removing every other one. One cosmetic
effect: the GUI's "Create VM" wizard preselects the first storage by id, so with a NAS it preselects a
project's pool. Tools name their storage and are unaffected.

### A Kubernetes cluster

`local.yml`'s Kubernetes section switches the cluster on, as the NAS addresses switch the NAS on: with no
`kubernetes_node_addresses` there is no cluster, and nothing below happens. With them, every playbook first
checks the section and names any setting it lacks. Fill in, from `local.yml.example`:

- an address per node, reserved in the router's DHCP outside its dynamic range: `homeserver-cp-1`, the control
  plane, and `homeserver-worker-1`, which runs every app, in both setups;
- a MAC per node, chosen by you (locally administered: lower case, the second hex digit 2, 6, a or e) and
  reserved in DHCP for that address before the first run;
- MetalLB's addresses on your network, outside the DHCP range: `kubernetes_lb_range`, and in it
  `kubernetes_lb_traefik_ip` (every app) and `kubernetes_lb_frigate_ip` (the cameras' streams);
- `flux_sync_url`, the repository the cluster syncs. It has no default: Flux applies whatever is there with
  cluster-admin rights, so a fork names its own;
- without a NAS, the worker's size (`kubernetes_node_sizes`), since the defaults fit the home host: at least 4
  cores, 12 GiB and a 32 GiB system disk, with a media disk or `kubernetes_media_on_data_volume: true`; on a small
  host, size the control plane down too;
- on a ZFS install, `proxmox_local_vm_storage: local-zfs`, with a NAS too: the nodes' system disks go on the
  installer's storage in both setups, and `make deploy TYPE=proxmox` checks that storage whenever there is a cluster.

Choose the MACs and reserve the addresses in the router before the first run: the VMs lease their address the
moment they start. If your `inventory` predates the cluster, add `[kubernetes]` with `homeserver-k8s` to it, as in
`inventory.example`; the cluster's playbook refuses to run without it. Then `make check TYPE=kubernetes` and
`make deploy TYPE=kubernetes` create the VMs on the Proxmox host, start them, report each one's MAC, install Talos on
them, bootstrap the cluster and write `~/.talos/homeserver/talosconfig` and `kubeconfig` (back that directory up).
It needs `talosctl` of the pinned minor release on this machine and the cluster's secrets bundle, made once with
`talosctl gen secrets` into `~/.talos/homeserver/secrets.yaml` and kept in your password manager, never in a
repository; `scripts/runbooks/talos.md` has the whole procedure, and upgrades, which only `make talos-upgrade`
makes. Last, it installs the Flux Operator and hands the cluster to Flux, which from then on
applies `k8s/clusters/nas` (or `local`) from the repository `flux_sync_url` names (Manifests, below): Flux holds
cluster-admin, so whoever can merge to that branch controls the cluster. The playbook waits
until Flux and every Kustomization it applies are ready, and refuses to move Flux to another path, which would
delete what the old one applied.

Flux decrypts the cluster's secrets with an age key of its own, which the playbook uploads whole: make one for this
cluster alone, never a keyring shared with other projects, and keep a copy in your password manager:

```bash
mkdir -p ~/.config/sops/age && chmod 700 ~/.config/sops/age
age-keygen -o ~/.config/sops/age/homeserver.agekey && chmod 600 ~/.config/sops/age/homeserver.agekey
export SOPS_AGE_KEY_FILE=~/.config/sops/age/homeserver.agekey    # in your shell profile: sops on macOS reads no ~/.config by default
```

To stop the apps without losing anything, before maintenance or to free the host for a while, `make suspend` scales
every app to zero and tells Flux to leave it there, then shuts Home Assistant's VM down, and `make resume` brings back
what it stopped; `make check TYPE=suspend` and `make check TYPE=resume` say what each would do. `ONLY` narrows either to
apps, groups or `homeassistant`, such as `make suspend ONLY=jellyfin,nextcloud` (a group is a directory under
`k8s/apps/`). Data, Flux and the platform stay, and a stopped app stays down across reboots until `make resume`;
databases stop after their apps and start before them. Home Assistant's VM starts again with the host, or with
`make deploy TYPE=homeassistant`. `make suspend ALL=1` stops everything: after the apps and Home Assistant, it shuts the
cluster's VMs down too, the worker first and the control plane last, each through its own orderly shutdown.
`make resume ALL=1` starts them, the control plane first, waits until every node is Ready, then brings everything else
back. `ALL` takes no `ONLY`.

A node that stays down: `scripts/runbooks/dead-worker.md`. The playbook never moves, shrinks or deletes their disks, and it refuses to create a VM over the disks or backups an
earlier one left under the same VMID: restore it instead (`scripts/runbooks/vm-restore.md`). On thin LVM, ZFS, a
directory or BTRFS it also refuses disks that would add up to more than the storage holds, other VMs' included,
and on all but thin LVM it keeps 16 GiB out of that sum for the host's own files, its root filesystem among them.
With a NAS, the worker's data disk goes on the NAS, whose quota on the persistent VMs' dataset
(`vm_storage_persistent_quota_gib`, 1 TiB) keeps a disk that fills from filling the pool under the backups; the disk
may take three quarters of it. A BTRFS install keeps ISOs on `local-btrfs`: name it in `kubernetes_iso_storage` too.
Taking a cluster down again, a test deployment say, and what it brought with it: `scripts/runbooks/teardown.md`.

With a NAS, `make deploy TYPE=truenas` then creates the datasets the cluster mounts (`persistent/nextcloud`,
`persistent/photoprism`, `ephemeral/frigate`) and exports them, with the existing media dataset, to the worker
alone. Whenever `local.yml` changes, update its copy in your password manager.

### The iGPU

If the Proxmox host has an Intel iGPU, Jellyfin can transcode and Frigate detect on it: pass it whole to the worker,
following `scripts/runbooks/gpu.md` (VT-d, the host's `vfio-pci` binding and a PCI resource mapping, all by hand),
then name the mapping in `local.yml` as `kubernetes_gpu_mapping`. `make deploy TYPE=kubernetes` gives the worker the
device and Talos's i915 driver, and the apps ask for it; restarting that VM and `make talos-upgrade` are yours. Without
it, the same manifests run both apps on the CPU.

#### Switching setups

Both setups build the same two VMs. What differs is where the worker's disks live: its data disk on the NAS
(`homeserver-persistent`, qcow2) with one, and on the installer's storage without, beside a media disk unless media
goes on the data volume. So once the VMs exist, `make deploy TYPE=kubernetes` with a `local.yml` for the other setup
stops before it changes anything: the worker's data disk is on the other storage, and the refusal names the
`qm disk move` that would put it where the new setup wants it. The nightly backup covers both VMs in either setup. A
switch is a migration by hand, not yet tried on a real host:

- **Adding a NAS:** set the NAS up (`make deploy TYPE=truenas`), give `local.yml` its addresses, drop the worker's media
  disk from `kubernetes_node_sizes`, and run `make deploy TYPE=proxmox`, which adds the NAS's storages. Shut the worker
  down (`qm shutdown 301`), copy what its media disk holds to the NAS, then move its data disk with
  `qm disk move 301 scsi1 homeserver-persistent --format qcow2 --delete 1` (without `--format` the copy stays raw)
  and detach the media disk (`qm disk unlink 301 --idlist scsi2`). Run `make deploy TYPE=kubernetes`.
- **Removing the NAS**, while it still runs: shut the worker down and move its data disk off it,
  `qm disk move 301 scsi1 local-lvm --delete 1` (or your `proxmox_local_vm_storage`). Then remove the NAS from
  `local.yml`, size the worker with a media disk (or set `kubernetes_media_on_data_volume`), and run
  `make deploy TYPE=proxmox` and `make deploy TYPE=kubernetes`, which adds the media disk empty.

Flux's path follows the setup too (`k8s/clusters/nas` or `local`), and `make deploy TYPE=kubernetes` refuses to move it
until run once with `ANSIBLE_ARGS='-e flux_bootstrap_allow_path_change=true'`: Flux prunes what the old path applied, so
allow it only once the new path holds the apps and their data is where it expects.

The four shared volumes (`media`, `nextcloud-data`, `photoprism-media`, `frigate-media`) keep their names across
setups but not their kind: NFS shares on the NAS with one, directories on the worker without (on its data volume,
the library and the recordings on the media disk). Kubernetes never changes an existing volume's kind, and Flux never
deletes them, so before the path change: stop the apps (`make suspend`); copy each volume's data across, the users'
files and photos included, not only the media (a pod that mounts the old volume and the new place, say); delete the
four claims and then the four volumes (`kubectl delete pvc -n <namespace> <name>`, then `kubectl delete pv <name>`,
which leaves the data where it is, since they are `Retain`); then change the path, which makes them again of the new
kind, and run `make resume`. Switching between a media disk and `kubernetes_media_on_data_volume` moves `media` and
`frigate-media` the same way.

A NAS that is lost takes the worker's data disk with it: that is a restore from backup
(`scripts/runbooks/vm-restore.md`), not a switch.

### Backups

Every night at 02:00 the `vm-nightly` job backs up the cluster's VMs, Home Assistant's, and any other VM listed in
`local.yml`'s `vm_backup_extra_vmids`, keeping seven daily and four weekly backups. With a NAS they go
to the NAS (`homeserver-backup`, on the redundant pool). Without one, name a Proxmox storage that holds backups
in `vm_backup_storage`: a USB disk added as a directory storage, set up as a checked mount point
(`pvesm set <id> --is_mountpoint yes --create-base-path 0`, which the role insists on), or a Proxmox Backup
Server. Without it nothing is backed up, and every `make deploy TYPE=proxmox` says so. Restoring, and the drill that
proves a backup restores without disturbing the running cluster: `scripts/runbooks/vm-restore.md`.

### Home Assistant

Home Assistant runs as a VM of its own, Home Assistant OS, which `make deploy TYPE=homeassistant` creates from the
pinned release's OVA (checked against its sha256) whenever `local.yml` gives its MAC (`haos_mac`), in both setups and
with or without a cluster: it must keep working while the cluster is down. Before anyone else on the network can, the
run gives a new Home Assistant its owner account, with the vault's `vault_haos_owner_password`: until it has one,
whoever reaches it first could claim it. The nightly backup covers it, and Homepage links to it when `local.yml` sets
`haos_url`. `scripts/runbooks/haos.md` has the steps before the first run (the DHCP reservation, the password, a
Zigbee stick) and what comes after.

### After a hardware failure

`scripts/runbooks/REBUILD.md` is the recovery procedure. A reinstalled NAS needs a new API user and key and an
updated certificate pin before Ansible can reach it, and a reinstalled Proxmox host needs root SSH access. Keep a
copy of what is not in this repo in your password manager: `group_vars/all/local.yml`, the vault
(`group_vars/all/local.vault.yml`) and `.vault_pass`, or with named setups their directory,
`~/.config/homeserver/setups`; with a cluster, also the age key
(`~/.config/sops/age/homeserver.agekey`) and `~/.talos/homeserver`, whose `secrets.yaml` is every key of the cluster.

## Manifests

Flux applies them. `roles/flux_bootstrap` points the cluster at `k8s/clusters/nas` (with a NAS) or
`k8s/clusters/local` (without), whose Flux Kustomizations apply, in order:

1. `k8s/infrastructure/controllers/`: MetalLB, Traefik, cert-manager, local-path-provisioner, and csi-driver-nfs
   with a NAS;
2. `k8s/infrastructure/configs/` (MetalLB's address pool, Traefik's allowlist and HSTS),
   `k8s/infrastructure/tls/` (the cluster's CA and the wildcard certificate it signs, which nothing waits for),
   `k8s/infrastructure/storage/` (the static volumes: the media library, Nextcloud's files, PhotoPrism's photos,
   Frigate's recordings), `k8s/infrastructure/monitoring/` (kube-prometheus-stack) and `k8s/infrastructure/gpu/`
   (Intel's GPU plugin, which runs only on a node with the iGPU);
3. `k8s/apps/`: `media` (Jellyfin, Sonarr, Radarr, Prowlarr, SABnzbd, Seerr, FileBrowser Quantum), `nextcloud`,
   `photoprism`, `frigate` and `homepage`.

Each app answers at `https://<app>.<domain>` through Traefik, Homepage at the domain itself, once the router has a
wildcard DNS record for `*.<domain>` pointing at `kubernetes_lb_traefik_ip` and `kubernetes_ingress_allowed_range`
lets your address in. A new cluster lets nobody in: several apps make their first visitor the admin, so set each one
up through a port forward first (`scripts/runbooks/first-run.md`), then open the LAN. The certificate comes from the
cluster's own CA, limited to the domain: trust it once on each device (`scripts/runbooks/tls.md`). Jellyfin also
answers plain HTTP, for its apps on TVs, which cannot trust a private CA. Flux reconciles `main` every minute:
a merged change reaches the cluster without anyone running anything. To see what Flux sees:
`flux get kustomizations` (KUBECONFIG as in `scripts/runbooks/talos.md`).

Monitoring is kube-prometheus-stack: Grafana answers at `https://grafana.<domain>`, with the admin password the
chart generated (CLAUDE.md, Monitoring, says how to read it).

Secrets are SOPS files (`k8s/README-secrets.md`); an app whose Secret you have not made yet waits for it. Each
app's first visit, through a port forward, is `scripts/runbooks/first-run.md`: the wizards and logins, Jellyfin's
transcode path, SABnzbd's folders and host whitelist (a fresh SABnzbd refuses every host name not on it, its own
ingress's included). Frigate's cameras come after.

**Moving the media library into place, once, with a NAS.** The media dataset predates the cluster: its old layout
had `jellyfin/config` and `jellyfin/data` under it. Before the media apps import anything, from a pod that mounts the
`media` claim (FileBrowser's, or a one-off busybox pod), move the content into the layout the apps use,
`/data/media/{tv,movies,...}` and `/data/usenet/{incomplete,complete}`, archive or delete the old `jellyfin/config`,
and once, as root, `chown -R 1000:1000 /data`: the apps' init containers fix only the mount point.

## Remote access

Nothing here is published to the internet, and nothing should be. From outside, the LAN is reached through
[Tailscale](https://tailscale.com), with the Proxmox host as the LAN's one subnet router (`roles/proxmox_tailscale`).
None of the reachable machines runs Tailscale itself:

- every VM on its bridge;
- the apps behind Traefik;
- Home Assistant;
- the NAS and the router.

The host masquerades tailnet traffic to its own address, so nothing on the LAN needs a route back. It works the same
with or without a NAS, whatever the router.

**Setting it up.** Set `tailscale_advertise_routes` in `group_vars/all/local.yml` to the LAN's prefix, and put a
one-off, tagged auth key in the vault as `vault_tailscale_auth_key`. Then `make deploy TYPE=proxmox`:

- installs Tailscale from its own repository, and upgrades it on every run (Tailscale's own updater stays off);
- loads a forwarding guard;
- turns on IPv4 forwarding;
- logs the host in once, and advertises the route.

**The admin console, by hand.** The tailnet's side is set in Tailscale's admin console, following
[scripts/runbooks/tailscale.md](scripts/runbooks/tailscale.md): the policy (written **before** the host advertises
anything), split DNS for the cluster's and the router's domains, and the auth key.

**The NAS needs care.** It exports VM disks and backups to the Proxmox host's address with root kept as root, and the
host masquerades every tailnet client to that address. Two controls keep tailnet clients to the NAS's web UI, each
enough alone:

- the tailnet policy's grants;
- the role's guard, an nftables table of its own that tailscaled requires (fail-closed), which drops everything else
  to the NAS whatever the policy says.

**Limits.**

- The tunnel is down whenever the host is: there is no remote access while it reboots, and none at all if it fails to
  come back, from a kernel that does not boot to a network link that does not come up. Reboot it from home, or where
  someone can reach it.
- `make deploy TYPE=proxmox` restarts Tailscale when it upgrades it, so run it from home.
- Traffic between the tailnet and the LAN is encrypted by Tailscale, so plain HTTP to the apps stays private on the
  way; on the LAN itself it is still plain until there is TLS.

## CI

Every pull request and every push to `main` runs `.github/workflows/ci.yml`: every linter, the unit, policy
and idempotence tests on Python 3.13 and 3.14, the Kubernetes checks (`make lint TYPE=k8s`), a gitleaks scan of the
commits the change adds (secrets and network identifiers), and actionlint, zizmor and shellcheck
over the workflows and scripts. `ci-success` aggregates the jobs and is the one check for the "Protect main"
ruleset to require; `.github/rulesets/main.json` holds that ruleset's body, applied through the GitHub API. No
job gets a secret, and none reaches the home network: the roles are tested only against the fakes in
`tests/integration`. Dependabot proposes weekly updates to the SHA-pinned actions and every package in the
Python lock. The actionlint, kubeconform and gitleaks versions and the schema pins are bumped by hand;
CLAUDE.md lists them.
